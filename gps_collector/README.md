# GPS-1 — коллектор точек Wialon

Тянет сообщения из Wialon и кладёт точки в помесячные файлы SQLite. Больше
ничего не делает: геометрию не считает, гектары не считает, в `transport.db`
не пишет и не читает. Расчёт — это GPS-2 (`gps/daily.py`), и он отдельный
процесс.

Техническое задание — `docs/GPS_PLAN_FAKT_VISION_ROADMAP.md` §5.1.

---

## Почему это отдельный пакет со stdlib

| Кто | Что делает | Что импортирует |
|---|---|---|
| `gps_collector/` | тянет сообщения, кладёт точки | **только stdlib** |
| `gps/daily.py` | считает участки за сутки, пишет агрегаты | `gps.area` (геостек) |
| приложение Flask | только читает агрегаты | `models.py` |

Коллектор — служба. Служба, которая тащит numpy/shapely ради модуля, который
никогда не вызывает, платит за них при каждой установке и при каждом
обновлении, а одно сломанное колесо останавливает **сбор точек**, а не только
арифметику. То же правило уже действует между `drone_collector` и приложением.

Коллектор не импортирует ни `app`, ни `models`: `app = create_app()` вызывает
`db.create_all()` на импорте, и любой скрипт с `from app import app`
становится писателем в базу приложения.

В `transport.db` коллектор пишет ровно одно и ровно после прогона — строку
журнала приёма (`gps_sync_log`, GPS-7), через stdlib `sqlite3`. Любая ошибка
этой записи печатается и проглатывается: точки важнее записи о точках, и
упавший журнал не должен стоить ночи сбора.

---

## Что он делает за один прогон

1. **Один** запрос отдаёт весь парк вместе со временем последнего сообщения
   каждого объекта, его датчиками и счётчиками (`core/search_items`, флаг
   `0x3401` — имя, последняя позиция, датчики, счётчики; до GPS-24 был 1025).
   Объекты, молчащие дольше `SILENT_DAYS = 30`, не спрашиваются вовсе: на
   18.08.2026 это 183 объекта из 481.
2. По каждому оставшемуся объекту: интервал от его watermark до «сейчас минус
   `LAG_MINUTES = 30`», загрузка сообщений, `messages/unload`, запись точек.
   Рядом с каждой точкой — значение датчика зажигания (GPS-24, ниже).
3. **Watermark двигается только после того, как точки записаны и
   зафиксированы.** Это весь замысел: падение между двумя шагами стоит
   повторно загруженного интервала, который `INSERT OR IGNORE` проглатывает.
   Обратный порядок стоил бы дыры в истории, о которой никто никогда не
   узнает — сутки просто вышли бы с меньшим числом гектаров.

### Хранилище

```
instance/gps_points_202608.db     точки августа: points(unit_id, t, lon, lat, speed, course, sats, ign)
instance/gps_points_202607.db     точки июля
instance/gps_collector_state.db   collector_watermarks(unit_id, last_t, updated_at)
                                  collector_units(unit_id, name, seen_at)
                                  collector_counters(unit_id, last_t, cneh, cfl, taken_at)
```

`collector_counters` — снимок счётчика моточасов Wialon каждым прогоном
(GPS-25, с 19.10.2026): `cneh` в часах на момент последнего сообщения
объекта `last_t`, `cfl` — как Wialon его считает. Приходит тем же запросом
списка (флаг `0x3401` — ровно флаги прогона GPS-23). Разность двух соседних
снимков — моточасы, которые Wialon насчитал сам по тому же датчику
зажигания; против них `tools/gps_engine_hours_check.py` проверяет правило
часов метода «время» (предрегистрация — трек GPS, §0.6). Строки только
добавляются; повтор того же `(unit_id, last_t)` не пишется.

`collector_units` — имя каждого объекта из списка парка Wialon (с 09.10.2026).
Список с именами коллектор получает первым запросом прогона и раньше только
печатал; теперь имена кладутся в файл отметок до загрузки точек, для всего
парка, и экран «Факт по технике» называет ими объекты без строки
сопоставления вместо голого номера. Пустое имя прежнее не затирает, строки
не удаляются: у объекта, исчезнувшего из Wialon, остаётся последнее имя.
Таблица создаётся сама (`CREATE TABLE IF NOT EXISTS`) первым же прогоном
новой версии; приложение читает её только `mode=ro`.

### Зажигание (GPS-24, с 19.10.2026)

Метод «время» сверки заявок (решение владельца 09.10: моточас — время с
включённым зажиганием по трекеру) стоит на одном значении в точке: `ign` —
**сырое** значение параметра датчика зажигания объекта в этом сообщении.

- Датчик — тип `engine operation` из `sens` объекта в списке парка; его
  параметр берётся тем же запросом списка, лишнего запроса нет. Обзор GPS-23
  на production 19.10: 621 объект, у 620 датчик зажигания; параметры —
  `io_239` (543), `in` (76), `spn183` (1).
- `io_239`, `spn183` и прочие — ключи `p` сообщения. `in` и `inN` — нет: это
  цифровые входы Wialon в поле `i` (битовая маска): `inN` — бит N, считая с 1
  справа, `in` — сумма всех входов.
- Значение хранится сырым, не «вкл/выкл»: что считать работой, коллектор не
  решает. Wialon считает цифровой датчик выключенным при нуле и включённым
  при любом другом значении, но датчик может сидеть и на напряжении с
  таблицей — правило применит суточный расчёт часов.
- `NULL` — у объекта нет датчика зажигания, сообщение не несло параметра,
  выражение вместо имени параметра (не вычисляется), или точка легла до
  GPS-24.
- Файлы месяцев, созданные раньше, колонки не имеют: `open_points` проверяет
  её через `PRAGMA table_info` и добавляет `ALTER TABLE ... ADD COLUMN`.
  Колонка допускает `NULL`, ALTER файл не переписывает. **Откат кода** —
  `git revert`; колонка остаётся, старый код пишет точки по именам колонок и
  её не читает — **с данными делать ничего не нужно**.
- Повторная загрузка интервала заполняет только пустой `ign`: координаты,
  скорость и спутники остаются как легли впервые, известное значение не
  заменяется.

Строка прогона в журнале: `ignition: N of M points with a position carry it |
asked objects without an ignition sensor: K | filled into points stored
before: F | engine-hour counters noted: C`. В `gps_sync_log` эти числа не пишутся — схема журнала не менялась.

### Дозаполнение прошлых недель — `gps_collector.refill`

Точки, лёгшие до GPS-24, зажигания не имеют. Дозаполнение перечитывает
период из Wialon и пишет `ign` **только в уже лежащие точки** (`UPDATE ...
WHERE ign IS NULL`):

- точку не вставляет: сообщение, которого ночной сбор не сохранил, так и
  остаётся несохранённым — иначе изменились бы точки посчитанных суток;
- известное значение не заменяет, координаты не трогает;
- watermark не двигает;
- объект без пустых точек в периоде не спрашивает вовсе: повторный прогон
  спрашивает только то, что ещё не заполнено;
- грузит промежуток пустых точек объекта кусками по
  `MAX_MESSAGES_PER_INTERVAL`, обрезанный кусок продолжает с последнего
  сообщения.

```
cd C:\transport-report
```

```
& "C:\Program Files\Python314\python.exe" -m gps_collector.refill --from 2026-09-01 --to 2026-10-19 *> gps_refill.log
```

`--to` включительно. Не во время ночного сбора в 01:00. Консоль печатает по
месяцам «точек / с зажиганием» до и после. Коды выхода: 0 — готово; 1 —
часть объектов не прочитана (прогон можно просто повторить); 2 — плохой ввод
(даты, пустой период, нет папки точек); 3 — вход отклонён.

Первичный ключ `(unit_id, t)` — повторная загрузка того же интервала не даёт
дублей. Точка попадает в файл **своего** месяца по местному времени (UTC+5),
поэтому интервал, пересекающий полночь первого числа, делится, а не теряется.

Ретенция 90 дней — это удаление файла, а не `DELETE` и `VACUUM`:

```
del C:\transport-report\instance\gps_points_202605.db*
```

Звёздочка не украшение: файлы в режиме WAL, рядом лежат `-wal` и `-shm`.

Watermark лежит **отдельно от точек** намеренно: он обязан пережить удаление
месяца, иначе ретенция сказала бы коллектору, что он никогда ничего не
собирал, и следующий прогон пошёл бы за всей историей по каждому объекту.

## Запуск

Токен — `wialon_token.txt` в рабочей папке или в корне репозитория, либо
переменная `WIALON_TOKEN`. Не печатается никогда.

```
cd C:\transport-report
```

```
& "C:\Program Files\Python314\python.exe" -m gps_collector.main *> gps_collect.log
```

Перенаправление вывода в файл — не украшение. Консоль Windows в режиме
выделения (включается случайным щелчком в окне) останавливает процесс на
первом же выводе, и это стоило треку трёх суток ожидания прогона, который все
считали медленным. Процесс, пишущий в файл, так остановить нельзя.

Аргументы: `--dir`, `--pause` (по умолчанию 2 с, решение G9), `--backfill-days`
(насколько назад идёт первый прогон по объекту), `--silent-days`,
`--lag-minutes`, `--only <wialon_id>` (можно повторять).

### Сколько это стоит

Замерено `tools/wialon_measure_cost.py`: `messages/load_interval` по машине с
2718 сообщениями за сутки отвечает за **0,4 секунды**. Темп задаёт не сервер, а
наша собственная пауза: 298 объектов × 2 запроса × 2 с ≈ **20 минут** за ночь.

## Тракт запросов перенесён, а не написан заново

Каждая гвардия в `wialon.py` оплачена провалившимся прогоном
`tools/wialon_probe6_fleet_health.py`:

- пауза между запросами (решение G9) — после потери доступа 14.08 на ~2000
  запросов за 40 минут;
- **жёсткий срок на запрос целиком через поток**: `timeout` у `urlopen` — на
  одну операцию с сокетом, и собеседник, отдающий по байту в полминуты,
  держит чтение вечно. Прогон 16.08 простоял на одном объекте сутки;
- три повтора с растущей паузой — один разрыв связи убивал сорокаминутный
  прогон;
- коды 1003/1004/1005 — это «подожди», а не отказ: пауза и один повтор;
- отказ во входе по лимиту неудачных входов с адреса (1003, «LIMIT
  invalid_logins» — их делает кто-то другой с адреса кластера) — пауза
  65 с и до шести попыток (GPS-31): 20.10 ночь пропала, когда отказали
  обе прежние две;
- скользящий двухминутный бюджет сообщений, половина документированного
  потолка;
- `messages/unload` после каждой загрузки;
- ASCII в консоль: 18.08 прогон умер на «Нива 80 350 SBA (Ҳокимият)», потому
  что U+04B2 не существует в cp1251. Половина парка названа по-узбекски.

**Только чтение.** Используются `token/login`, `core/search_items`,
`messages/load_interval`, `messages/unload`, `core/logout`. Метода, который мог
бы что-то изменить в Wialon, здесь нет по построению.

## Тесты

```
& "C:\Program Files\Python314\python.exe" -m unittest discover -s gps_collector/tests -t .
```

Ожидается `Ran 85 tests` и `OK`. Сети не требуется: сервер заменён
консервами, код коллектора при этом выполняется целиком. Журнал приёма
(GPS-7) проверяется в общем наборе — `python -m unittest tests.test_gps_sync_log`.

Четыре критерия приёмки закрыты так:

| Критерий | Чем проверен |
|---|---|
| Повторный прогон не добавляет ни строки | `RepeatRun` — два теста: один на watermark, второй сбрасывает watermark и проверяет **ключ** |
| Сбой между загрузкой и записью не двигает watermark | `CrashBetweenLoadAndWrite` — дочерний процесс убивается `os._exit(9)` между шагами |
| За ночь: темп и ни одного повторного логина | `NightlyRun` — 1 логин, ровно 2 запроса на объект, пауза меряется секундами |
| Смена месяца ничего не теряет и не дублирует | `MonthBoundary` — интервал через полночь 1 августа: 1379 точек в июле, 60 в августе |

**У теста на watermark есть отрицательный контроль.** Дочерний процесс умеет
работать и в неправильном порядке (`wrong-order-crash`: сначала watermark,
потом точки), и тест требует, чтобы в этом случае watermark **сдвинулся**. Без
этого проверка давала бы одинаковый результат при верном и неверном коде.

Мутационная проверка (2026-08-19), каждая мутация поймана:

| Мутация | Упало тестов |
|---|---|
| watermark не двигается никогда | 5 |
| фильтр молчащих объектов убран | 1 |
| месяц файла считается по UTC | 4 |
| гвардия обрезанного ответа убрана | 1 |
| долгота и широта переставлены | 1 |
| правка без изменения поведения (контроль) | 0 |

### GPS-24 — зажигание (19.10.2026)

`gps_collector/tests/test_ignition.py`, 42 теста (с GPS-25 — снимки
счётчика, `CounterSnapshots`):

| Что держится | Чем проверено |
|---|---|
| Параметр датчика — из списка парка, тем же запросом (флаг `0x1401`) | `IgnitionParam` (4), `CollectorStoresIgnition.test_the_sensors_come_with_the_unit_list_request` |
| `io_239` — из `p`, `in` — сумма входов поля `i`, `inN` — бит N; ничего не угадывается | `IgnitionValue` (7) |
| У точки сырое значение; у объекта без датчика — `NULL` | `CollectorStoresIgnition.test_each_point_carries_its_raw_ignition_value` |
| Старый файл месяца получает колонку и сохраняет точки; гонка двух ALTER — не ошибка | `IgnitionColumn` |
| Повтор заполняет только пустой `ign`, координаты и известное значение не меняет | `IgnitionColumn`, `CollectorStoresIgnition.test_a_replay_brings_ignition_to_points_stored_without_it` |
| Дозаполнение: только лежащие точки, ни одной вставки, watermark на месте, второй прогон ничего не спрашивает, обрезанные куски доходят до конца | `FillIgnition`, `Refill`, `RefillCommand` |

Мутационная проверка (19.10.2026): 15 мутаций — каждая поймана, контроль
без изменения поведения — 0 падений. Среди мутаций: вход `in` ищется в `p`
(как у GPS-23), `in` как сырая маска, бит `inN` со сдвигом на один, список
парка без датчиков, повтор перезаписывает известное значение или
координаты, нет ALTER для старых файлов, дозаполнение вставляет точки,
двигает watermark, останавливается на обрезанном куске, спрашивает
заполненные объекты, грузит промежуток без запаса в секунду.

## Чего коллектор не делает

- Не решает, что считать работой, а что проездом. Зажигание кладёт сырым
  значением; «вкл» и часы — дело расчёта.
- Не считает площадь.
- Не пишет и не читает `instance/transport.db`.
- Не пишет в Wialon.
