## 1. Коротко

1. В репозитории есть полный облачный тракт DJI SmartFarm: сборщик на
   Playwright, который **слушает** запросы сайта и не подписывает своих;
   очередь на диске; четыре приёмника с токеном в теле; неизменяемые ревизии
   источников (`list`, `card`, `route`, `v4`, `airlines`, каталог полей);
   декодер V4 с семантикой «присутствие ≠ ноль»; четыре несмешиваемые
   величины площади; append-only решения администратора. Карта — §2.
2. Облако уже даёт больше, чем формулирует ТЗ §0.4: кроме времени,
   координат, ширины, `spray_flag` и `flow` декодер читает скорость, высоту,
   режим, остаток и счётчик раствора, а в блоке состояния — батарею,
   RTK/режим позиционирования, ветер, число спутников. Степень
   подтверждения смысла этих полей разная; таблица — §3.
3. Ни одного упоминания пульта как источника данных, Android, APK, ADB в
   коде и документах нет (поиск по репозиторию). Типа происхождения `RC`
   в схеме нет, и приёмник `source_sync` отказывает любому типу вне
   пяти облачных (`dji_area/evidence.py:48`, `dji_area/store.py:187`). Это
   правильно: экспериментальный файл пульта в боевой тракт не попадёт даже
   по ошибке.
4. Подготовлен инструмент `tools/dji_rc_probe.py` — опись папки с файлами,
   снятыми с пульта, **только чтением**: класс по содержимому, SHA-256,
   перепись protobuf без значений, «похоже ли на V4 / маршрут облака»,
   маркеры секретов, сравнение двух V4, снимок в изолированную папку с
   проверкой хеша. 37 тестов на синтетике, 7 из 7 мутантов убиты, шаг в CI.
   Результаты проверок — §9.
5. Подготовлен план этапа 0Б — `docs/DJI_RC_COLLECTOR_001_SURVEY_PLAN.md`:
   три раздельные проверки доступа (USB с компьютера, штатный экспорт,
   обычное приложение), паспорт пульта без секретов, полевой тест на воде,
   команды PowerShell для владельца, шаблон матрицы возможностей.
6. Чего нет и не будет до 0Б: Android-приложения, таблиц и миграций под
   `RC`, приёмника, маршрута в сеть, изменений сборщика, площади, решений и
   финансов. Искусственные файлы инструмента доказательством доступа к DJI
   не являются (ТЗ §0.7).

## 4. Ограничения, которые новый источник обязан соблюдать

Из `CLAUDE.md`, `docs/AGENT_SESSION.md`, трека, консенсуса и ТЗ §0; здесь —
только те, что прямо задевают проект пульта, с местом в коде.

1. Машина определяется только по нику через `drone_nicknames`; аппаратный
   ID — `hardware_id` карточки/маршрута; `serial_number` — никогда
   (`models.py:1720`, `:1840`; ТЗ §0.3). Новые аппаратные идентификаторы —
   наблюдения с происхождением, не правка связей.
2. `source_sync` принимает пять облачных типов и перестраивает указатели
   доказательств — файл пульта туда не отправляется (`drones.py:1662`;
   ТЗ §0.6). `route_sync` связывает только с известным вылетом
   (`drones.py:1293`).
3. `drone_sync_logs` — только приём вылетов, инвариант `seen = new +
   duplicates + errors` (`models.py:1805`). События пульта туда не кладутся.
4. V4 не несёт flight id; идентичность — путь захвата + окно
   (`evidence.py:331`, `v4.py:490`). Для файла пульта облачный путь
   неприменим; совпадение времени — не доказательство (ТЗ §0.4).
5. Присутствие поля ≠ ноль (`v4.py` докстринг, `summarize_v4`). Пропуск
   protobuf не превращается в ноль; `flow = 0` при неисправном датчике не
   доказывает отсутствие распыления (ТЗ §3.4).
6. RAW не переписывается; принятая площадь — техническая; без расчёта —
   `NOT_CALCULATED` (`accepted.py:200`); retained-footprint — 12 м и 0,027
   только для своего правила (`footprint.py:44-45`).
7. Решения администратора append-only; поступление данных с пульта не
   меняет решения, принятые показатели, отчёты, финансы (`models.py:3318`;
   ТЗ §0.5).
8. Секреты не хранятся и не печатаются (`store.py:175`, `outbox.py:158`);
   `DRONE_API_TOKEN` — общий секрет сборщика, на пульты не ставится.
9. Общие файлы (`app.py`, `models.py`, `templates/base_next.html`,
   `static/css/design-system.css`, `migration_utils.py`, `excel_export.py`)
   в этом этапе не тронуты; замороженные файлы модели площади — тоже.
10. Схема без миграции не меняется; production, пульт, прошивки и сеть из
    сессии не меняются (ТЗ §0.7).

## 5. Что может добавить источник с пульта — гипотезы для 0Б

Все пункты — `ГИПОТЕЗА`; у каждого названо, чем он проверяется на 0Б.
Ничто из этого не подтверждено.

| № | Гипотеза | Чем лучше облака, если верна | Как проверить на 0Б |
|---|---|---|---|
| H1 | Записи вылета появляются на пульте раньше синхронизации с SmartFarm и остаются при отсутствии интернета | задержка данных меньше суток; защита от потери при проблемах облака | время изменения файла (`mtime_utc` описи) против `create_date`/момента появления в кабинете на **тех же вылетах** |
| H2 | На пульте лежит телеметрия, эквивалентная V4, **для каждого** вылета, а не только для кандидатов | полнота покрытия телеметрией: числитель/знаменатель по контрольной ведомости | `inventory` → число `v4_like` против числа вылетов в ведомости; `compare-v4` с облачным V4 тех же вылетов (`drone_collector.main --sources --ids-file`) |
| H3 | Файлы пульта несут то, чего нет в облаке: ID пульта, прошивки борта и пульта, план задания с версией контура на момент вылета, время у точек маршрута, события насоса/расходомера, ID батареи, учётная запись | закрывает `НЕДОСТУПНО` из §3.2 | перепись protobuf / ключи JSON / таблицы SQLite из описи → ручной разбор на синтетике → контролируемый тест (ТЗ §6.3) |
| H4 | Байты V4 на пульте совпадают с облачными (SHA-256) | второе независимое наблюдение тех же байтов — подлинность **копии** | `compare-v4 … identical_bytes`; совпадение не доказывает подлинность DJI, момент полёта и оператора (ТЗ §0.6) |
| H5 | Обычное приложение (без обхода защиты) может читать эти файлы через системный выбор папки | автоматический сбор возможен | только отдельной проверкой 3.3 плана, после решения владельца |

Риски, известные до устройства (все — к проверке, не к выводу):

- журналы пульта могут быть зашифрованы: для Mavic это утверждают
  сторонние инструкции по DJI Assistant 2 (DroneNerds); для T40 не
  проверено;
- Android 11+ ограничивает `Android/data` даже при широком разрешении
  (ТЗ §3.7); формат и путь хранения меняются между версиями приложений
  (сторонние инструкции по DJI Fly называют `Android/data/dji.go.v5/files/
  FlightRecord` и старые `DJI/<app>/FlightRecord` — для DJI Agras путь
  **неизвестен**);
- установка APK на DJI RC Plus допускается по ответу представителя DJI на
  форуме (2023), при этом есть сообщение об ошибке активации стороннего
  приложения; для T40 и конкретной прошивки — не проверено;
- экспорт через DJI Assistant 2 for MG описан в руководстве T40/T20P
  (подключение по USB-C, выбор журналов); формат экспорта и наличие нужных
  полей не описаны;
- экспорт может содержать токены учётной записи — описи инструмент это
  поймает, но правила хранения такого файла — решение владельца;
- копия активной SQLite без WAL — неконсистентна (`SQLITE_WAL_OR_JOURNAL_PRESENT`
  в описи) — ТЗ §9.2.

## 10. Оценка пользы и рисков до устройства

- **Польза возможна там, где облако уже слабо**: V4 только для кандидатов,
  задержка до утра следующего дня, 12-месячное окно, отсутствие ID пульта и
  прошивок, отсутствие событий насоса. Измерить её можно только на
  совпадающей выборке (ТЗ §6.4) — для этого инструмент даёт `inventory` и
  `compare-v4`, а существующий сборщик — адресный захват облачных V4.
- **Польза нулевая**, если пульт отдаёт только то же V4 теми же байтами и
  не раньше, либо если экспорт только ручной и зашифрованный — тогда
  `SIMPLIFY/STOP`, и приоритет — закрыть конкретный пробел облачного
  сборщика (ТЗ §2.3 п. 3).
- **Риски до 0Б**: нулевые для production — ничего не развёрнуто и не
  подключено. Риски этапа 0Б перечислены в §5 и в плане; главный —
  принять искусственную или частичную передачу за доказательство.

## 11. Границы следующего этапа

Этап 0Б делает **только** обследование по плану и приносит матрицу,
доказательства и вывод. Не делается: приёмник и таблицы для `RC`,
миграции, изменение сборщика и его расписания, изменение площади,
решений, отчётов и финансов, сетевые настройки, прошивки, установка
чего-либо на пульт без отдельного решения владельца (проверка 3.3 плана).
Этап 1 и далее — только после рассмотрения результатов 0Б владельцем и
куратором (ТЗ §0.7, §16).

Минимальные регрессии будущего инкремента (ТЗ §0.7, последний абзац)
записаны как требования в плане §7 и в этом отчёте §4 — реализовывать их
сейчас нечего.

## 13. Вопросы владельцу и куратору

   --ids-file`); если да — согласовать день, чтобы не пересечься с
   ежедневным циклом и площадкой.

   и аккаунт DJI (руководство требует аккаунт для обновлений; для экспорта
