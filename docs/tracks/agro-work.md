# Трек: agro-work — изучение, импорт заявок, сверка с GPS

Заведён 2026-09-28 решением владельца вести agro-work отдельной сессией. До
этого вопрос жил внутри трека GPS как этап 3 дорожной карты («сверка нарядов»,
схема C + B, `docs/GPS_PLAN_FAKT_VISION_ROADMAP.md` §5 и §6).

## 1. Цель и границы

Сверить заявки agro-work.uz с фактической работой техники по GPS **в обе
стороны**, с раскрытием до машины и суток:

- есть заявка → была ли работа (да / нет);
- работа по GPS была → была ли заявка (да / нет, сколько).

Это ровно то, чего владелец не получает от самого agro-work (раздел 2.3).

**Не входит:**

- **Любая запись в agro-work.** Только чтение: живые заявки кластера не
  создавать, не сохранять, не закрывать, не экспортировать чужое.
- **Расчёт факта работы.** Он в треке GPS (`gps_daily_aggregates`,
  `gps_work_polygons`, правила по категориям в `gps/exclusion.py`); здесь
  только читается. Меняется метод — меняется в треке GPS.
- **Карта.** Общий картографический компонент строит трек GPS для всей
  программы (см. `docs/tracks/gps-plan-fakt.md`, раздел «Карта»); здесь им
  пользуются.

### 2.3 Недостатки agro-work — со слов владельца (документ 2026-09-28)

1. Панель «Предприятия × Категория транспорта — работавшая техника»
   (`agro-work.uz/admin/dashboard`) даёт только числа по категориям и
   организациям. **Нет расшифровки**, на какие именно машины составлены заявки.
2. Таблица «Работали сегодня (по данным GPS)» берёт данные из Wialon по
   API-токену и считает работой **любое включение зажигания или небольшое
   движение** — отсюда расхождение с числом заявок (на экране 28.09: по
   заявкам 161–165 машин, по GPS 227).
   Пробовали фильтр поездок Wialon (не менее 20 минут, не менее 3 км) —
   **выпала спецтехника**: экскаватор и погрузчик работают на месте.
   Сделали два фильтра (по пробегу и по моточасам) — программисты agro-work
   их не принимают, программа «работает только с одним». Единого фильтра не
   существует: техника работает по-разному.
3. **Нет сверки «заявка → было ли движение в Wialon».** Чтобы увидеть машины
   заявок, надо идти в «Заявки» и фильтровать по организации.
4. **Нет обратной сверки** «работала по GPS → была ли заявка»; в таблице GPS
   не показано, какая именно машина была активна.
5. Нужно: свод нарушений в обе стороны с раскрытием списка, табличным
   дашбордом.

### 2.4 Почему у нас это получится

Мы **не используем фильтр поездок Wialon**. Факт считается из сырых точек, и
метод свой у каждой категории техники — ровно ответ на пункт 2:

| Категория | Что считается работой | Основание |
|---|---|---|
| Тракторы (`mtz`, `qatnov`, `yukori`, `mini`), комбайны | участки и гектары по треку | метод GPS-2 |
| Спецтехника (`special`) | след и время, **без гектаров** | решение владельца 2026-09-28 |
| Грузовые (`yuk_transport`) | в площадь не входят; дальше — рейсы и посещение геозон | решение владельца 2026-09-28, этап 5 GPS |
| Легковые (помеченные «нет в системе») | не входят | GPS-14 |

«Техника работает по-разному» решается не одним фильтром, а методом по
категории.

### 2.5 Их GPS-модуль (скриншот 2026-09-28)

Всплывающее окно машины на `gps.agro-work.uz/dashboard`: период с быстрыми
кнопками (сегодня, вчера, неделя, месяц, ±1 день), режимы «Трек» и «Гектар»,
плитки «моточасы, топливо в движении, пробег, площадь», карта на Leaflet со
спутником, счётчик загруженных точек. Удачная форма — её стоит повторить у
себя (раздел 3, B4, и трек GPS).

**Находка по безопасности.** Окно открывается адресом вида
`gps.agro-work.uz/dashboard?plate=…#token=…`: **токен доступа лежит в адресной
строке** (72 знака — по формату токен Wialon). Любой, у кого есть этот адрес,
история браузера или скриншот, читает данные. Сам токен в репозиторий,
отчёты и чат не переносить никогда — только факт.

Оценки: S — один PR, M — 2–3 PR. Порядок важен: без B0 неизвестно, есть ли
даты, а без дат B3 бессмысленна.

**B0. Изучение, только чтение (S).** Через расширение Claude в Chrome, под
входом владельца. Карта экранов и внутреннего API (вкладка Network): заявки —
отдаётся ли «Добавлено в систему», как листается список, есть ли фильтр по

— раздел 5 этого файла, без токенов и cookie. **Выполнен 2026-09-28.**

**Где выполняется B0 — только на рабочем компьютере владельца** (уточнено
28.09). Облачная сессия идёт в контейнере и браузера владельца не видит, а
расширение соединяется только с Claude Code, запущенным на том же компьютере,
что и Chrome (`claude --chrome`). Поэтому B0 — локальная сессия Claude Code в
отдельной рабочей копии репозитория на этом компьютере. **Не на сервере и не
в `C:\transport-report`.** Итог уходит веткой и PR, как у облачных сессий.
B1–B4 — облачная сессия с репозиторием: браузер им не нужен, итоги B0 они
читают из этого файла.

**B1. Импорт заявок (M).** Идемпотентный по номеру заявки: повторная загрузка
не дублирует, изменившиеся строки обновляются с журналом. Источник — их API,
если B0 его подтвердит; иначе xlsx. Дата — «Добавлено в систему», если
отдаётся. Сопоставление техники по госномеру (`plate_norm.py`), несопоставленное
— в CSV владельцу, как у `tools/gps_link_mappings.py`. Своя таблица и
миграция по образцу `migrate_drones_reattach_001.py`.

**B2. Словарь «вид работы → единица → метод сверки» (S).** 40 строк; метод —
один из: гектары, время, рейсы, не сверяется. Размечает владелец, код не
угадывает.

**B3. Дашборд сверки в обе стороны (M).** Сутки × машина: заявка есть/нет ×
работа по GPS есть/нет, по методу из B2. Свод по организациям и категориям с
раскрытием до машины и суток — то, о чём владелец просит в разделе 2.3.
Читает факты трека GPS, не пересчитывает их. Карта — общий компонент трека
GPS.

**B4. Что взять у agro-work к себе.** Список из B0 на решение владельца:
форма окна машины (период, трек/гектар, сводка) и прочее.

## 4. Протокол изучения — обязателен

- Только чтение. Ни одной кнопки, меняющей данные: «Новая заявка»,
  сохранение, закрытие, удаление, импорт — не нажимать.
- Запросы к их API из страницы — только GET. POST, PUT, PATCH, DELETE не
  выполнять ни в каком виде, даже «проверочные».
- Разрешения расширения: сессия просит только переходы, чтение и нажатия
  для навигации (вкладки, фильтры, листание). Окно разрешения с нажатием,
  которое меняет данные, владелец отклоняет.
- Токены, cookie, заголовки авторизации, HAR-файлы целиком — **не сохранять в
  репозиторий и не печатать**. В отчёт идут адреса методов, форма запроса и
  ответа, имена полей; значения — только обезличенными.
- Персональные данные фермеров и водителей в репозиторий не класть.
- Всё, что меняет картину для трека GPS, записывать и в его файл.

### 5.1 Главный ответ: даты заявки

**«Добавлено в систему» API отдаёт.** Это `created_at` в списке и в карточке
заявки: ISO 8601 с микросекундами и поясом `+05:00` (у всех 4 785 заявок).
Список фильтруется по нему (`created_at_from`, `created_at_to`) и
сортируется (`ordering=created_at` или `-created_at`, второе по умолчанию).
Первая заявка — 15.06.2026 17:32; по месяцам: июнь 655, июль 1 638, август
1 267, сентябрь 1 225 (до 28.09).

**Отдельного поля с датой закрытия нет; она есть в истории статусов.**
`GET /applications/{id}/history/` и массив `history` в карточке
`GET /applications/{id}/`: у события есть `action` (`created`,
`status_changed`, `updated`), `old_status`, `new_status`, `changed_at`, кто
изменил, `changes` (какие поля и как, подписи по-узбекски), `note`. Дата
закрытия — `changed_at` события с `new_status = COMPLETED`, отмены —
`CANCELLED`.

Проверено на случайной выборке 190 заявок: 150 выполненных, 30 в процессе,
10 отменённых.

| Что | Результат |
|---|---|
| У выполненной есть переход в `COMPLETED` | 150 из 150 |
| У отменённой есть переход в `CANCELLED` | 10 из 10 |
| Первое событие (`created`) совпадает с `created_at` | 190 из 190, в пределах секунды |
| `updated_at` совпадает с моментом закрытия | 149 из 150 выполненных, 10 из 10 отменённых |
| Событий в истории одной заявки | не больше 4 |

`updated_at` годится как приближение даты закрытия, но любая правка после
закрытия его сдвигает (1 случай из 150).

`start_time` и `end_time` — это «Бошланиш» и «Тугаш» экспорта. Заполнены у
1 601 и 169 заявок из 4 785 (33 % и 3,5 %). По виду это плановое время
(круглые 09:00), рядом флаги напоминаний `start_reminder_sent` и
`end_reminder_sent`.

**Что эти даты значат — факты для решения владельца, а не правило:**

- Путь выполненной заявки (выборка 150): создана «в процессе» → выполнена —
  85; «ожидание» → выполнена — 41; **сразу «выполнено»** — 23; через все три
  статуса — 1. По всему списку «сразу выполнено» — 586 из 3 914 (15 %):
  `updated_at` отстоит от `created_at` меньше чем на минуту; по выборке тоже
  15 % (23 из 150). У таких заявок `created_at` — момент ввода задним числом,
  начало работы неизвестно.
- От создания до закрытия (выборка 150): медиана 1 484 мин (≈ 25 ч),
  90-й перцентиль 15 972 мин (≈ 11 сут), максимум ≈ 34 сут.
- Заявки заводят утром: 3 347 из 4 785 (70 %) созданы между 06:00 и 12:00.
- Их плитка «Работали сегодня» на «Мониторинге» считает день работы по
  `created_at`: 169 на 28.09 — ровно число разных машин с неотменёнными
  заявками, созданными 28.09 (с отменёнными — 170, статус транспорта
  «Банд» — 129).
- После создания в заявке правят объём (47 из 152 событий после создания в
  выборке), сумму (34), цену (15), комментарий (12), топливо и тип оплаты
  (по 11), вид работы (10), транспорт (7), фермера (6), плановые даты
  (по 3). Импорт обязан обновлять строки, а не только добавлять.

Какое окно брать для сверки — вопрос 4 раздела 6.

### 5.2 Карта API

Адрес — `https://api.agro-work.uz/api/v1`, по виду — Django REST Framework.
Список методов взят из JS-бандла самого приложения и сверен с вкладкой
Network.

**Авторизация** — пара JWT (access и refresh) в заголовке `Authorization`;
фронтенд держит её в localStorage, cookie нет; без заголовка — 401. Выдача и
обновление — `/auth/token/` и `/auth/token/refresh/` (из бандла, не
вызывались). Срок жизни токена не выяснялся.

**Листание:** `page`, `page_size`; ответ — `count`, `current_page`,
`total_pages`, `next`, `previous`, `results`. **`page_size` больше 100 молча
урезается до 100**: весь список заявок — 48 страниц. **Незнакомый параметр
молча игнорируется** (`zzz_unknown=1` → все 4 785), поэтому любой фильтр
проверяется счётчиком против такого контроля.

**Фильтры `GET /applications/`**, проверенные контролем (заведомо пустое
значение даёт 0, незнакомый параметр — все записи):

| Работают | Молча игнорируются |
|---|---|
| `created_at_from`, `created_at_to`, `status`, `transport`, `company`, `work_type`, `farm`, `payment_type` (неверное значение → 400), `search`, `application_number`, `start_time_from`, `end_time_from`; `ordering=created_at` и `-created_at` | `updated_at_from`; `ordering=updated_at` и `-updated_at` |

`start_time_to` и `end_time_to` есть в коде экрана выгрузки, не проверялись.
**Инкрементальной выгрузки по дате изменения нет:** изменения видны только
полным обходом списка и сравнением `updated_at` на своей стороне.

**Поля заявки** — в списке и в карточке одни и те же, в карточке ещё
`history`:

| Поле | Что это | В xlsx-экспорте 12.08 |
|---|---|---|
| `id` | UUID | нет |
| `application_number` | `APP-<орг>-2026-NNNNNNN` | номер заявки |
| `company`, `company_key`, `company_name` | предприятие: UUID, код из 5 латинских букв, название | организация |
| `transport`, `transport_info` | машина: `plate_number`, `brand_name`, `model`, `category_name`, `driver_name` | транспорт |
| `farm`, `farm_info` | фермер-контрагент: `name`, `owner_name`, `owner_phone` | фермер |
| `work_type`, `work_type_info` | вид работы: `name`, **`unit`**, `unit_display`, цены | вид работы, без единицы |
| `volume`, `unit_price_snapshot`, `total_amount` | объём, цена, сумма | есть |
| `payment_type` | `TRANSFER`, `CASH`, `CARD`, `TERMINAL`, `OTHER` | тип оплаты |
| `with_fuel` | с топливом или без | топливо |
| `status` | `PENDING`, `IN_PROGRESS`, `COMPLETED`, `CANCELLED` | статус |
| `start_time`, `end_time` | плановые начало и конец | начало, конец |
| `created_at`, `updated_at` | ввод и последняя правка | **нет** |
| `created_by`, `updated_by` и их `_name` | кто ввёл и правил | нет |
| `comment`, `is_active`, `start_reminder_sent`, `end_reminder_sent` | — | нет |

У полей-перечислений есть пара `…_display` с подписью по-узбекски.
**Персональные поля:** `farm_info.owner_name`, `farm_info.owner_phone`,
`transport_info.driver_name`, `created_by_name`, `updated_by_name`.

**Единица работы отдаётся** (`work_type_info.unit`). По заявкам: `HECTARE`
2 480, `MOTOR_HOUR` 896, `HOUR` 785, `TON` 259, `PIECE` 251, `TRIP` 73,
`KM` 34, `TON_KM` 7. Видов работ в заявках — 67; в экспорте 12.08 было 40.

**Остальные методы.**

- `/dashboard/recent/activity/` — последние смены статуса по всем заявкам;
  `limit` не больше 100, листания нет; 28.09 сотня событий покрывала
  10:48–15:23. Для полной загрузки не годится.
- Справочники: `/transports/`, `/transports/categories/`, `/companies/`,
  `/work-types/` (проверены); `/farms/`, `/regions/`, `/districts/`,
  `/regions/{id}/districts/` (из бандла).
- Сводки: `/dashboard/overview/`, `/dashboard/applications/by-{status,
  company, day, month, year, region, district, farm, payment, transport,
  work-type}/`, `/dashboard/transports/by-{status, brand, category, company,
  district, driver, region}/`, `/dashboard/top/{…}/` (`limit` не больше 100),
  `/dashboard/timeline/…`, `/dashboard/recent/{applications, upcoming}/`.
  Период в них задаётся `date_from` и `date_to` или `period=today`;
  `created_at_from/to` они игнорируют (проверено на `by-status`).
- Таблицы: `/tables/workload/?rows=company&cols=category` — панель
  «Предприятия × Категория» на «Мониторинге», в клетке **только числа**
  (всего, занята, не вышла), списка машин нет; `/tables/pivot/` (`entity`,
  `rows`, `cols`, `metric`, `period`), `/tables/catalog/`, `/tables/presets/`.
- **Меняют состояние — не вызывались:** `/applications/{id}/change-status/`,
  `/users/{id}/activate/`, `/users/{id}/reset-password/`,
  `/auth/change-password/`, `/auth/logout/`. Выгрузки
  `/{applications, transports, companies, farms, work-types}/export/{excel,
  pdf}/` не запускались.
- **Методов GPS и Wialon в этом API нет.**

### 5.5 Что у них сломано или слабо

1. Даты закрытия нет ни в полях заявки, ни в экспорте — только в истории.
2. Инкрементальной выгрузки нет. Неподдерживаемый фильтр и опечатка в его
   имени молча игнорируются — ошибка не видна.
3. **Плитки статусов на «Заявках» не зависят от выбранного периода.** Экран
   передаёт `created_at_from/to`, а метод сводки понимает `date_from/date_to`:
   за 28.09 список даёт 171 заявку, плитки — 4 786 за всё время. При периоде
   по умолчанию (с 01.06) этого не видно: туда попадают все заявки.
4. У сводок `date_from` = `date_to` даёт пустой ответ (конец интервала —
   начало суток), а у `period=today` границы суток в ответе помечены
   `+00:00`; считается ли день по UTC, не проверялось.
5. «Работали сегодня» считается по дате ввода заявки: введённая задним числом
   «работает» в день ввода.
6. Панель «Предприятия × Категория» и в API отдаёт только числа — расшифровки
   до машины нет (подтверждает п. 1 раздела 2.3).
7. 21 машина в реестре с нестандартным госномером (5.3).
8. GPS-модуль 28.09 данных не показывал (5.4).

### 5.6 Безопасность

- На «Мониторинге» и в GPS-модуле адрес сервера Wialon и поле ключа доступа
  (замаскированное) выведены прямо на экран: GPS у них считается в браузере
  пользователя, а не на сервере. Это согласуется с находкой 2.5.
- **Во фронтенд-бандле agro-work** (JS, который браузер скачивает с
  `agro-work.uz`, модуль `wialon`) есть одна строковая константа из 72
  шестнадцатеричных знаков — формат токена из 2.5. Значение не читалось и не
  выводилось. Файл был получен запросом из страницы без cookie и без
  заголовка авторизации. **Не проверено:** тот ли это токен, рабочий ли он,
  отдаётся ли файл из чистого браузера без входа. Если да — токен доступен
  любому, кто откроет сайт. К вопросу 2 раздела 6.

### 5.7 Выводы для B1–B4

- **B1: источник — их API, а не xlsx.** В API есть всё нужное, включая
  `created_at`, единицу работы и историю. Порядок: полный обход списка
  (48 страниц по 100) → запись по `id` → для новых и изменившихся заявок
  (другой `updated_at`) — `GET /applications/{id}/history/` → дата
  закрытия. Первичная загрузка истории — около 4 800 запросов, её надо
  растянуть во времени. Упирается в вопросы 5 и 6 раздела 6.
- **B2 упрощается:** единица берётся из API, 8 кодов. Владелец размечает
  только метод сверки по 67 видам работ. `MOTOR_HOUR` (моточасы) и `HOUR`
  (часы) — разные единицы; моточасы у нас уже приходят из Wialon
  (`wialon_import`).
- **B3:** сопоставление по госномеру через `plate_norm.py` покрывает 340 из
  361 машины реестра; 86 заявок на 5 машинах с нестандартными номерами уйдут
  в CSV несопоставленного. Окно сверки — вопрос 4.
- **B4, кандидаты на решение владельца:** окно машины за период (2.5, у GPS
  это A3); отметки «активна с заявкой / без заявки» над таблицей машин — у нас
  то же самое, но за любой период и с раскрытием до суток; экран выгрузки с
  фильтрами по всем полям заявки.

## 6. Открытые вопросы

1. Отдаёт ли API agro-work дату «Добавлено в систему» и дату закрытия заявки?
   **Закрыт 28.09 (B0):** `created_at` отдаётся; отдельного поля с датой
   закрытия нет, она берётся из истории статусов — раздел 5.1.
2. Чей токен открывает их GPS-модуль — выданный кластером от его учётной
   записи Wialon или их собственный? Если кластерный — решить, перевыпускать
   ли его (перевыпуск выключит их GPS-модуль до получения нового).
   **Закрыт 28.09:** токен владельца, он сам выдал его agro-work и
   перевыпустит, когда сочтёт нужным. Действий от сессий не требуется.
   Находка раздела 2.5 остаётся недостатком agro-work как факт; значение
   токена по-прежнему никуда не переносится.
   **Новый факт B0, 28.09:** константа формата токена во фронтенд-бандле
   agro-work — раздел 5.6; проверку сессия не проводила. Решение о
   перевыпуске по-прежнему за владельцем.
3. Как их «Гектар» считает площадь — метод неизвестен; сравнить с нашим на
   одних и тех же машино-сутках можно только после B0.
   **После B0 открыт:** 28.09 их GPS-модуль данных не загрузил, сравнивать
   было не с чем.
4. **Окно сверки для B3.** Варианты: сутки `created_at` — так считает сам
   agro-work; интервал от создания до закрытия — медиана ≈ 25 ч, у 10 %
   заявок больше 11 суток; плановые `start_time` и `end_time` — заполнены у
   33 % и 3,5 %. Отдельно: 15 % выполненных заявок заведены сразу
   выполненными, начало работы у них неизвестно. Решает владелец (5.1).
5. **Учётная запись для импортёра B1.** Нужна от agro-work, лучше только на
   чтение; есть ли у них такая роль, неизвестно. И их согласие на нагрузку:
   первичная загрузка истории — около 4 800 запросов. Логин и пароль — у
   владельца, в репозиторий и чат не попадают.
6. **Персональные поля:** хранить ли у нас владельца хозяйства и его
   телефон, водителя, операторов (5.2). Предложение сессии: пока не решено,
   B1 их не импортирует.
7. **21 машина с нестандартным госномером** (5 с заявками, 86 заявок):
   сопоставить вручную через CSV B1 или попросить agro-work исправить реестр
   (5.3).
