# Трек «Дроны»

## 1. Цель и границы трека

Холдинг эксплуатирует 15 опрыскивающих дронов DJI Agras T40; данные о вылетах живут в облаке DJI
SmartFarm, публичного API нет. Отдельное приложение, собиравшее их с марта по май 2026 года, умерло
вместе с переустановленным компьютером — дроны становятся модулем внутри Vehicle Soft. Задача
модуля: получать измеренные гектары автоматически и связывать их с заказчиком и суммой, потому что
сегодня счета выставляются по цифрам, названным по телефону.

**Не входит, и вот почему.** Касса, движения денег и P&L — только начисление и отметка оплаты:
в закрытом приложении денежный контур был построен и **ни разу не использован**, в `sqlite_sequence`
нет записей для `orders`, `clients`, `cash_accounts`, `cash_movements`, то есть ни одной строки туда
не вставлялось за 3,5 месяца работы и 10 385 собранных вылетов; в холдинге есть 1С. Нормы расхода
жидкости — химию поставляет заказчик, перерасход не является затратой холдинга. Аналитика по
пилотам — физически невозможна (см. раздел 2). Дроны не заводятся в `equipment` и не связываются с
`work_orders`.

## 2. Ключевые архитектурные факты

Прочитано в исходниках Vehicle Soft, в базе закрытого приложения (10 385 вылетов) и в живом
интерфейсе SmartFarm.

- **`serial_number` в полезной нагрузке DJI — идентификатор вылета, а не машины:** 10 385 различных
  на 10 385 строк, в экспорте 50 из 50. Вылет с машиной связывает только ник.
- **Машин 15, номера 1…15; ник устроен как «номер + место» и меняется.** Ников 19; интервалы разных
  ников одного номера не пересекаются ни разу. Идентичность — номер; карта алиасов обязана жить в
  БД, а не в коде.
- **Единицы:** `new_work_area` — м², /10000 → га; `spray_usage` — мл, /1000 → л; `sow_usage` —
  **граммы**, /1000 → кг (выведено точно: 1 525 350 против 1 525,3 кг в сводке); таймстемпы — unix
  UTC, показывать UTC+5.
- **`plot_name` пуст во всех 10 385 записях, `Field Name` в экспорте — во всех 50.** Привязки вылета
  к полю в DJI нет; только геометрия по `lat`/`lng`, которые заполнены везде.
- **`flyer_name` = `DzzDron` и `team_name` = `Бригада 1` во всех записях** — весь парк работает под
  одним аккаунтом DJI, поэтому выработку по пилотам считать не из чего. Поле хранить всё равно надо.
- **Ник не говорит, для кого работали:** 24 % гектаров отработаны вне Бухарской области (Навоийская —
  2 437 га), девять машин из пятнадцати летали более чем в одной; разрез «на кого работали»
  появляется только с заявками.
- **`work_orders.equipment_id` объявлен `nullable=False`** — переиспользовать наряды под заявки
  дронов нельзя.
- **`customers` содержит только `name` и `customer_type`**; внутренние записи уже ведутся по паттерну
  «<подразделение> ерлари» — готовый механизм для внутренних работ без новой сущности.
- **Образец приёмного endpoint'а — `_perform_fuel_sync()`** (`fuel_routes.py`, ~3416): токен в теле
  JSON, `hmac.compare_digest`, путь в `is_csrf_exempt()` (`app.py`, ~130), лог, дедуп по внешнему id,
  аудит от синтетического актора. Дронам нужен отдельный `DRONE_API_TOKEN`.
- **Сид `app_modules` в `app.py` срабатывает только на пустой таблице** — для существующих БД модуль
  `drones` добавляется миграцией. В меню (`base_next.html`) правом закрыт только пункт «Запчасти»;
  пункт дронов делать закрытым по `has_module_access('drones')`.
- **Вылет — один залив бака, а не смена:** до 708 с и до 2,38 га, в среднем 0,98 га, 3 % записей с
  нулевой площадью. «Вылетов» и «гектаров» — разные метрики. В сезон 150 вылетов в день, пик 476,
  поэтому серверная пагинация и фильтры обязательны с первого дня.
- **`excel_export.py` не проверен лично:** копия в project knowledge не соответствует серверу, любые
  утверждения о влиянии дронов на управленческий Excel недоказаны.

### Принятые решения — инварианты трека

Менять их можно, но только явным решением владельца и с записью причины.

| № | Решение | Почему именно так |
|---|---|---|
| Р1 | Модуль пишется с нуля, код закрытого приложения не портируется | Там сырой `sqlite3` против SQLAlchemy, своя авторизация против модульных прав, моноязычный русский против обязательного двуязычия, свои шаблоны против `vs-*`. Порт любого экрана — это его переписывание плюс занос чужих конвенций |
| Р2 | Из старого забираются три вещи: логика сборщика, предметные факты, отрицательные уроки | Сборщик — единственный дорогой артефакт: подпись запроса считается в WebAssembly, воспроизвести её вне браузера нельзя |
| Р3 | Дроны — отдельная таблица `drone_units`, не строки `equipment` | Нет госномера и типа техники; 150 вылетов в день против модели «одна запись в день на единицу» в `daily_records`; `work_orders.equipment_id` — NOT NULL; `Equipment.organization_id` — единственный обязательный FK |
| Р4 | Все 15 машин закреплены за `organization_id = 12` («Агрокластер»), ник в расчётах не участвует | Решение владельца 2026-07-28: все дроны принадлежат Агрокластеру, вся выручка идёт туда. **Следствия:** карта алиасов всё равно нужна, иначе `8 Garden` / `8 Garden U` / `8 GardenU` разъедутся на три строки; разрез «чьи гектары» до заявок отсутствует; новых строк в `organizations` не требуется |
| Р5 | Нормы расхода жидкости в скоуп не входят | Химию поставляет заказчик. Данные хранятся, отчётов нет |
| Р6 | Касса, дебиторка и P&L не строятся | Контур уже был построен и ни разу не использован (см. раздел 1). Причина механическая: связать деньги с фактом вручную при 150 вылетах в день не может никто. Сначала дешёвая привязка, деньги — только если она заработает |
| Р7 | Сборщик — служба на сервере Vehicle Soft под доменной учётной записью | Прежняя машина не существует; интернет до `www.djiag.com` с сервера проверен. POST идёт на production, staging кормится скриптом-реплеем — приём, уже применённый для карт Топаза |
| Р8 | История начинается с самой ранней даты, которую отдаёт SmartFarm (на 2026-07-29 это 30.06.2025). **Изменено решением владельца 2026-07-29**; прежняя редакция — «с 01.01.2026» | Причина изменения: окно истории, судя по всему, скользит примерно на 13 месяцах, и данные 2025 года могут стать навсегда недоступными, а цена их сбора сейчас — одно лишнее окно бэкфилла. Следствие: исторический бэкфилл идёт **календарно-годовыми окнами** (`2025-06-30…2025-12-31`, затем `2026-01-01…сегодня`), потому что календарь SmartFarm сбрасывает диапазон через границу года. Оценка объёма ≈ 29 185 вылетов ≈ 584 страницы по 50 |
| Р9 | ETL из старой `app.db` отменён | Старая база покрывает 31.01–19.05.2026, а сбор идёт с 01.01.2026 — тот же период приедет из облака. База остаётся образцом сырого `raw_json` и материалом для сверки |
| Р10 | Эталон приёмки сборщика — плитка SmartFarm за конкретный период, а не реестр устройств | Реестр даёт пожизненные итоги и включает, по-видимому, неагрономические полёты (раздел 4) |
| Р11 | Заявку заводит админ, поэтому заявка нужна только там, где приходят деньги извне | Внутренние работы холдинга оформляются через `customers` типа `internal` и заявкой не сопровождаются. Иначе заявки повторят судьбу старых заказов |
| Р12 | Порядок: заявки (DRONE-005) перед полями (DRONE-006) | Контур сам по себе денег не считает; он ускоряет заполнение заявки, но подставлять его пока некуда |

Решение владельца 2026-07-29, фиксируется здесь же: **ни одна машина не
исключена из отчётности** — флаг исключения (`is_excluded` с датой) уезжает в
прод пустым. `9 Garden` тестовой больше не считается (раздел 6).

**2026-07-30 — `DRONE-SUMMARY-ALLTIME-001` и `DRONE-SUMMARY-XLSX-DIVERGE-001`.** В строке фильтров
сводки после кнопки «Показать» стоит ссылка «За всё время» / «Барча вақт» (`vs-btn-ghost`, без
нового CSS и без JavaScript): она отправляет `date_from=` и `date_to=` пустыми, а подстановка
текущего месяца срабатывает только когда параметров даты нет вовсе, — то есть сводка снова умеет
показывать всё время и перестаёт расходиться со списком вылетов. Вместе с этим `_drone_link_args`
больше не выбрасывает **явно очищенную** дату, а печатает её пустым значением: раньше ссылка на
`summary.xlsx` теряла ключи даты, экспорт не видел их и подставлял свой текущий месяц, отдавая
книгу за месяц под экраном за всё время. Правило: ссылка, питающая экспорт, кодирует разрешённое
состояние фильтров, а экспорт своё умолчание не выводит. Пара «список — `flights.xlsx`» не тронута:
у неё подстановки нет ни с одной стороны. Схемы, миграций и данных правка не касается.

**Дополнение к записи выше.** Тем же PR, четвёртым коммитом (`a6fe1e1`), закрыт
`DRONE-SUMMARY-DRILLDOWN-500-001` — дефект, живший в `main` независимо: переходы
сводки в список передавали `unit_id` (и `region`) дважды — именованным
аргументом и внутри `link_args`, — поэтому при применённом фильтре Jinja
поднимала `TypeError` на рендере и страница отдавала 500. Правка — слияние
словаря, `**dict(link_args, unit_id=r.unit_id)`. На приёмке DRONE-004 не
поймано потому, что переход проверяли **без** применённого фильтра, а при
фильтре по умолчанию таблица машин пуста и ссылка не рисуется вовсе: контроль
«страница открылась» этот класс дефектов не различает.

**2026-07-31 — `DRONE-003`: сборщик прогнан на живом кабинете.** Мерж `00f859a`
(PR #38), 22 коммита, 24 новых файла под `drone_collector/`, 4379 вставок и
**ни одной удалённой строки**. Приложение не затронуто: пакет не импортирует ни
`app`, ни `models`, своих зависимостей приложению не добавляет, миграций не
несёт. `docs/RELEASE_GATE.md` не изменён — прогон выполнен **до** мержа, поэтому
строке гейта нечего было записывать.

Ниже — то, что установлено на живых ответах DJI, а не выведено рассуждением.

- **Успех — `code: 0`, а не 200.** Конверт успешного ответа:
  `{"status": 200, "code": 0, "message": "OK"}`. У отказов `status` равен
  `code`: `101/101` — подписи нет или она недействительна, `408/408` —
  недействительное время запроса. **HTTP-статус равен 200 в обоих случаях и о
  результате не говорит ничего.** Подтверждено на двенадцати ответах из HAR и
  на живом прогоне.
- **Подпись `Signature` покрывает строку запроса целиком.** Проверено прямым
  вмешательством в исходящий запрос самого приложения: снятие заголовка даёт
  `101`, подмена `page_size` в уже подписанном URL даёт `101`. Отсюда: ни
  размер страницы, ни период переписать в URL нельзя — обе величины задаются
  только через интерфейс.
- **Размер страницы: `10 / 20 / 30 / 50`, максимум 50.** Список прочитан с
  живого контрола. **Варианта 100 не существует.**
- **Период задаётся печатью в `.ant-picker-range .ant-picker-input input`.**
  Поля `readonly`, клик перед вводом это снимает. Пока печатается вторая дата,
  сайт успевает сходить за данными с **полуприменённым** периодом — такие
  страницы обязаны отбрасываться, это не теоретический случай.
- **Календарь через границу года не сбрасывается, если резать окно самому.**
  Прогон `2025-12-01 .. 2026-01-31` разрезан на два подокна, каждое
  подтвердилось независимо, пересечение идентификаторов между ними — ноль.
- **Payload списка содержит все двадцать полей, которые читает
  `api_flight_sync`**, включая `lat`, `lng` и `work_time_seconds`.
  Дозапрашивать карточки отдельных вылетов не нужно ни для чего.
- **`geometry_md5` в списке отсутствует** — он есть только в карточке
  отдельного вылета. Связка «вылет → контур поля» через этот ключ потребовала
  бы отдельного запроса на каждый вылет. Для `DRONE-006` это меняет расклад.
- **Плитка кабинета подписывает гектары как `mu`** — подтверждено сверкой за
  1–7 июля: сборщик 1318.58 га, плитка 1318.62 «mu». Настоящие му за тот же
  период — 19 778.7, в интерфейсе они не показываются нигде.

**Сверка приёмки.** Период 1–7 июля 2026: сборщик собрал 1217 вылетов на 25
страницах; плитка кабинета за тот же период — 1217 вылетов, 31 154 л, 0 кг. Все
идентификаторы уникальны, ни один вылет не вышел за границы окна, отработали 8
машин из 15.

**Ошибка метода, допущенная здесь же.** Признак успеха был определён пробой,
чья регулярка искала первое из полей `code` или `status`. У отказов они равны,
поэтому проба показывала правду; у успеха первым шёл `status: 200`, и `code: 0`
до вывода не доходил. Вывод «успех = 200» попал в промпт как установленный
факт и стоил первого прогона. Проверка, в которой два разных поля неразличимы,
проверкой не является — этот же урок уже записан в треке про прибор, врущий
одинаково в обе стороны.

## 4. Открытые хвосты

- Размер страницы — **закрыто 2026-07-31**: сайт предлагает `10 / 20 / 30 / 50`,
  варианта 100 не существует, максимум 50. Сборщик открывает список, логирует
  все опции, выбирает наибольшую и читает `page_size` обратно из URL запроса.
- Видны ли в карточке поля Field Management контур и координаты, есть ли у поля идентификатор —
  **не проверено**. Открыть `/mission`, кликнуть по полю. Нужно для DRONE-006.
- Навоийская область, 2 437 га за четыре месяца — работа на сторону или своё хозяйство? Вопрос к
  владельцу, влияет на трактовку отчётов.
- Расхождение 3 059 вылетов между реестром устройств (32 244) и суммой периодов (29 185) **не
  объяснено**; версия — реестр считает и неагрономические полёты. На решения не влияет.
- Забирать ли 2025 год (8 491 вылет, 8 710 га с 30.06.2025) — **решено 2026-07-29**: забирать,
  история ведётся с самой ранней доступной даты (см. изменённый инвариант Р8). Исходники старого
  сборщика прочитаны, но **не запускались**.
- Каждый чанк реплея создаёт свою строку `drone_sync_logs` — 21 строка на прогон, 63 за три.
  На историческом сборе (~29 185 вылетов) это десятки почти одинаковых записей, и вопрос
  «прошёл ли сбор 2025 года» превращается в ручное суммирование. Решать при DRONE-003: крупнее
  чанки либо `run_id`, группирующий чанки в один логический прогон. Заведено как
  `DRONE-SYNC-RUN-GROUPING-001`, на приёмку DRONE-002 не влияет. **Закрыто
  2026-07-31:** выбраны крупные пачки по 1000 — максимум, который принимает
  приёмник. Идентификатор прогона не вводился: он потребовал бы правки
  `drones.py` и миграции ради удобства чтения логов.

- **Боевая отправка не выполнялась ни разу.** Сборщик проверен только в режиме
  `--dry-run`, где он пишет JSON-файл вместо POST. Тракт до `api_flight_sync`
  на живых данных не проверен.
- **`DRONE_API_TOKEN` на production не задан.** Проверено с трёх сторон:
  параметра `AppEnvironment` у службы нет вовсе, в `AppEnvironmentExtra` лежат
  только `FLASK_ENV`, `PORT`, `HOST`, а `FUEL_API_TOKEN` и `SECRET_KEY` заданы
  на машинном уровне. Токена дронов нет ни там, ни там, поэтому
  `api_flight_sync` сейчас отвергает всё с 401 — штатный deny-by-default.
  Задавать его следует на машинном уровне, рядом с `FUEL_API_TOKEN`, а не через

## 6. Грабли этого трека

- **Площадь показана тремя способами:** строка списка — гектары; плитка сводки — гектары,
  подписанные `mu`; экспорт (`Sprayed area`) — настоящие mu, ×15, без подписи. Проверено построчно и
  дважды независимо по литрам на гектар. Числа с экрана и из экспорта не брать, нормализовать из
  сырого `new_work_area`. В Settings единица площади не настраивается.
- **Экспорт выгружает только текущую страницу** (50 строк) и не содержит ни идентификатора вылета,
  ни координат — как источник данных непригоден.
- **Период не уезжает в URL** (`/records/list` без параметров), календарь работает по годам:
  диапазон через границу года сбрасывается. Исторический сбор — годовыми окнами. Самая ранняя
  доступная дата — 30.06.2025.
- **`Other Regions` — переключатель страны.** Случайный клик уводит сессию в пустой регион, и сбор
  молча вернёт ноль. Проверять регион после входа.
- **Служба под `LocalSystem` не видит Chromium** — он ставится в профиль пользователя. Самая частая
  ошибка в логах; всего 95,8 % успешных прогонов из 520, остальные — таймауты XHR и `goto`, поэтому
  повторный прогон за тот же период должен быть нормой.
- **`records_written` всегда равнялся `records_seen`** — старый сборщик переписывал окно целиком; по
  логу нельзя было понять, приехали ли данные.
- **Жёстко зашитый словарь соответствий стоил 20 % данных:** старый `divisions.py` знал 16 ников из
  19, и 2 036 вылетов (2 082 га) уходили в отчёте в «—».
- **`9 Garden` больше не тестовый** (480 вылетов, 493 га): признак исключения — поле машины с датой.

**Ошибки метода, уже допущенные в этом треке.** Стоили времени, повторять не надо.

- **Числа из промта-передачи приняты на веру.** В прежнем промте стояло «~2800 вылетов», в базе их
  10 385. Любую цифру, доставшуюся по наследству, проверять на данных, прежде чем на неё опираться.
- **Названия организаций взяты из документа, а не из БД.** Маппинг по названиям привязал бы модуль к
  дублям `id` 20–24 — фиктивным организациям со `sort_order = 999` и нулём техники. Поймано
  read-only preflight-скриптом; соответствия строить только по `id`, прочитанным из живой базы.
- **Дважды сделан слишком широкий вывод из одного наблюдения.** Сначала «историю из SmartFarm заново
  не собрать» — на деле не умел этого старый код, а сам SmartFarm период принимает. Затем «подпись
  mu врёт» — оказалось, что в экспорте mu настоящие. Обобщать только после двух независимых проверок.
- **Оценка `excel_export.py` по устаревшей копии** из project knowledge. Копии там расходятся с
  сервером; аргумент снят как недоказанный.
