# Трек: Запчасти

## 1. Цель и границы трека

Модуль ведёт правду о движении запчастей: заявка механика → утверждение → резерв
→ выдача → списание, плюс складской остаток и справочники. Отвечает на вопрос
«что реально стоит на технике и сколько это стоило», которого нет ни в 1С, ни у
конкурента.

**Не входит:** закупка и расчёты с поставщиками, стоимостной учёт склада
(денежного поля у остатка нет и не планируется), нормирование ТО, топливо,
наряды. Связь «деталь ↔ техника» есть (`SparePartCompatibility`), но наполняется
из фактических выдач, а не ведётся вручную.

## 2. Ключевые архитектурные факты

Всё прочитано в `spare_parts.py`, `models.py` и шаблонах, не в project knowledge.

- **Остаток ведётся только по варианту поставки (`spare_part_skus`).** Позиция
  каталога (`spare_parts`) без варианта отслеживаемого остатка не имеет.
- Количество пишется только через `_apply_inventory_movement`: в той же
  транзакции создаётся строка движения с `balance_after`, гард
  `UPDATE ... WHERE quantity + delta >= 0 ... RETURNING` — отрицательный остаток
  невозможен. Единица строки остатка берётся из позиции каталога **в момент
  создания строки** и больше не меняется.
- **Движения append-only**, роута правки движения и его примечания нет. Вручную
  вводятся только `receipt` и `adjustment`; `issue` и `write_off` приходят из
  выдачи заявки.
- `SparePartRequestItem.sku_id` nullable; NULL означает «только позиция каталога,
  без привязки к складу». Механики варианты не выбирают.
- Резерв создаётся при утверждении, строка на позицию заявки с ненулевым
  `sku_id`. `_check_repeat_orders` и отчёты по расходу ключуются по
  `spare_part_id`, не по варианту.
- Индекс `uq_spare_part_skus_normalized` действует **внутри одной позиции**:
  один и тот же номер каталога на разных позициях разрешён намеренно.
- Единица — строгий справочник `spare_part_units.code`; в старых записях
  встречается свободный текст (`шт`) и нормализуется при правке.
- У остатка и движения **нет денежного поля**. `last_price` / `avg_price`
  обновляются односторонне подтверждением цены — руками не писать.
- Один склад на организацию, UNIQUE в БД; роута переименования склада нет.
- `app = create_app()` (`app.py:2915`) вызывает `db.create_all()`
  (`app.py:2883`) на импорте: любой скрипт с `from app import app` — писатель.
  Диагностика пишется на чистом `sqlite3`.
- Права: каталог и варианты — `spare_parts_catalog_manage`; склад и движения —
  `spare_parts_inventory_manage`.

## 4. Открытые хвосты

- **Три проверки инкремента 8 не прогнаны. Строка трека висит в «Открытых
  пунктах» `RELEASE_GATE.md`** (заведена коммитом `596304b`), снять её может
  только этот трек. Пункты: исключение отменённых заявок из подсказки о повторном
  заказе (`1a9369a`) — создать заявку на ту же технику с той же позицией, что в
  отменённой, и убедиться, что её в предупреждении нет; карточка отменённой
  заявки в узбекском — бейдж стиппера и «Сўров бекор қилинган — амал йўқ.»;
  учётка с правом выдачи без права утверждения не должна видеть карточку отмены.
  Первый пункт требует записи, браузерный агент его не сделает. 15–30 минут.
- **`openpyxl` и имена, начинающиеся с `=`.** Такая позиция на staging есть,
  `openpyxl` превращает такую строку в формулу. Затрагивает ли это выгрузки
  инкремента 7 — **не проверено лично**: открыть выгрузку с такой позицией.
- **Мусор агентов на staging** (`DEMO-CLEANUP-002`): 529 демо-заявок, две единицы
  техники, три позиции `CODEX-SOL-*`, две тестовые `ТЕСТ UNIFY`. Мешает измерять
  объёмы.

## 5. Следующие шаги трека

Сначала три проверки инкремента 8: дёшево, и они снимают строку из гейта,
который блокирует прод-деплой всему проекту. Дальше по возрастанию цены: `SP-PICKER-SEARCH-001` (фильтр по вводу в подборах
позиции — **бэкенд уже готов**, `/api/catalog-search` с `difflib` и дебаунсом,
нужна обвязка трёх подборов), `SP-STOCK-XLSX-001` (выгрузка остатков в Excel),
`SP-SKU-XREF-DUP-001` (предупреждение при повторе номера каталога на другой
позиции), `SP-TERM-VARIANT-001` (полное переименование «Артикул» → «Вариант
поставки», **только одним проходом по всем поверхностям** — частичное уже
пробовали и откатили внутри PR #30).

**Зависимость, критичная для сводного плана:** развитие модуля упирается не в код,
а в данные. Пилот покрыл одну организацию из 22; пока остальные склады пусты,
отчёты по расходу, минимальные остатки и очередь закупки показывают пустоту и на
реальных объёмах не проверяются. `DEPLOY-DRIFT-001` (P1) формально
общепроектный, но обнаружен здесь: прод неделю работал без трёх миграций.

## 6. Грабли этого трека

- **Единица фиксируется при первом приходе.** Создавать позицию с правильной
  единицей до ввода остатка; правка позиции задним числом строку не чинит.
- **В каталоге два разных поля «Название (узб.)»** — в верхней форме и инлайново
  в строке списка, они уходят в **разные роуты**. Инструкции проверок должны
  называть конкретную карточку и кнопку: на этом уже сорвалась одна проверка.
- **Атрибут `hidden` скрывает контейнер, но не отключает поля внутри** — они всё
  равно уходят в POST. Защищать надо и в роуте.
- **Слить активные позиции каталога интерфейс не умеет** (роут слияния только
  для `pending_review`), поэтому неточное название придётся носить годами:
  заводить по известному минимуму, а не по догадке.
- `part_number` позиции приходит из заявки оператора для кандидатов из очереди.
  Форма его больше не шлёт, поэтому `catalog_save` отличает «поля нет» от «поле
  пустое» — не сломать при правках.
- **Не сливать справочники «Каталог» и «Артикул»** (разбор с шестью причинами в
  `TASKS.md`) и **не вводить межпозиционную уникальность номера каталога** — на
  ней держатся пилотные данные, нужно предупреждение, а не ограничение.

## 7. Данные, которые надо собирать заранее

Это узкое место трека — недели календарного времени, кодом не ускоряется.

- **Остатки складов остальных организаций.** Пилот покрыл одну из 22. По каждой
  нужна выгрузка со счёта 1040 (наименование, код номенклатуры, единица,
  количество, сумма, МОЛ) и **физически подтверждённое** количество, а не цифра
  из 1С. Для Пахтасаноаттранса это заняло около недели переписки.
- **Сопоставление номенклатуры 1С с каталогом.** В 1С 217 716 позиций, на счёте
  1040 — 99 011. Пятнадцать сопоставлялись вручную; массовое сопоставление
  отдельная задача, для неё нужна выгрузка кодов и правила соответствия.
- **Узбекские названия каталога.** Заполнены у 14 позиций из 250, остальные в
  узбекском интерфейсе показывают русский текст. Нужен носитель языка.
- **Ревизия единиц измерения.** У всех унаследованных позиций стоит `dona`,
  включая масла, шланги и тросы. Нужен человек, знающий номенклатуру.
- **Минимальные остатки по складам.** Механизм с инкремента 4, значения никто не
  задавал — решение снабженцев, не разработки.
- **Бренды и каталожные номера производителей.** В 1С их нет — собираются у
  поставщиков и с самих деталей.
