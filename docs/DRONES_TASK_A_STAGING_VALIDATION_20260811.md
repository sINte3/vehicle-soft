## 4. Сухой прогон бэкфилла подразделений (#65)

Сначала на staging, потом — отдельным шагом релиза — на production. **Режим по
умолчанию сухой; `--apply` пишет.**

```powershell
cd C:\transport-report-staging
& "C:\Program Files\Python314\python.exe" backfill_drone_works_subdivision.py --db instance\transport.db
```

Ожидание по §5 промпта, измеренное на production 2026-08-09: **105 сирот, 88
решаются, 17 остаются**, и нерешённая книга ровно одна —
`Сервис Дрон Маълумот (2).xlsx` (операторы из двух подразделений).

**Если числа не совпали — остановиться и сообщить, а не подгонять.** Числа
мерялись на production; на staging база другая, поэтому расхождение здесь
ожидаемо и само по себе дефектом не является — сверять надо на production.

Применение и проверка идемпотентности:

```powershell
& "C:\Program Files\Python314\python.exe" backfill_drone_works_subdivision.py --db instance\transport.db --apply
& "C:\Program Files\Python314\python.exe" backfill_drone_works_subdivision.py --db instance\transport.db
```

Второй прогон обязан сказать «0 rows to change».

**Откат данных** (изменение только одно — запись в пустой `subdivision_name`):
отчёт рядом с базой перечисляет id каждой изменённой работы, и откат
механический —
`UPDATE drone_works SET subdivision_name = NULL WHERE id IN (<ids из отчёта>);`

Только чтение, ничего не меняет; на staging полётная сторона живёт реплеем,
поэтому **числа читать на production**, а на staging проверять лишь то, что
скрипт отрабатывает и печатает отчёт.

```powershell
cd C:\transport-report-staging
& "C:\Program Files\Python314\python.exe" tools\drone_reattach_evidence.py --db instance\transport.db --report C:\qa\reattach_evidence_staging.txt
```

Что смотреть в отчёте: сколько написаний попало в `HOMOGLYPH` (выводимо
сводом раскладок), сколько в `AMBIGUOUS`, сколько в `UNKNOWN`, и какие
написания собрались в семьи. **Ни одной записи в базу скрипт не делает** — это
и есть причина, по которой его можно запускать на production без окна.

## 6. Задание браузерному агенту (Codex, профиль `qa-staging`)

Запуск: `codex -p qa-staging -C C:\qa`. Ниже — то, что проверяется глазами и
кликами; числа сверяются с этим файлом, а не с памятью агента.

### 6.1 `/fuel/` — регресс верстки (#64), **первый по важности**

Дефект виден на production сегодня, поэтому проверка — до и после.

1. Плитки показателей стоят **в ряд**, а не столбцом во всю ширину.
2. Ни одно значение не перекрыто белым прямоугольником: «Выдано сегодня»,
   «Складов ниже порога», «Открытые предупреждения» читаются целиком.
3. У плашки «**ДТ.**» есть левая полоса и фон.
4. У «Последней синхронизации» перед временем есть цветная точка.
5. Пилюля «ДТ» на `/fuel/report`, `/fuel/receipts`, `/fuel/manual-expenses` —
   скруглённая плашка, а не голый текст.
6. Ширина 390 px: страница не едет вбок, вбок движется только таблица.

### 6.2 `/drones/reports/closing` — подписи корзин (#65)

1. У корзин «Подразделение не определено» и «Машина не определена» есть
   подпись, что это работы без опознанного подразделения, **а не чья-то
   несданная книга**.
2. После бэкфилла (раздел 4) итог месяца **не сдвинулся**: сумма по
   подразделениям равна тому же месяцу на `/drones/reports/reconcile`.
   Переезд работы между корзинами не имеет права двигать итог.
3. Оба языка; узбекский — только кириллица.

### 6.3 `/drones/reports/health` — экран контроля данных (#66)

1. Открывается, пять секций на месте, пустая секция показана пустой с
   подписью «аномалий нет», а не спрятана.
2. Каждая строка ведёт в первоисточник с применённым фильтром.
3. Плитка экрана есть в хабе отчётов.
4. Оба языка; узбекский — только кириллица.

### 6.4 `/drones/reports/flight-calendar` — пятое состояние клетки (#67)

1. Строка «машина не определена» присутствует, её пустые дни **пустые** —
   без серой заливки и без пунктирной рамки, то есть отличимы и от «простой»,
   и от «не записано».
2. Остальные четыре состояния не изменились.

### 6.5 Права

Под учётной записью без права `drones` — 403 на `/drones/reports/health` и
`/drones/reports/closing`, пункта меню нет. Учётки без прав администратора
по-прежнему нет — если так, записать это как непроверенное, а не как

## 7. Порядок релиза на production

Только после того, как разделы 4–6 закрыты и строки партии сняты из
`docs/RELEASE_GATE.md`.

```powershell
Stop-Service TransportReport
Stop-Service TransportBot
Stop-Service TransportBot003
Get-Service TransportReport, TransportBot, TransportBot003
```

Бэкап **до** любого изменения:

```powershell
cd C:\transport-report
& "C:\Program Files\Python314\python.exe" backup_transport_db.py --dest-dir C:\transport-report-backups\before_task_a --suffix before_task_a
& "C:\Program Files\Python314\python.exe" tools\check_db_lock.py --db instance\transport.db
```

`check_db_lock.py` после бэкапа печатает `CLEAN`, а не `STALE`: online backup
API закрывает базу штатно и убирает WAL. Это записанный фон
(`TOOL-DBLOCK-PERSIST-WAL-001`), а не находка.

Выкат и запуск:

```powershell
cd C:\transport-report
git fetch origin
git merge --ff-only origin/main
git rev-parse --short HEAD
& "C:\Program Files\Python314\python.exe" tools\check_migration_drift.py --db instance\transport.db
Start-Service TransportReport
Start-Service TransportBot
Start-Service TransportBot003
Get-Service TransportReport, TransportBot, TransportBot003
```

`check_migration_drift.py` требует `--db` — вызов без аргумента падает; в
прошлом релизе шаг из-за этого пропустили. Вердикт `DRIFT DETECTED` на чистом
дереве — записанный фон (`TOOL-DRIFT-VERDICT-001`); смотреть на строку
`file-but-not-registered: 0`.

Реестр миграций обязан остаться **38** — в партии миграций нет.

Смоук после старта: `/fuel/` (плитки в ряд), `/drones/reports/closing`,
`/drones/reports/health`, `/drones/summary`.

Затем — прогон бэкфилла (раздел 4) на production, сухой прогон против чисел
§5, и только после совпадения `--apply`.

Затем — улики по вылетам без машины (раздел 5) на production: это первый
живой прогон инструмента, и его вывод нужен для решения по сорока написаниям.

Записать релиз в `docs/DEPLOYED.md` — это делает та сессия, которой поручен
релиз; трековые сессии этот файл не трогают.

## 8. Что заведомо останется непроверенным

Названо прямо, чтобы не выдать за проверенное:

- **Сколько написаний закроется сводом раскладок — неизвестно**; возможно,
  ноль. Классы инструмента проверены на синтетике, распределение живых данных
  не видел никто.
- Замер экрана закрытия (ведомости 1.9 мс, вылеты 38.3, экран 42.0, сверка
  30.7) сделан на синтетике 31 000 вылетов в SQLite внутри контейнера. На
  сервере не повторялся.
- Экраны `/fuel/` проверялись на стенде с одним складом против 23 на
  production; поведение сетки при 23 складах глазами не смотрено.
- Вход и запись под неадминистратором не проверялись: отдельной учётки без
  прав администратора по-прежнему нет. Это старый долг устава, а не пробел
  этой партии.
