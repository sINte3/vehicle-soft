Часть 1 технического задания: токены. Компоненты — часть 2, ниже по файлу.

Все числа получены измерением, а не подбором. Контраст считан по формуле
WCAG 2.1 для каждой пары «текст на фоне», объявленной в системе; исходные
значения — из `10-repo-inventory.json`.

## 1.3. DD-020 · Шкала текста сокращается с четырёх уровней до двух

**Основание.** Чтобы `--vs-text-soft` прошёл AA на самом тёмном из фонов
(`--vs-bg` #eef2f7), его нужно затемнить до `#616f82`. Это даёт 4,55 — но
`--vs-text-muted` равен `#5b6b80` и даёт 4,84. Два значения отличаются на
шесть единиц яркости и на глаз неразличимы. **Уровень, приведённый к норме,
перестаёт быть отдельным уровнем.**

Ниже `muted` места нет: порог 4,5 на светлом фоне и есть нижняя граница.

**Решение.**

| Токен | Судьба |
|---|---|
| `--vs-text` `#182230` | остаётся |
| `--vs-text-muted` `#5b6b80` | остаётся, единственный вторичный уровень |
| `--vs-text-soft` `#8a97a8` | **удаляется**, 28 использований переводятся на `--vs-text-muted` |
| `--vs-text-faint` `#b5c0d0` | **удаляется**, использований 0 |

**Отвергнуто.** Оставить `soft` для «неважного» текста — отвергнуто: у WCAG
нет исключения для текста, который автор счёл неважным. Если текст читают,
он обязан быть читаемым; если не читают — его не должно быть на экране.

## 1.5. DD-022 · Три пары-дубля разводятся по смыслу

Сверка по значению, не по имени (PR-002).

| Значение | Токены | Решение |
|---|---|---|
| `#15803d` | `--vs-brand-green`, `--vs-success` | `--vs-brand-green` **удаляется**; зелёный бренда и зелёный успеха — одно и то же, второе имя лишнее |
| `#e7f6ec` | `--vs-brand-green-s`, `--vs-success-bg` | то же: остаётся `--vs-success-bg` |
| `#ffffff` | `--vs-side-active-fg`, `--vs-surface` | **остаются оба**: белый текст на тёмном сайдбаре и белая поверхность карточки — разные роли, и в тёмной теме они разойдутся. Это тот случай, когда совпадение значений сегодня оправданно |

Последняя строка — причина, по которой чекер сообщает о дублях, а не падает
на них: совпадение значений бывает осмысленным, и решение принимает человек.

## 1.6. DD-023 · Двухуровневая архитектура токенов

Это и есть «заложить место под тёмную тему» из DD-001. Тёмная палитра
**не подбирается**; создаётся только механизм.

```css
/* Уровень 1 — ПАЛИТРА. Сырые значения, смысла не несут.
   Компоненты к ним не обращаются никогда. */
:root {
  --p-blue-600:  #2563eb;
  --p-slate-900: #182230;
  --p-slate-500: #5b6b80;
  --p-white:     #ffffff;
  /* … */
}

/* Уровень 2 — РОЛИ. Что этот цвет значит. Именно их видит весь код. */
:root {
  --vs-primary:    var(--p-blue-600);
  --vs-text:       var(--p-slate-900);
  --vs-text-muted: var(--p-slate-500);
  --vs-surface:    var(--p-white);
  /* … */
}

/* Тёмная тема переопределяет ТОЛЬКО уровень 2 и ничего больше.
   Сейчас блок пуст — место заложено, значения не подобраны. */
[data-theme="dark"] {
  /* --vs-surface: var(--p-slate-900); … */
}
```

**Правило, которое проверяет чекер.** CSS компонента обращается только к
`--vs-*`. Обращение к `--p-*` вне блока ролей — нарушение: оно обходит
переключение темы и снова разведёт интерфейс на два вида.

**Что это даёт.** Включить тёмную тему = заполнить один блок. Без этого
уровня пришлось бы править каждое место, где цвет использован.

# 2. Брейкпоинты

## 2.1. DD-024 · Тринадцать значений сводятся к четырём

**Как есть:** 1280, 1200, 1100, 1050, 1000, 900, 768, 760, 720, 700, 640,
600, 480. Восемь в `design-system.css`, пять — из `<style>` в шаблонах.
Опасны близнецы: 768 и 760, 720 и 700, 1100 и 1050 (PR-004).

**Шкала:**

| Значение | Что переключает |
|---|---|
| **1280** | контент перестаёт помещаться в `--vs-content-max` |
| **1024** | планшет: сайдбар сворачивается в иконочный рельс |
| **768** | сайдбар выходит из потока, становится выдвижным |
| **480** | одна колонка |

Значения совпадают с матрицей вьюпортов обхода
(`40-baseline-crawl-spec.md`) намеренно: съёмка попадает **внутрь** ветки
CSS, а не на её границу.

**Порядок перевода — по одному правилу за раз, не пакетом.** Каждый из 37
`@media` вне шкалы переносится на ближайшее объявленное значение, после чего
затронутые страницы переснимаются на четырёх вьюпортах и дифф просматривается.
Автоматической замены «ближайшим числом» не будет: 640 может означать и
«телефон», и «узкий планшет», и решает это содержимое правила, а не
расстояние до соседа.

# 3. Радиусы, тени, типографика

## 3.1. DD-025 · Радиусы: шесть ступеней → три

**Как есть:** 6, 8, 9, 10, 12, 14 px плюс `pill` (PR-005). 9 px не отличим
от 8 и 10, но требует решения при каждом новом компоненте.

| Токен | Значение | Где |
|---|---|---|
| `--vs-r-sm` | 6px | поля ввода, мелкие чипы, бейджи |
| `--vs-r` | 10px | карточки, панели, таблицы |
| `--vs-r-lg` | 14px | модальные окна, выдвижные панели |
| `--vs-r-pill` | 999px | пилюли и круглые кнопки |

## 3.2. DD-026 · Тени: пять → три, цветные свечения удаляются

`--vs-shadow-primary` и `--vs-shadow-success` (`0 8px 18px rgba(...,.28)`)
удаляются (PR-006). Тень цвета кнопки не несёт ни высоты, ни состояния — и
она мощнее тени модального окна, то есть шкала высот перевёрнута.

Состояние кнопки несут цвет фона и кольцо фокуса `--vs-ring-primary`,
которое уже есть.

| Токен | Роль |
|---|---|
| `--vs-shadow-sm` | приподнятая строка, наведение |
| `--vs-shadow` | карточка, выпадающее меню |
| `--vs-shadow-lg` | модальное окно, выдвижная панель |

## 3.3. DD-027 · Типографика: без изменений, кроме удаления неиспользуемого

Шкала 11/12/13/14/17/21/23 px при базовом 13 px **сохраняется**. Она плотная
и для ERP уместная; замечаний по ней измерение не дало.

Удаляется `--vs-fs-xl` (21px, использований 0) и `--vs-t` (0,17 с,
использований 0 — реальная шкала времени состоит из одного значения
`--vs-t-fast`). Вместе с шестью мёртвыми алиасами слоя совместимости это
закрывает PR-007: девять токенов из девяти.

**Ширины проектируются по узбекскому варианту** (метрики M6: узбекские
подписи на 19–47 % длиннее русских в тех же полях). Проверка обязательна:
базис снимается и на `lang=uz`, а не только на русском.

# 4. Компонент таблицы

Отвечает на PR-060 (сортировки нет нигде), PR-061 (пагинация в 5 шаблонах
из 86), PR-010 (17 одноразовых классов), PR-053 (нет поведения переполнения).

## 4.1. DD-028 · Три режима по объёму, режим объявляется явно

Разброс объёмов — пять порядков: от 394 817 строк в `fuel_transactions2` до
3 в `work_orders`, плюс двенадцать всегда пустых таблиц. Один компонент без
объявленных режимов оба конца не покрывает — и именно отсутствие этого
решения породило 17 одноразовых классов.

| Режим | Когда | Сортировка | Пагинация | Итоги |
|---|---|---|---|---|
| `is-static` | до ~200 строк, всё помещается | на клиенте | нет | по всей таблице |
| `is-paged` | 200 – ~5000 | на сервере | серверная, по страницам | по всей выборке, отдельным запросом |
| `is-stream` | свыше ~5000 | на сервере, ограниченный набор колонок | «дальше» по курсору | только по видимому окну, с явной подписью |

**Почему пороги именно такие — их надо проверить, а не поверить.** Числа
взяты из объёмов боевой базы и **на реальных данных не измерялись**: на
эфемерном экземпляре 394 817 строк не воспроизводятся. Порог между `is-paged`
и `is-stream` уточняется на staging в P7 замером времени ответа, и до тех пор
помечен как предположение.

## 4.2. DD-029 · Сортировка

Заголовок сортируемой колонки — кнопка, а не текст: доступна с клавиатуры,
несёт `aria-sort`. Состояний три: не отсортировано, по возрастанию, по
убыванию. Сортировка по умолчанию объявляется на каждом экране явно.

В `is-stream` сортировка разрешена только по колонкам, у которых есть индекс
в базе. Разрешать сортировку по неиндексированной колонке на 394 тысячах
строк — способ уронить отклик, а не удобство.

## 4.3. DD-030 · Переполнение колонки

Ширина проектируется по `p90` длины поля из метрик, обрезается после `p99`,
полное значение доступно по наведению и в карточке записи.

Поля, у которых `max` намного выше `p99`, обязаны иметь это поведение
объявленным — иначе одна аномальная строка ломает ширину всей таблицы:

| Поле | p90 | p99 | max |
|---|---|---|---|
| `daily_records.customer` | 25 | 40 | **111** |
| `daily_records.idle_reason` | 37 | 50 | **211** |
| `deficiencies.text` | 115 | 161 | **314** |
| `drone_flights.location_text` | 57 | 81 | 138 |

## 4.4. DD-031 · Действия строки

`vs-row-actions` существует и использован **один раз** при 104 таблицах
(PR-012). Расширяется до компонента: фиксированная зона справа, иконочные
кнопки с доступным именем, зона нажатия не меньше 32×32 px.

# 5. Статус

## 5.1. DD-032 · Один компонент, семантика параметром

PR-012: девять из двадцати однократных классов — варианты бейджа под
значение справочника (`vs-badge-cat-mtz`, `vs-badge-role-admin`…). Классы
под каждое значение данных удаляются; остаётся один компонент, которому
передаётся семантическая роль.

Всего статусных значений в системе около 25, почти все словари по 2–4
значения (метрики M10) — набор мал, и разрастание классов ничем не оправдано.

**Форма — точка с подписью или залитая пилюля — решается отдельно** после
замера плотности на эталонном экране `fuel/transactions`. В P1 это не
измерялось, и предрешать нельзя (`21-reference-analysis.md`, ADAPT-5).

# 6. Визуализация данных

## 6.1. DD-033 · Четыре типа, каждый привязан к экрану

Решение владельца — заводить (DD-003). Рисуется своим кодом на SVG.

| Тип | Отвечает на вопрос | Экран |
|---|---|---|
| Столбцы по времени | «как менялось по дням/месяцам» | расход топлива, дневная выработка |
| Горизонтальные полосы с рангом | «кто больше, кто меньше» | техника по выработке, операторы дронов |
| Линия с одной серией | «растёт или падает» | остаток на складе АЗС |
| Полоса-доля | «сколько из скольких» | техника в работе / всего, простои |

**Правила, обязательные для всех четырёх.** Ось с подписями и нулевой
линией. Никаких градиентов внутри элемента: градиент делает высоту
столбца неоднозначной. Цвет — только из семантических токенов. Каждое
значение доступно текстом рядом или в таблице под графиком: график не может
быть единственным носителем числа, иначе он недоступен без зрения.

**Не заводится:** кольцевые диаграммы, полукруглые датчики, радары,
трёхмерное — механизм вреда разобран в `21-reference-analysis.md`, REJECT-2.

# 7. Что эта спецификация не решает

- **Формы.** `daily_entry` несёт 83 % работы и содержит 386 строк
  собственного CSS. Контракт формы — отдельный документ после эталонного
  экрана, а не раздел здесь.
- **Пустые состояния.** Двенадцать экранов пользователь видит только
  пустыми (PR-051); это самостоятельная задача, а не вариант компонента.
- **Мобильные раскладки.** По DD-002 они делаются под задачу, а не выводятся
  из десктопных, и в основаниях системы им места нет.
- **Единицы измерения.** DD-004 разделён: схема вне трека, поле выбора —
  внутри, после появления справочника.
