### Три вывода, которые меняют постановку задачи

**INFERENCE 1. Дизайн-системы «нет» — неверная посылка. Она есть и доказана в
бою.** F2 + F8: 90 токенов, 16 секций, и целый модуль из 22 экранов, полностью
на ней построенный, без единой легаси-переменной. Проблема не в отсутствии
системы, а в **покрытии** (F7: 22 шаблона мимо неё) и в **энтропии на входе**
(F4, F9: каждая задача дописывает свой CSS и свой класс таблицы). Значит цель
не «создать Design System», а «замкнуть систему: доработать → мигрировать →
запретить обход».

**INFERENCE 2. Главный дефект — не эстетика, а способ производства.** F9 (15+
классов таблиц, названных по кодам задач `fuel002a…fuel002h`) и F4 (CSS вне
системы больше, чем внутри) описывают один механизм: инкремент делается
локальным CSS вместо общего компонента, потому что ничто этого не запрещает.
Без автоматической преграды любой редизайн деградирует ровно тем же путём за
следующие полгода. **Механизм важнее палитры.**

**INFERENCE 3. Стандартный набор «AI-slop» здесь по большей части
отсутствует.** F12: градиентов 5 штук на весь проект. F14: базовый шрифт
13 px, потолок шкалы 23 px — гигантских заголовков нет, плотность
ERP-совместимая. Внешних шрифтов нет (F1). Обвинять интерфейс в
«шаблонном SaaS-виде» на этих данных нельзя. Реальные кандидаты в slop
другие: **эмодзи вместо иконок** (F11), **цветные свечения под кнопками**
(F15), **6 ступеней радиуса** (F14), **8 брейкпоинтов** (F13). Это разбирается
в §5.4, и часть из них требует подтверждения рендером.

## 1. Executive decision

Основная интеллектуальная работа ведётся **в Claude Code cloud (эта среда) с
подключённым GitHub** — потому что здесь одновременно доступны репозиторий,
Node 22 и уже установленный Chromium (F25), а `tests/harness.py` (F17)
позволяет поднять **настоящее приложение на одноразовой SQLite** и снимать с
него скриншоты. Это снимает главный компромисс задачи: визуальное
исследование становится доступным **без доступа к staging и production
вообще** — что критично, поскольку staging сегодня занят треком Дронов (F20),
а прод-деплой закрыт незакрытым гейтом (F21). Claude Desktop получает роль
не рабочей среды, а канала загрузки reference-скриншотов и обсуждения; сами
скриншоты кладутся **в репозиторий** (`docs/ux/references/`), потому что
только там их увидит любая будущая сессия. Claude Code CLI на сервере
подключается **позже и только** для staging-валидации и релиза по
действующим процедурам проекта. Браузерный доступ нужен обязательно
(обоснование — §5.1) и реализуется **Playwright под Node**, не интерактивным
Cowork, потому что базовый набор скриншотов должен быть воспроизводимым
скриптом, а не разовым проходом. Порядок работ меняется относительно
предложенного: **сначала измеряем продукт, потом смотрим референсы** —
иначе референсы задают цель раньше, чем известна задача (§2). И главный
результат Phase 1–3 — не палитра, а `tools/check_design_system.py`:
автоматическая преграда, без которой редизайн распадётся тем же способом,
каким распался предыдущий (INFERENCE 2, F19).

## 2. Рекомендуемая архитектура работы

Предложенная в задании цепочка `REFERENCES → VISUAL AUDIT → …` исправлена в
двух местах.

**Исправление А: референсы после аудита, не до.** Механизм: reference-скриншот
— это *кандидат в решения*. Пока не измерена проблема, невозможно отличить
подходящий паттерн от красивого; а увиденный первым визуальный образец
становится целью и дальше подтверждается задним числом. Практическое
следствие — жёсткий критерий выхода фазы 2: **референс без привязки к
зарегистрированной проблеме не попадает в спецификацию** (§14, P2).

**Исправление Б: repository analysis перед visual audit, не после.** Статический
инвентарь (F4, F7, F9) даёт список того, *что именно* идти смотреть в браузере
и на каких экранах ожидается расхождение. Обратный порядок даёт красивые
скриншоты без гипотез.

```
USER
 │
 ▼
REPOSITORY INVENTORY            ← измеримо, скриптом, регенерируемо
 │   tools/ux/inventory.py → docs/ux/10-repo-inventory.json
 ▼
EPHEMERAL APP INSTANCE          ← tests/harness.py, одноразовая SQLite
 │   ни staging, ни production не затрагиваются
 ▼
VISUAL BASELINE                 ← Playwright, матрица вьюпортов, PNG в репозиторий
 │
 ▼
PROBLEM REGISTER                ← дефект = ID + артефакт + модуль + тяжесть + цена
 │
 ▼
REFERENCES                      ← консультируются как кандидаты к проблемам из регистра
 │   ADOPT / ADAPT / INSPIRE / REJECT
 ▼
DESIGN DECISIONS                ← по одному решению на проблему, ADR-формат
 │
 ▼
DESIGN SYSTEM v2 + CHECKER      ← токены, контракты компонентов, tools/check_design_system.py
 │
 ▼
CANONICAL SCREENS               ← настоящие Jinja+CSS, не макеты
 │
 ├──────────── GATE: подпись владельца на отрендеренных экранах ────────────
 ▼
CLAUDE CODE: FOUNDATION         ← токены и общие компоненты; немигрированные страницы не меняются
 │
 ▼
CLAUDE CODE: MODULE MIGRATION   ← один модуль = один PR
 │
 ▼
VISUAL QA                       ← пересъёмка baseline, диффы, a11y, checker
 │
 ▼
STAGING                         ← только когда площадка свободна (docs/STAGING.md)
 │
 ▼
RELEASE GATE пуст → PRODUCTION
```

Обратные связи, которых нет в исходной схеме, но которые нужны: из VISUAL QA
в MODULE MIGRATION (дифф не принят — возврат), из CANONICAL SCREENS в DESIGN
SYSTEM (экран не собирается из компонентов — правится система, а не экран).

## 3. Какую среду Claude использовать

Сравнение по критериям из `<decision_method>`. Оценка «+ / ± / −».

| Критерий | Claude.ai чат | **Claude Code cloud** | Claude Desktop | Claude Code CLI на сервере |
|---|---|---|---|---|
| Доступ к репозиторию | − (вставка кусков) | **+ полный, git** | ± (MCP/локальный клон) | + полный |
| Запуск приложения | − | **+ harness + Node + Chromium (F17, F25)** | ± | + но это боевая машина |
| Браузерный аудит | − | **+ Playwright headless** | ± зависит от настройки | ± ставить браузер на прод-сервер |
| Приём reference-изображений | + | ± (через репозиторий — надёжнее) | **+** | − |
| Агентность (правки, тесты, PR) | − | **+** | ± | + |
| Безопасность для production | + | **+ изолированный контейнер** | + | **− ближе всего к бою** |
| Воспроизводимость | − | **+ всё в git** | − | ± |
| Сохранение контекста | − сессия чата | **+ артефакты в git** | − | ± |
| Стоимость инфраструктуры | 0 | **0** | 0 | 0 |
| Сложность настройки | 0 | **низкая, всё есть** | средняя | средняя (Windows, NSSM) |

**PRIMARY — Claude Code cloud (эта среда).** Единственная, где сходятся
репозиторий, исполняемое приложение и браузер, и при этом отсутствует любой
путь к production. Здесь делается: инвентарь, baseline-скриншоты, проблемный
регистр, анализ референсов, спецификация дизайн-системы, ТЗ, реализация,
визуальная QA.

**SECONDARY — Claude Desktop.** Только приём и первичная сортировка
reference-скриншотов, обсуждение решений с владельцем, чтение готовых
документов. Никакой реализации: то, что решено в Desktop и не записано в
`docs/ux/`, для следующей сессии не существует.

**EXECUTION ENVIRONMENT (релиз) — Claude Code CLI на сервере.** Подключается
на фазах P7–P8: развёртывание на staging, прогон валидации, релиз на
production по `docs/RELEASE_AND_BACKUP_PROCEDURE.md`. Не участвует в
проектировании.

**Claude.ai чат — не используется.** Отдельного полезного места в этой схеме
у него нет: всё, что он может, лучше делает Desktop (изображения) или Code
cloud (код).

## 4. Reference screenshot workflow

### 4.1. Нужна ли структура каталогов вообще

Да, но **не та, что предложена**. Девять папок из задания включают категории,
под которые у Vehicle Soft либо нет проблемы, либо нет объекта: `typography/`
как отдельная папка бессмысленна — типографика оценивается на каждом
скриншоте и по одному кадру не выносится; `charts/` преждевременна, потому
что визуализации данных в продукте нет вовсе (F16) и вопрос «заводить ли её»
— отдельное решение, а не вопрос оформления; `cards/` растворяется в
`dashboards/`.

**RECOMMENDATION.** Семь категорий, привязанных к измеренным дефектам:

```
docs/ux/references/
  _unsorted/     ← приёмник; здесь ничего не остаётся после сортировки
  shell/         ← сайдбар, топбар, вторичная навигация, хлебные крошки,
                   заголовки страниц   [привязка: F10 — три разные навигации]
  tables/        ← плотность, липкие области, действия строки, массовые
                   действия, переполнение   [F9 — 15+ реализаций таблицы]
  filters/       ← панели фильтров, поиск, периоды, сохранённые виды
  forms/         ← группировка полей, валидация, сохранение/отмена
                   [F4 — daily_entry.html: 387 строк своего CSS]
  dashboards/    ← иерархия KPI, приоритизация, плитки, и (отдельно)
                   визуализация — если решение её заводить будет принято
  states/        ← пустое, загрузка, ошибка, нет прав
  density/       ← компактный десктоп, планшет, мобильный
                   [F13 — 8 брейкпоинтов без шкалы]
```

Если у вас есть материал, который никуда не ложится, — он остаётся в
`_unsorted/` и это сигнал: либо категория лишняя, либо у Vehicle Soft нет
соответствующей проблемы, и такой референс в спецификацию не пойдёт.

### 4.2. Куда загружать

**Основной способ: в репозиторий, ветка UI-трека.** Причина — §16: только
файл в git виден любой будущей сессии без пересказа. Изображение, приложенное
в чат, живёт до конца сессии.

Практически: положите файлы в `docs/ux/references/_unsorted/` любым способом
(через Desktop-сессию с доступом к клону, через веб-интерфейс GitHub, или
приложите их мне в сессии — я разложу и закоммичу по именам, `git add` только
поимённо, как требует CLAUDE.md).

Гигиена размера: понижать до ширины ≤ 1600 px, JPEG/WebP качество ~82,
цель ≤ 300 КБ на файл, ориентир по объёму — 30–50 файлов. При 40 файлах
это ~10 МБ, приемлемо. Скриншоты — чужие продукты, они остаются
внутренним аналитическим материалом, в поставляемую сборку не попадают
и визуально не копируются (§4.5).

### 4.4. Как анализировать

Каждый значимый кадр проходит рубрику из 22 критериев задания, но с двумя
обязательными полями, которых в задании нет и без которых рубрика
превращается в вкусовщину:

1. **`PROBLEM-ID`** — на какую зарегистрированную проблему Vehicle Soft этот
   паттерн отвечает. Пусто → референс в спецификацию не идёт.
2. **`COST`** — оценка внедрения в терминах *этого* кода: сколько строк
   `design-system.css`, сколько шаблонов, нужен ли JS (у проекта только
   ванильный JS, F1), ломает ли `check_templates.py`.

Формат строки в `docs/ux/21-reference-analysis.md`:

| Поле | Содержание |
|---|---|
| FILE | `tables-04-sticky-header-inline-row-actions.png` |
| PATTERN | одно предложение: что именно наблюдается |
| WHY IT WORKS | механизм, а не впечатление: «действия строки не занимают колонку, потому что появляются в правом липком слое при наведении, освобождая ~120 px ширины» |
| PROBLEM-ID | `PR-014` |
| SCORES | 22 критерия, шкала 0–2, только там, где кадр даёт основание судить; «не видно» — это `n/a`, а не 0 |
| VERDICT | ADOPT / ADAPT / INSPIRE / REJECT |
| ADAPTATION | если ADAPT — чем именно отличается решение для Vehicle Soft |
| COST | по шкале S / M / L с обоснованием в строках и файлах |

Классификация — с явными порогами, иначе всё становится ADAPT:

- **ADOPT** — паттерн решает зарегистрированную проблему, реализуется
  существующими средствами (Jinja + CSS + ванильный JS), не требует новых
  зависимостей, не снижает плотность.
- **ADAPT** — идея верна, но её прямая форма конфликтует с ограничением
  Vehicle Soft (двуязычность и длина кириллических строк; плотность ERP;
  отсутствие JS-фреймворка; on-premises без внешних шрифтов). Обязательно
  указывается, какое ограничение и как обходится.
- **INSPIRE** — влияет только на направление (ощущение плотности, характер
  границ), в спецификацию не переносится буквально.
- **REJECT** — с указанием **механизма вреда**, а не «не подходит». Типовые
  для ERP: крупные карточки KPI, вытесняющие таблицу за первый экран;
  анимация переходов между разделами (стоимость — задержка на каждом
  переключении при 40+ переходах в день); иллюстрации пустых состояний
  вместо действия; «карточка на любую сущность» вместо таблицы.

### 4.5. Граница копирования

Извлекаются: пропорции, плотность, иерархия, порядок элементов, поведение
состояний. Не извлекаются: палитра как таковая, иллюстрации, шрифты,
узнаваемые формы бренда. Практическая проверка: если решение нельзя
пересказать одним предложением о механизме — это копирование внешнего вида,
а не заимствование паттерна.

## 5. Vehicle Soft visual audit workflow

### 5.1. Зачем нужен рендер, если есть репозиторий

Четыре причины, каждая опирается на факт:

1. **Каскад не читается из исходников.** F4: 2292 строки inline-CSS
   переопределяют дизайн-систему постранично. Какое правило победит на
   конкретном элементе — вопрос рендера.
2. **Слой совместимости делает разметку неоднозначной.** F3 + F7: одна и та
   же разметка выглядит по-разному в зависимости от того, какой набор
   переменных разрешился. Предыдущий аудит уже поймал ровно такой дефект —
   `fuel/cards.html` с `var(--text-muted)`, не определённой в области
   видимости: код выглядит корректным, рендер — нет.
3. **Плотность, переполнение и переносы не выводятся из кода.** F13:
   8 брейкпоинтов без шкалы. Проект уже обжигался на этом — в `tools/`
   лежит `measure_drone_card_wrap.py`, написанный из-за переноса денежной
   суммы внутри карточки.
4. **Длина реальных строк определяет ширину колонок.** Двуязычность
   (русский/узбекская кириллица) даёт разброс длины подписей, который на
   синтетике не воспроизводится.

### 5.2. На чём смотреть

**RECOMMENDATION: эфемерный локальный экземпляр как основная площадка.**
`tests/harness.py` (F17) уже умеет собирать настоящее приложение на
одноразовой SQLite во временном каталоге. Требуется дописать только сидер
фикстур с **реалистичными длинами строк**, не реальными данными:
названия техники, ФИО операторов, номера карт, суммы порядка
`15 878.64`, узбекские подписи. Это даёт: ноль риска, доступность прямо
сейчас (в обход занятого staging, F20), полную воспроизводимость и
возможность прогонять baseline повторно после каждого PR.

Ограничение этого пути честно называется: **объёмы данных синтетические**,
поэтому вопросы «как ведёт себя таблица на 20 тысячах строк» и «как выглядит
дашборд на настоящей сезонной нагрузке» решаются позже на staging (§7).

| Дефект | Что не так → почему хуже → чем заменить |
|---|---|
| **Эмодзи вместо иконографии** (F11: 228 вхождений, 43 глифа) | Эмодзи рендерится системным шрифтом: на Windows-рабочих местах это Segoe UI Emoji — цветной, другой оптический вес, другой базовый уровень, чем у текста. → В плотной таблице цветное пятно перетягивает внимание с данных; ⚠ и ❌ вводят цвет, не входящий в семантическую палитру, мимо токенов; смысл 🔸 и 💡 неоднозначен и не переводится. → Заменить на инлайновый SVG-набор с едиными размером и толщиной штриха: секция 15 CSS (`ICONS (size + stroke conventions)`) уже существует, набор в `base_next.html` (18 SVG) уже есть — нужно его расширить и вынести в Jinja-макрос `{{ icon('save') }}`. | **Одноразовые классы таблиц** (F9: 15+, названных по кодам задач) | Каждая новая задача создаёт свой визуальный вариант одной сущности. → Пользователь на четырёх экранах одного модуля видит четыре разные таблицы: разный внутренний отступ, разное выравнивание чисел, разное поведение при переполнении — и не может перенести навык между экранами. → Один компонент `vs-table` с объявленными модификаторами (`is-compact`, `vs-num`, и то, что покажет P1), плюс запрет на новые классы `*-table` в `check_design_system.py` |
| **Три реализации вторичной навигации** (F10: 110 / 136 / 31 строк) | Одна функция — три верстки. → Разное положение, разные активные состояния, разная реакция на сжатие окна между модулями Запчастей, АЗС и Дронов. → Один макрос `_module_nav.html`, принимающий список пунктов; три файла становятся тремя списками данных |
| **Цветные свечения под кнопками** (F15: `--vs-shadow-primary`, `--vs-shadow-success` — `0 8px 18px rgba(...,.28)`) | Это единственная пара токенов с чисто декоративной функцией: тень цвета кнопки не сообщает ни высоты, ни состояния. → Ровно тот приём, который читается как «SaaS-лендинг внутри рабочей системы», и он же ломает шкалу высот: под кнопкой тень мощнее, чем под модальным окном (`--vs-shadow-lg`). → Убрать; состояние кнопки нести цветом фона и кольцом фокуса (`--vs-ring-primary` уже есть) |
| **Шесть ступеней радиуса** (F14: 6/8/9/10/12/14 + pill) | 9 px не отличим от 8 и 10 на глаз, но требует решения при каждом новом компоненте. → Решение принимается наугад → визуальная несогласованность между соседними элементами. → Три ступени + pill; какие именно — по результатам замера фактического использования каждого токена в P1 |
| **Восемь брейкпоинтов** (F13) без объявленной шкалы | Новый `@media` дописывается под конкретную страницу. → Поведение на промежуточных ширинах не определено ни для одной страницы целиком. → 4 брейкпоинта, совпадающие с матрицей вьюпортов §5.3; остальные вычищаются в фазе Foundation с обязательным диффом скриншотов |
| **CSS вне системы больше, чем внутри** (F4) | Это не дефект оформления, а **источник всех предыдущих строк таблицы**. → Пока inline-`<style>` разрешён, любая исправленная несогласованность возвращается со следующим инкрементом. → Порог в `check_design_system.py`: блок `<style>` длиннее N строк — блокирующая ошибка; для существующих файлов — зафиксированный базовый уровень, который может только уменьшаться |

**INFERENCE.** Наблюдаемое ощущение «интерфейс отстаёт от функциональности»
вызвано не декоративностью, а **энтропией**: одна и та же вещь выглядит
по-разному в разных местах. Это лечится замыканием системы, а не сменой
визуального языка. Смена языка (палитра, радиусы, тени) — вторична и дешева
после того, как обход системы закрыт.

## 6. Browser automation decision

**Выбор: Playwright под Node, headless Chromium из `/opt/pw-browsers`.**

Обоснование по критериям:

| | Playwright (скрипт) | Cowork / интерактивный браузер |
|---|---|---|
| Воспроизводимость | **скрипт в git, повторяется дословно** | проход не повторяется |
| Матрица вьюпортов | **4 вьюпорта × 86 маршрутов автоматически** | вручную нереалистично |
| Артефакты для сравнения до/после | **PNG с детерминированными именами** | разрозненные кадры |
| Интеграция с a11y | **`@axe-core/playwright` в том же прогоне** | отдельно |
| Разведка неизвестного | ± по списку URL | **+ там, где не знаешь, что искать** |
| Стоимость настройки | низкая: Chromium уже стоит (F25), Node 22 есть | 0 |

Ключевой аргумент: baseline существует не чтобы посмотреть один раз, а
**чтобы пересниматься после каждого PR** и давать дифф (§ visual_validation).
Интерактивный проход этого дать не может по определению.

**Роль Cowork — fallback, а не альтернатива**, для двух конкретных ситуаций:
(1) разведочный проход по staging, когда площадка освободится, где заранее
неизвестно, что смотреть; (2) сценарии, которые не воспроизводятся на
синтетических фикстурах (реальные объёмы Topaz, экраны интеграции Wialon).

**Важно:** `playwright` для Python **не устанавливать** (F25 — его нет, и
CLAUDE.md запрещает добавлять зависимости без обоснования). Node-инструмент
живёт в `tools/ux/` со своим `package.json` и **не входит в
`requirements.txt`** — это dev-инструмент, а не зависимость приложения.
Тем не менее это новая зависимость в репозитории, и по правилу CLAUDE.md она
**объявляется владельцу до внесения**, а не добавляется молча. И `playwright
install` не запускать — браузеры уже есть.

## 7. Production vs Staging

**Однозначно: три уровня, в этом порядке.**

**Уровень 1 — эфемерный локальный экземпляр. Основная площадка, ~95 % аудита.**
Что: инвентарь, baseline-скриншоты, все состояния форм, все вьюпорты, a11y,
визуальная QA после каждого PR. Почему: ноль риска, доступен немедленно,
воспроизводим. Основание: F17.

**Уровень 2 — Staging (`10.103.25.14:5051`). Вторичная, ~5 %.**
Что: реальные объёмы данных — поведение таблиц на настоящем количестве строк,
дашборд АЗС на сезонной нагрузке, экраны интеграций. Плюс обязательная
приёмочная валидация перед релизом (P7).
**Когда: не сейчас.** F20 — площадка занята треком Дронов с 2026-08-09,
правило «один трек за раз» действует. UI-трек **встаёт в очередь**, а
не деплоит поверх. Это не помеха: уровень 1 не требует staging.

**Уровень 3 — Production (`10.103.25.14:5050` / `app.vehiclesoft.pp.ua`).
Только READ-ONLY, только если уровень 2 не даёт материала, и с оговоркой,
которой в задании нет.**

**Оговорка, вытекающая из F24 — она важнее общего запрета.** В этом
репозитории задокументированы три исправленных дефекта класса «GET с
побочным эффектом»: `RELEASE_AUDIT_GET_SIDE_EFFECT_001` (экспорт Wialon по
GET), `_002` (выгрузка workload по GET), `_003` (logout по GET). Следствие:
**«только GET-запросы» здесь не эквивалентно «безопасно»**, и краулер,
переходящий по ссылкам, может выполнить logout или запустить выгрузку. Отсюда:

- обход только по **явному белому списку URL**, зафиксированному в
  `docs/ux/11-baseline/prod-allowlist.txt` и утверждённому владельцем;
- **переход по ссылкам выключен** (`page.goto` по списку, никаких кликов);
- отдельная учётная запись с минимальными правами, не администратор;
- ни одной отправки формы, ни одного клика по кнопке действия, ни одного
  экспорта;
- ни `Restart-Service`, ни деплоя, ни правки настроек;
- фиксация: список URL, время прогона, отсутствие не-GET запросов в
  логе — в `docs/ux/11-baseline/prod-readonly-run.md`.

**RECOMMENDATION: вероятнее всего уровень 3 не понадобится вовсе.** Более
безопасная и более полезная замена — **обезличенная копия продовой базы**,
поднятая на уровне 1: она даёт настоящие длины строк и настоящие объёмы без
единого запроса в боевую систему. Это и есть пункт в списке §17.

| Формы | как реализованы валидация, обязательность, ошибки — единообразно или постранично | чтение `daily_entry.html`, `spare_part_form.html`, `work_order_form.html` |
| Модальные окна / drawer | существуют ли вообще как компонент, или каждый экран свой | grep `modal|drawer|dialog|<dialog` |
| Состояния | реализованы ли skeleton / loading / «нет прав» | grep + рендер |
| Доступность | что уже сделано: есть skip-link, есть `tests/test_cycle23_a11y.py` — каков охват | чтение теста |
| Экспорт | `excel_export.py` и `spare_parts_pdf.py` — **защищённая зона**: деловое содержание колонок не меняется (CLAUDE.md) | только фиксация границы |

Всё это оформляется как **регенерируемый** `tools/ux/inventory.py` →
`docs/ux/10-repo-inventory.json`, чтобы цифры не устаревали и чтобы новая
сессия получала их командой, а не чтением прозы.

**Ограничение, которое должно быть учтено сразу:** `app = create_app()`
выполняет `db.create_all()` на импорте (CLAUDE.md). Любой инструмент

Импорт допустим только в `tests/harness.py`, где база одноразовая.

## 11. Figma decision

**Ответ: полноценный Figma не использовать. Ограниченное использование —
опционально и решается только на гейте P3.**

Обоснование механизмом, а не предпочтением:

1. **Второй источник правды разъедется.** Дизайн-система уже существует в
   коде (F2) и доказана 22 экранами (F8). Figma-библиотека станет вторым
   описанием тех же токенов, и первое же расхождение придётся разрешать
   вручную. У проекта нет JS-компонентов, к которым можно привязать Code
   Connect: разметка — Jinja, стили — рукописный CSS. Автоматической связи
   не будет ни в одну сторону.
2. **Стоимость дубля несоразмерна.** 86 шаблонов. Отрисовка даже трети —
   недели, и результат устареет к первому же инкременту соседнего трека
   (за последний месяц появился целый модуль дронов).
3. **Canonical screens лучше делать настоящими.** Отрендеренный экран на
   реальном Jinja+CSS — это одновременно макет и проверка, что система из
   своих компонентов собирается. Макет в Figma такой проверки не даёт: в нём
   собирается всё.

**Единственный случай, когда Figma окупается** — компоновка, которой в
продукте нет вообще и которую дороже перебирать в CSS, чем двигая
прямоугольники: перестройка информационной иерархии главного дашборда и
(если будет решено) первое появление визуализации данных. Тогда — 2–4
разведочные доски, только layout, без библиотеки компонентов, без токенов,
без handoff. Итог доски — решение в `docs/ux/30-design-decisions.md`, а не
файл, на который потом ссылаются.

**Что заменяет Figma в этой схеме:** dev-маршрут `/__ui/kitchen-sink` (§9)
как живая витрина компонентов и 7 canonical screens (§13) как согласуемые
эталоны.

## 13. Структура будущего ТЗ

ТЗ — не один документ, а **`31-design-system-v2.md` + набор
`41-task-specs/UI-NNN-*.md`**. Причина: единый 200-страничный файл не
исполняется агентом порционно и не ревьюится.

**Спецификация дизайн-системы `31-design-system-v2.md`:**

```
1. Принципы          — 5–7 правил, каждое с механизмом и проверкой
2. Foundations
   2.1 Типографика   — шкала, где какая ступень, кириллица ru/uz
   2.2 Цвет          — токены; таблица «было → стало → селекторов затронуто»;
                       контраст каждой пары текст/фон числом
   2.3 Отступы       — шкала, привязка к плотности таблиц
   2.4 Радиусы       — сокращение 6 → 3 (F14) с обоснованием по факту использования
   2.5 Границы/тени  — шкала высот; судьба цветных свечений (F15)
   2.6 Брейкпоинты   — 8 → 4 (F13), совпадают с матрицей съёмки
   2.7 Иконки        — SVG-набор, размеры, толщина штриха, макрос,
                       карта замены 43 эмодзи (F11)
3. Core components   — только фактически используемые: кнопка, иконочная
                       кнопка, поле, select, мультиселект, дата/период,
                       чекбокс, радио, бейдж, статус, дропдаун, пагинация,
                       табы, тултип
4. Enterprise        — таблица (+модификаторы), панель фильтров, поиск,
                       KPI-блок, форма, модальное окно, вторичная навигация,
                       заголовок страницы, панель действий, алерт,
                       пустое/загрузка/ошибка/нет прав
5. Не входит         — явный список: чего не делаем и почему
                       (визуализация данных — отдельное решение; drawer —
                       если не подтверждено использование; тёмная тема — нет)
6. Контракты         — для каждого компонента: разметка, классы,
                       обязательные атрибуты доступности, состояния,
                       поведение при переполнении, поведение на 4 вьюпортах

**Спецификация задачи `41-task-specs/UI-NNN-*.md`** — 10 обязательных полей,
формат согласован с `docs/PROMPT_PROTOCOL.md`:

```
ID, название, фаза, зависимости
SCOPE               — что делаем, одним абзацем
AFFECTED FILES      — поимённо; git add только по этому списку
ALLOWED CHANGES     — что разрешено трогать
PROTECTED AREAS     — что не трогаем: смысл выгрузок Excel/PDF,

REQUIRED TESTS      — compileall, check_templates, check_design_system,

VISUAL CHECKPOINTS  — список маршрутов × вьюпортов для пересъёмки
BEFORE/AFTER        — пути к baseline и к новым кадрам, порог диффа
ROLLBACK            — git revert в обратном порядке (reset --hard запрещён)
GIT                 — ветка, гранулярность коммитов, merge commit не squash

## 14. Roadmap

Восемь фаз. Переход разрешён только при выполнении **проверяемых командой**
критериев. «Выглядит нормально» критерием не является.

---

**P0 — Workflow & Discovery** *(этот документ)*
- **GOAL** — зафиксировать схему работы и границы.
- **INPUT** — репозиторий, задание.
- **WORK** — инспекция (§0), выбор среды, проектирование процедуры.
- **OUTPUT** — `docs/ux/00-workflow.md`, `docs/tracks/ui.md`, место в очереди на staging.
- **EXIT** — документ закоммичен; трек-файл создан по конвенции; владелец подтвердил разрешения из §17.

---

**P1 — Evidence**
- **GOAL** — измеримая картина текущего состояния.
- **INPUT** — P0.
- **WORK** — `tools/ux/inventory.py`; сидер фикстур; эфемерный экземпляр; Playwright-съёмка 4 × ~86; прогон axe; матрица консистентности; проблемный регистр.
- **OUTPUT** — артефакты 2–6 из §12.
- **EXIT** —
  1. `inventory.py` воспроизводит json дважды подряд байт в байт;
  2. прогон съёмки: **0 маршрутов с ошибкой рендера**, каждый маршрут из списка представлен на 4 вьюпортах;
  3. `a11y-baseline.json` содержит **числа** по severity;
  4. **у каждой записи проблемного регистра есть минимум один артефакт-доказательство** (кадр или строка инвентаря);
  5. в матрице консистентности нет ячеек «?».

---

**P2 — References**
- **GOAL** — отобрать паттерны под зарегистрированные проблемы.
- **INPUT** — P1 + материал владельца.
- **WORK** — сортировка по 7 категориям, рубрика 22 критериев, вердикты.
- **OUTPUT** — артефакты 7–8.
- **EXIT** —
  1. каждый файл имеет строку в INDEX;
  2. **каждый ADOPT/ADAPT ссылается на существующий PROBLEM-ID; референсов без привязки нет** — это и есть механизм против декоративного редизайна;
  3. каждый REJECT содержит **механизм вреда**, а не оценку;
  4. каждая проблема тяжести ≥ средней либо получила кандидата, либо помечена «решение без референса».

---

**P3 — Design decisions + Design System v2 spec**
- **GOAL** — одно решение на проблему и написанная преграда.
- **INPUT** — P1, P2.
- **WORK** — ADR; спецификация; **написание `tools/check_design_system.py`**.
- **OUTPUT** — артефакты 9–10 + чекер.
- **EXIT** —
  1. ровно одно решение на каждую проблему тяжести ≥ средней;
  2. таблица токенов заполнена: старое значение, новое, **число затронутых селекторов** (посчитано, не оценено);
  3. контраст каждой объявленной пары текст/фон — **числом**, порог WCAG AA;
  4. чекер написан, запускается, **падает с известным зафиксированным числом нарушений** — базовым уровнем, который дальше только уменьшается;
  5. отрицательный контроль: чекер проверен на заведомо нарушающем фрагменте и **отличает нарушение от его отсутствия** (правило CLAUDE.md о проверках, дающих одинаковый результат);
  6. решение по Figma (нужны ли разведочные доски) принято и записано.

**P4 — Canonical screens** ← **ГЛАВНЫЙ ГЕЙТ**

- **INPUT** — P3.
- **WORK** — реализация 7 экранов на новой системе + `/__ui/kitchen-sink`.

  1. 7 экранов отрендерены, `check_design_system.py` на них **чист**;
  2. axe: **0 serious/critical** на этих экранах;
  3. до/после на 4 вьюпортах приложены;
  4. **число одноразовых CSS-правил, добавленных ради этих экранов, — 0**: всё, чего не хватило, стало компонентом системы (это и есть проверка, что система собирается);

## 15. Safety boundaries

**Production.**
- Никаких изменений: ни данных, ни настроек, ни кода, ни деплоя, ни
  перезапуска служб — весь период аудита.
- Если чтение всё же понадобится: только белый список URL, **без перехода по
  ссылкам** (обоснование — F24), минимальные права, ни одной отправки формы,
  ни одного экспорта. Прогон документируется.
- Прод-деплой физически закрыт, пока `RELEASE_GATE.md` не пуст (F21).

**Staging.**
- Правило «один трек за раз» соблюдается: сейчас занят Дронами (F20),
  UI-трек ждёт. Заняв площадку — заменить строку целиком, отдельный коммит;
  освободив — вернуть «нет».

**Репозиторий.**
- `git add -A` и `git add .` запрещены — только поимённо, с `git status
  --short` перед коммитом.
- `git reset --hard` как откат запрещён — только `git revert` в обратном
  порядке.
- Мерж PR — merge commit, не squash.
- Общие файлы `templates/base_next.html` и `static/css/design-system.css` —
  **предмет этого трека по определению**, поэтому UI-трек объявляет это
  соседям заранее в `docs/tracks/ui.md` и в описании каждого PR. Это самый
  вероятный источник конфликта с треками Дронов, АЗС и Запчастей.

**Инструменты.**
- Любой скрипт аудита — читатель: не импортирует `app` (иначе
  `db.create_all()` на импорте). Приложение поднимается только через
  `tests/harness.py` на одноразовой базе.
- `requirements.txt` не меняется. Node-инструменты — в `tools/ux/`, объявляются.
- `playwright install` не запускать: браузеры уже стоят (F25).

**Границы Claude Code при реализации.**
- Изменяются только файлы из `AFFECTED FILES` спецификации задачи.
- Не меняется смысл выгрузок Excel и PDF.
- Не трогается `_perform_fuel_sync`.
- Схема БД не меняется — у UI-трека миграций быть не должно; если
  понадобится, это признак выхода за границы, и задача останавливается.
- Отдельное разрешение владельца требуется на: деплой, любое действие на
  production, добавление зависимости, изменение общего файла сверх
  объявленного, переименование сущностей.

Четыре правила, без которых структура протухнет:

1. **Числа не пишутся прозой** — только в `10-repo-inventory.json`, и он
   регенерируется скриптом. Расхождение прозы и json разрешается в пользу json

2. **Каждая фаза заканчивается файлом.** Решение, принятое в чате и не
   записанное, для следующей сессии не существует.
3. **`docs/tracks/ui.md` содержит одну актуальную строку состояния**, как
   `docs/STAGING.md` содержит одну строку занятости. Летопись — в git-истории.
4. **Все ссылки относительные внутри репозитория.** Ссылка на сообщение в
   чате нечитаема для новой сессии.

Отдельно: указатель в CLAUDE.md на `docs/AGENT_STATE.md` и `docs/TASKS.md`
устарел — файлы в `docs/archive/` (F23). Стоит поправить одной строкой, но
это правка общего файла и делается объявленно, не попутно.

## Self-review

- **Один основной workflow выбран?** Да: Claude Code cloud как PRIMARY, Desktop только под референсы, CLI на сервере только под релиз. Альтернативы названы как fallback с указанием ситуации.
- **Достаточно ли evidence до редизайна?** P1 не выпускает дальше без артефакта-доказательства на каждую запись регистра; P2 не выпускает референс без привязки к проблеме.
- **Production защищён?** Аудит не требует его вовсе; если потребуется — белый список без перехода по ссылкам, что строже стандартного «только GET» и обосновано F24.
- **Нет ли overengineering?** Отклонены Storybook, Percy, токен-тулинг, Lighthouse, полный Figma и все скиллы UI-генерации. Добавляются два python-скрипта stdlib и один Node-инструмент.
- **Пригодна ли дорожная карта для Claude Code?** Каждая задача — файл с 10 полями, включая защищённые зоны и откат; критерии выхода проверяются командой, не взглядом.
- **Восстановит ли новая сессия проект?** Точка входа `docs/tracks/ui.md`, числа регенерируются скриптом, решения в ADR, эталоны отрендерены.
- **Чего этот документ не знает.** Всё, что требует рендера: реальная плотность, наличие skeleton/empty/permission-состояний, поведение на промежуточных ширинах, фактическая читаемость. Помечено как ASSUMPTION и закрывается в P1 — это и есть его назначение.
