# Часть A. Подтверждающий прогон на staging

## A.1. Занять площадку — **сделано**

`docs/STAGING.md` — одна строка на весь проект: кто сейчас пользуется
staging. Чужой деплой посреди прогона обесценивает его целиком, и понять это
по кадрам нельзя.

Строка занятости уже стоит в этом же PR:

```
| да | UI | 2026-08-10 | подтверждающий прогон UI-P9 после мержа PR #58 |
```

То есть площадка считается занятой **с момента мержа PR**, а не с момента,
когда вы дойдёте до деплоя. Освобождается в A.5 — обратной правкой той же
строки.

## A.2. Выкатить `main` на staging

Порядок: остановить всё → бэкап → код → миграция → поднять. SQLite не терпит
двух писателей, а миграция на живой службе — это второй писатель.

```
Stop-Service TransportReportStaging
Stop-Service TransportBotStaging
Stop-Service TransportBot003Staging
Get-Service TransportReportStaging, TransportBotStaging, TransportBot003Staging | Format-Table Name, Status
```

Все три обязаны показать **`Stopped`** в выводе. «Команда прошла без ошибки»
— не то же самое.

```
cd C:\transport-report-staging
.\backup_staging_db.bat
```

В выводе проверить три вещи: `SUCCESS`, размер приёмника **равен** размеру
источника, `Integrity check : ok`. Размер сверять числом, а не на глаз.

```
cd C:\transport-report-staging
git fetch origin main
git merge --ff-only origin/main
git rev-parse --short HEAD
```

Ожидается **`c651202`** или новее. Хеш записать — его обязан назвать агент в
отчёте.

Миграция `DAILY_UNITS_001` на staging уже применена в прошлый раз, но
запустить всё равно нужно — оба раза:

```
cd C:\transport-report-staging
& "C:\Program Files\Python314\python.exe" migrate_daily_units_001.py
& "C:\Program Files\Python314\python.exe" migrate_daily_units_001.py
```

Оба запуска обязаны сказать **«Already applied. Nothing to do.»** — она уже
в реестре. Если первый запуск начал что-то делать, значит база на площадке
подменялась, и это разбирают до прогона.

```
Restart-Service TransportReportStaging
Restart-Service TransportBotStaging
Restart-Service TransportBot003Staging
Get-Service TransportReportStaging, TransportBotStaging, TransportBot003Staging | Format-Table Name, Status
```

`Restart-Service`, а не `Start-Service`: последний на уже работающей службе
молча ничего не делает. Все три обязаны показать **`Running`**.

Убедиться, что поднялось, **до** всякого агента:

```
Invoke-WebRequest -Uri http://10.103.25.14:5051/login -UseBasicParsing | Select-Object StatusCode
```

Ожидается `200`. Затем открыть браузером `http://10.103.25.14:5051/entry`:
открылся — миграция на месте.

# Часть C. Прод-деплой

Порядок шагов — `docs/RELEASE_AND_BACKUP_PROCEDURE.md`, он полный и
самодостаточный. Здесь только то, что добавляет к нему трек UI.

## C.1. В релиз едет не только UI

Шаг 1 процедуры требует прочитать **весь** вывод

```
git --no-pager log --oneline HEAD..origin/main
```

и назвать каждый трек, который в нём присутствует. Это не формальность:
`main` общая для четырёх треков, и с 2026-08-03 в неё, кроме UI, влит трек
дронов со **своими миграциями**. Прод-деплой повезёт их тоже.

## C.2. Предсказание дрейфа записывается ДО первого замера

Значимая величина одна — `file-but-not-registered`, ожидаемый переход
`0 -> N -> 0`, где **N — число миграций в этом релизе**.

N считается на самой машине, из вывода шага 1, а не берётся отсюда: сколько
из шести миграций, появившихся в `main` после снимка `292c53e`, уже стоят на
production, отсюда не видно.

```
git --no-pager log --oneline --diff-filter=A --name-only HEAD..origin/main -- migrate_*.py
```

Из них трека UI — ровно одна: **`migrate_daily_units_001.py`**. Остальные —
трека дронов; их наличие в релизе стоит согласовать с соседом до деплоя.

Прочие секции вывода (`resolved-by-backfill`, `registered-but-no-file`,
`unclassifiable`) и ожидаемый ненулевой код возврата описаны в процедуре,
шаг 6, вместе с записанным заранее предсказанием на первый релиз после
`0bbfcbf`. Отдельно стоит помнить: **отсутствие `SyntaxWarning` в первой
строке вывода** — самый быстрый признак, что отработал новый чекер.

## C.3. Миграция трека UI

Каждая миграция релиза запускается **дважды подряд**:

```
& "C:\Program Files\Python314\python.exe" migrate_daily_units_001.py
& "C:\Program Files\Python314\python.exe" migrate_daily_units_001.py
```

Первый запуск обязан отработать и записаться в реестр, второй — сказать
«Already applied. Nothing to do.» и не сделать ничего.

**Без этой миграции `/entry` упадёт** с «no such column»: `app.py:1030`
читает `DailyRecord.unit_code`, а `db.create_all()` колонок не добавляет
никогда — он создаст пустую таблицу `daily_record_units` и оставит
`daily_records` без колонки.
