# Метрики боевой базы — что они меняют в постановке задачи

Источник: `ux_metrics.json`, снят `tools/ux/collect_metrics.py` на production
2026-08-09. Только счётчики, частоты и длины строк; значений полей в файле нет
(колонки с признаками персональных данных пропущены по имени, см.
`excluded_columns_rule` внутри файла).

Период аудита: 2026-05-26 → 2026-08-09. 73 таблицы, 3436 записей аудита,
7 пользователей.

Маркировка: **FACT** — прямо из файла. **INFERENCE** — вывод. **ASSUMPTION** —
не проверено, нужен ответ владельца или проверка в P1.

---

## M1. Один экран несёт 83 % всей человеческой работы

**FACT.** Из 3436 записей аудита 1152 сделаны ролью `system` (синхронизация
Topaz, `fuel_topaz_sync_completed`). Остаётся **2284 действия человека**.
Из них `/entry/save` — **1896, то есть 83,0 %**. Всё остальное вместе — 388
действий за два с половиной месяца.

Разбивка остатка: `deficiencies` 79, `spare_parts` 71, фактические действия по
топливу 58 (1210 минус 1152 машинных), `admin` 24, `references` 13,
`wialon` 2. Аутентификация — 141.

**INFERENCE.** `daily_entry.html` — не «одна из страниц», а **та самая
страница**. И это же самый запущенный файл в репозитории: 46 КБ, 387 строк
собственного CSS и 337 строк собственного JS — больше, чем у любого другого
шаблона.

**Следствие для порядка работ.** Обычный редизайн начинают с дашборда, потому
что он представительный. Данные говорят обратное: дашборд смотрят, а работают
в форме. `daily_entry` должен быть первым canonical screen, а не четвёртым.
Правка §14 плана: порядок эталонных экранов меняется.

## M2. Два модуля не оставили ни одной записи аудита

**FACT.** В `by_module` присутствуют: `daily_entry`, `fuel`, `auth`,
`deficiencies`, `spare_parts`, `admin`, `references`, `wialon`.
**Отсутствуют полностью: `drones` и `work_orders`.**

При этом данные в них есть: `drone_flights` 31 059 строк, `drone_works` 904,
`drone_customers` 713, `drone_units` 15. `work_orders` — 3 строки, все в
статусе `done`.

**INFERENCE, требующая проверки в P1.** Два возможных объяснения, и они ведут
к разным решениям:
1. экраны дронов — read-only аналитика поверх импортируемых данных, действий
   пользователя на них по построению нет;
2. `log_audit()` в `drones.py` и `work_orders.py` просто не вызывается.

Отличить можно только чтением кода — проверяется в P1, до расстановки
приоритетов. **Не додумывать:** от ответа зависит, считать ли 22 шаблона
дронов активно используемыми или витриной.

## M3. Активность операторов упала более чем в сто раз

**FACT.** По `role_by_month`, роль `operator`:

| Месяц | Действий | В сутки |
|---|---|---|
| 2026-06 | 1629 | 54,3 |
| 2026-07 | 395 | 12,7 |
| 2026-08 (9 дней) | 4 | 0,44 |

Машинная синхронизация за те же месяцы держится ровно: 403 / 540 / 209.
То есть система работает — перестали работать люди.

**ASSUMPTION.** Причин может быть две: сезонность сельхозцикла либо отказ от
использования. Придумывать нельзя — **это вопрос владельцу**, и он влияет на
весь проект: если операторы перестали вводить данные из-за неудобства формы,
редизайн `daily_entry` — самое ценное, что можно сделать; если это сезон,
приоритет тот же, но срочность другая.

## M4. Справочник единиц измерения разрушен вводом произвольной строки

**FACT.** `daily_records.unit` содержит 15 различных написаний примерно шести
реальных единиц:

| Смысл | Написания в базе |
|---|---|
| гектар | `га` (4907), `Га` (211) |
| час | `соат` (832), `Соат` (630) |
| моточас | `м-соат` (734), `М-соат` (72), `Мотосоат` (47) |
| рейс | `Рейс` (381), `рейс` (42), `1 Рейс` (24), `Реййс` (1 — опечатка) |
| тонно-километр | `тн/км` (296), `тонна/км` (11) |
| километр | `км` (2) |
| — | пусто (15 630) |

Плюс **одно значение длиной 253 символа**: в поле единицы измерения записан
абзац инструкции («м-соат будем считать с 08:00–18:00. Порог потери сигнала
>2 часов…»). Отсюда `daily_records.unit`: avg 3,0 — max 253.

**INFERENCE.** Механизм ровно один: поле свободного ввода там, где нужен
контролируемый словарь. Последствие выходит за пределы оформления — любая
группировка по единице в отчёте разносит `га` и `Га` по разным строкам.

**Граница ответственности.** Задача UI — закрыть ввод произвольной строки.
Нормализация уже накопленных значений и решение, какие написания считать
одним, — **бизнес-правило, его определяет владелец**, а не редизайн.
В `spare_parts` контролируемый справочник уже есть (`spare_part_units.code`:
`dona`, `metr`, `kv_metr`) — образец внутри самого проекта.

## M5. Двуязычность держится на 6 % данных

**FACT.** `users.language`: `uz` — 5, `ru` — 2. Большинство работает
по-узбекски.
`spare_parts`: `name` заполнено у 250 позиций, `name_uz` — **у 14 (5,6 %)**.
`spare_parts.category` — пусто у всех 250.

**INFERENCE.** Пять из семи пользователей видят русские названия внутри
узбекского интерфейса. Это не дефект вёрстки, но именно на него ложится любая
работа с двуязычностью: переключатель языка исправно работает, а данных для
второго языка нет.

## M6. Узбекский длиннее русского на 19–47 % — числом

**FACT.** Пары полей одной сущности, средняя длина в символах:

| Таблица | `name_ru` | `name_uz` | Разница |
|---|---|---|---|
| `app_modules` | 18,9 (max 33) | 22,5 (max 38) | **+19 %** |
| `spare_part_categories` | 15,5 (max 25) | 16,4 (max 35) | **+6 %**, max +40 % |
| `spare_part_units` | 3,2 (max 8) | 4,7 (max 8) | **+47 %** |

**Следствие для дизайн-системы, пригодное к проверке.** Ширина колонок,
кнопок и пунктов навигации проектируется по узбекскому варианту, а
макет проверяется на нём же. Это измеримое правило вместо пожелания «учесть
двуязычность»: контрольный прогон baseline на `lang=uz` обязателен, а не
опционален.

## M7. Разброс объёмов — пять порядков, поэтому «таблица» не один компонент

**FACT.** Строк в таблицах, по убыванию:

| Таблица | Строк |
|---|---|
| `fuel_transactions2` | **394 817** |
| `drone_flights` | 31 059 |
| `daily_records` | 23 821 |
| `fuel_card_aliases` | 9 770 |
| `engine_hours_records` | 9 870 |
| `fuel_cards` | 4 885 |
| `fuel_sync_logs2` / `audit_logs` | 3 430 / 3 436 |
| `drone_works` | 904 |
| `equipment` | 336 |
| `spare_parts` | 250 |
| `work_orders` | **3** |

**INFERENCE.** Один компонент `vs-table` без объявленных режимов не покрывает
оба конца. 394 тысячи строк требуют серверной пагинации и ограничения
сортировки; три строки требуют осмысленного малого состояния. Спецификация
таблицы обязана назвать режимы и порог переключения, иначе разработчик каждый
раз решает заново — а это и есть механизм, породивший 15 одноразовых классов
таблиц.

## M9. Двенадцать таблиц пусты — пустое состояние здесь основное, а не крайнее

**FACT.** Ноль строк: `fuel_receipts`, `fuel_transactions` (легаси v1),
`fuel_tanks`, `fuel_counter_mismatches`, `fuel_warning_reviews`,
`spare_part_maintenance_norms`, `spare_part_min_levels`,
`spare_part_reservations`, `field_contours`, `drone_reattach_runs`,
`drone_work_imports`, `bot_notification_queue`.

**INFERENCE.** Часть — легаси-таблицы после миграции v1→v2 (`fuel_receipts`,
`fuel_transactions`), их экранов может не быть вовсе. Остальные — живые
функции, которыми пока не пользовались: минимальные остатки, резервы, нормы
ТО, ревью предупреждений.

**Следствие для аудита.** Экраны этих функций пользователь видит **только
пустыми**. Значит baseline обязан снять их пустыми, а пустое состояние —
проектироваться как полноценный экран (что это, почему пусто, что сделать),
а не как серая надпись «нет данных». В `design-system.css` секция
`12. EMPTY / PLACEHOLDER` существует — в P1 проверить, что именно она даёт.

**FACT.** Все значения, из которых строится набор статусных индикаторов:

| Сущность | Значения |
|---|---|
| `daily_records.status` | `working` (8275), `idle` (15546) |
| `spare_part_requests.status` | `draft`, `submitted` (3), `approved`, `issued` |
| `spare_part_inventory_movements.movement_type` | `receipt` (16), `issue`, `adjustment` |
| `work_orders.status` | `done` (3) |
| `drone_unit_status_log.status` | `serviceable` (9), `unserviceable` (6) |
| `drone_sync_logs.kind` | `backfill` (34), `incremental` (24) |
| `audit_logs.status` | `ok` (3392), `failed` (32), `blocked` (12) |
| `equipment.category` | `mtz`, `qatnov`, `yukori`, `combine`, `yuk_transport`, `special`, `mini`, `motorcycle`, `passenger` |
| `spare_part_categories.kind` | `unit` (11), `consumable` (2) |

**INFERENCE.** Всего различных статусных значений — порядка 25, и почти все

мал, поэтому тяжёлый компонент бейджа с фоном и рамкой не окупается — хватает
точки с цветом и подписи (см. `docs/ux/21-reference-analysis.md`, ADOPT-2).

Отдельно: `equipment.category` смешивает английские и узбекские коды в одном
словаре (`combine`, `motorcycle`, `passenger` рядом с `qatnov`, `yukori`,
`yuk_transport`). Для UI это означает, что подписи категорий берутся не из
кода, а из перевода — проверить в P1.

## Что из этого меняет план Phase 0

1. **Порядок canonical screens меняется** (M1): `daily_entry` становится
   первым, дашборд — не первым.
2. **Появляется обязательный прогон на `lang=uz`** (M6) — не подмножество,
   а полноценная ветка проверки ширин.
3. **Контракт таблицы обязан объявить режимы по объёму** (M7) и поведение
   переполнения по p99/max (M8).
4. **Пустые состояния переходят из «состояний» в «основной сценарий»** для
   двенадцати экранов (M9).
5. **Два вопроса владельцу**, без ответов на которые приоритеты нельзя
   расставить честно: причина спада активности (M3) и статус модулей дронов
   и нарядов (M2, часть проверяется кодом).
