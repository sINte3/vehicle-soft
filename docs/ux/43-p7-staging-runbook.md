## Шаг 1. Занять площадку

**Что это значит.** `docs/STAGING.md` — одна строка на весь проект: кто
сейчас пользуется staging. Треки друг друга не видят, а чужой деплой и
рестарт службы посреди прогона обесценивают его целиком: половина кадров
снята с одним кодом, половина с другим, и понять это по кадрам нельзя.
Занять площадку — значит **заменить строку целиком** (не дописать вторую) и
закоммитить её отдельным коммитом, чтобы соседний трек увидел занятость до
того, как начнёт деплой.

В файле сейчас:

```
| Занято | Трек | С какого числа | Под что |
|---|---|---|---|
| нет | — | — | свободна после приёмки `DRONE-CLOSE-001` |
```

Заменить последнюю строку на:

```
| да | UI | 2026-08-10 | валидация P7 трека UI после мержа PR #55 |
```

и закоммитить **только этот файл**:

```
git add docs/STAGING.md
git commit -m "staging: площадку занимает трек UI под валидацию P7"
git push
```

Освобождая после прогона — вернуть `| нет | — | — | свободна после валидации P7 трека UI |`
тем же способом, отдельным коммитом.

## Шаг 2. Выкатить `main` на staging

Порядок как в `RELEASE_AND_BACKUP_PROCEDURE.md`: остановить всё → бэкап →
код → миграция → поднять. Пропуск порядка опасен не теоретически: SQLite не
терпит двух писателей, а миграция на живой службе — это второй писатель.

**2.1. Остановить все три службы.** Одна остановленная из трёх ничего не
даёт: у всех трёх `AppDirectory` — один каталог и одна база.

```
Stop-Service TransportReportStaging
Stop-Service TransportBotStaging
Stop-Service TransportBot003Staging
Get-Service TransportReportStaging, TransportBotStaging, TransportBot003Staging | Format-Table Name, Status
```

Все три обязаны показать **`Stopped`** в выводе. «Команда прошла без ошибки»
— не то же самое.

**2.2. Бэкап на остановленной базе.** В репозитории есть готовая обёртка
именно под staging — она сама подставляет источник и приёмник:

```
cd C:\transport-report-staging
.\backup_staging_db.bat
```

В выводе проверить три вещи: `SUCCESS`, размер приёмника **равен** размеру
источника, `Integrity check : ok`. Размер сверять числом, а не на глаз.

**2.3. Забрать код.**

```
cd C:\transport-report-staging
git fetch origin main
git merge --ff-only origin/main
git rev-parse --short HEAD
```

`--ff-only` намеренно: если слияние не перемотка, история разошлась, и это
надо разбирать, а не продавливать. **Короткий хеш из последней команды
запишите — его обязан назвать Codex в отчёте.** Ожидается `6c48e0d` или
новее.

**2.4. Миграция `DAILY_UNITS_001` — дважды подряд.**

```
cd C:\transport-report-staging
& "C:\Program Files\Python314\python.exe" migrate_daily_units_001.py
& "C:\Program Files\Python314\python.exe" migrate_daily_units_001.py
```

Первый запуск обязан отработать и записаться в реестр. **Второй обязан
сказать «Already applied. Nothing to do.» и не сделать ничего** — это и есть
проверка идемпотентности, а не формальность.

**Без этого шага экран `/entry` упадёт** с «no such column»: `app.py:1030`
читает `DailyRecord.unit_code`, а `db.create_all()` колонок не добавляет
никогда — он создаст пустую таблицу `daily_record_units` и оставит
`daily_records` без колонки.

**2.5. Поднять службы.**

```
Restart-Service TransportReportStaging
Restart-Service TransportBotStaging
Restart-Service TransportBot003Staging
Get-Service TransportReportStaging, TransportBotStaging, TransportBot003Staging | Format-Table Name, Status
```

`Restart-Service`, а не `Start-Service`: последний на уже работающей службе
молча ничего не делает. Все три обязаны показать **`Running`**.

**2.6. Убедиться, что поднялось, до всякого агента.**

```
Invoke-WebRequest -Uri http://10.103.25.14:5051/login -UseBasicParsing | Select-Object StatusCode
```

Ожидается `200`. Затем открыть браузером `http://10.103.25.14:5051/entry`
и войти: если `/entry` открылся — миграция применилась. Если «no such
column» — вернуться к 2.4.

## Шаг 3. Подготовить учётные записи для агента

Агенту нужны **две** учётные записи staging: одна с языком интерфейса
**русский**, одна с **узбекским**. Это не удобство, а условие проверки:
**язык берётся из учётной записи, а не из адреса**, и прогон «на узбекском»
через параметр в URL снимется по-русски, ничего об этом не сказав.

Проверить, что пара есть, можно на самой площадке: `/admin/users`, колонка
языка. Если пары нет — либо завести, либо честно сказать агенту, что языка
два не будет: тогда он проверит один и **напишет, что второй не проверялся**,
а не выдаст одинаковые кадры за двуязычие.

## Шаг 4. Запустить Codex

Агент должен работать **на сервере** (или на машине внутри той же сети) —
адрес `10.103.25.14:5051` из внешних сред недостижим.

**Каталог запуска:** `C:\transport-report-staging` — там лежит и код, и
`docs/ux/11-baseline/routes.json`, из которого агент берёт список адресов.

**Что дать агенту.** Ровно один файл — `docs/ux/42-p7-staging-prompt.md`,
раздел «2. Промт для Codex». Плюс три вещи, которых в файле нет и быть не
может:

1. короткий хеш из шага 2.3;
2. логины двух учётных записей и пароли к ним (в чат агента, не в репозиторий);
3. что миграция применена и `/entry` открывается — иначе агент решит, что
   поломка `/entry` относится к треку.

**Если Codex CLI:**

```
cd C:\transport-report-staging
codex
```

и первым сообщением:

> Прочитай `docs/ux/42-p7-staging-prompt.md` и выполни задание из раздела
> «2. Промт для Codex» целиком. Площадка развёрнута на коммите `<хеш из 2.3>`,
> миграция `DAILY_UNITS_001` применена, `/entry` открывается. Учётные записи:
> `<логин_ru>` (русский) и `<логин_uz>` (узбекский), пароль `<...>`.
> Ничего в базе не меняй, по ссылкам не ходи, код не правь.

**Если Codex в браузере или в IDE** и файлы репозитория ему не видны —
вставьте текст раздела «2. Промт для Codex» целиком как сообщение и добавьте
те же три уточнения. Промт написан так, чтобы работать без остального
репозитория, кроме `routes.json`; если и его не видно, агент обязан сказать
об этом и остановиться, а не выдумывать список адресов.

**Сколько ждать.** Четыре вьюпорта × 80 адресов × две учётные записи — это
порядка часа. Если агент возвращается через пять минут с «всё хорошо» —
он что-то пропустил, и первое, что надо спросить: сколько адресов он открыл
и сколько кадров снял.

   закрыт для всего проекта.

## Чего не делать

- **Не деплоить на production.** Гейт закрыт, и закрыт он именно этим треком.
- **Не запускать миграцию на работающей службе.** Второй писатель в SQLite —
  это повреждение базы, а не ошибка запуска.
- **Не давать агенту права менять данные.** Площадка держит копию боевой
  базы; правило режима `remote` — только `goto` по списку, никаких кликов по
  действиям, никаких отправок форм, никаких переходов по ссылкам.
- **Не принимать отчёт без хеша коммита.** Без него неизвестно, что снималось.
