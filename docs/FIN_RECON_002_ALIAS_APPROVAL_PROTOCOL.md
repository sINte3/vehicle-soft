# FIN-RECON-002 · Протокол утверждения заказчиков перед загрузкой книг

**Зачем.** Импорт книг сам заводит карточку на каждое незнакомое написание заказчика, всегда с типом `external` (`tools/import_drone_works.py`, `apply_rows`). Для июньских книг Ғиждувона и Шофиркона это до 66 новых карточек: среди них 8 похожих на подразделения холдинга и около 18 похожих на уже существующие. Протокол делает так, чтобы **каждая карточка и каждый алиас появились только по решению владельца**, механически и воспроизводимо, а импорт после этого не создавал ничего сам.

**Инструменты (ветка FIN-RECON-002):**
- `tools/drone_import_alias_candidates.py` — строит таблицу из собственного разбора импортёра;
- `tools/drone_alias_decisions.py` — проверяет и применяет утверждённую таблицу;
- `tools/fin_recon_002_staging_check.py --decisions` — репетиция всего окна.

## 1. Таблица решений

**Файл** `NEW_CUSTOMER_DECISIONS.csv`: UTF-8 с BOM, разделитель `;`. Его пишет `drone_import_alias_candidates.py` на **изолированной копии** полного бэкапа. Строки — ровно те написания, для которых импорт завёл бы карточку.

| Колонка | Кто заполняет | Смысл |
|---|---|---|
| `normalized_key` | инструмент | машинный ключ = `customer_key()` импортёра: регистр и пробелы свёрнуты, в одну строку. **Не править** |
| `new_card_name_as_imported` | инструмент | написание, как его сохранит импорт; перенос строки показан « ↵ » |
| `rows`, `area_ha`, `amount`, `tariffs`, `payment_types`, `source_sheets` | инструмент | что стоит за написанием |
| `holding_markers`, `hint`, `nearest_1..3` | инструмент | **подсказки**: признаки подразделения холдинга и три ближайшие карточки по сходству строк. Сходство не доказывает, что это тот же заказчик |
| `DECISION` | **владелец** | `ALIAS`, `NEW`, `HOLD` или `SET_TYPE` |
| `TARGET_CARD_ID` | **владелец** | id существующей карточки — для `ALIAS` и `SET_TYPE` |
| `NEW_CARD_TYPE` | **владелец** | `external` или `internal` — для `NEW` и `SET_TYPE` |
| `NOTE` | владелец | свободный комментарий, инструмент его не читает |

## 2. Допустимые решения

| `DECISION` | `TARGET_CARD_ID` | `NEW_CARD_TYPE` | Что произойдёт |
|---|---|---|---|
| `ALIAS` | id карточки | пусто | написание станет алиасом этой карточки; строки книги лягут на неё |
| `NEW` | пусто | `external` / `internal` | новая карточка с этим названием и типом плюс алиас на неё |
| `HOLD` | пусто | пусто | не решено. **Запись всей таблицы отклоняется, импорт книг заблокирован** |
| `SET_TYPE` | id карточки | `external` / `internal` | у **существующей** карточки меняется только `customer_type`. `normalized_key` пустой; в `new_card_name_as_imported` — текущее имя карточки как защита. Строку дописывают в конец таблицы |

**Тип `internal`** означает «подразделение холдинга, платит Агрокластеру по справке». На суммы к получению он не влияет: аудит `docs/FIN_RECON_002_FINANCE_RULE_AUDIT.md`, тест `tests/test_drone_internal_services_receivable.py`.

## 3. Матрица конфликтов (любая строка → вся таблица отклонена, код 1, ничего не записано)

| Код | Когда |
|---|---|
| `E_COLUMNS` | нет обязательной колонки |
| `E_DECISION` | значение `DECISION` не из списка |
| `E_DUP_KEY` | одно написание решено дважды или одна карточка переведена дважды |
| `E_KEY_NOT_NORMAL` | `normalized_key` не в нормальной форме импортёра (ключ правили руками) |
| `E_KEY_UNKNOWN` | импорт не завёл бы такое написание: оно уже алиас или его нет в книгах |
| `E_KEY_MISSING` | импорт завёл бы написание, которого нет в таблице |
| `E_ALIAS_TAKEN` | написание уже алиас какой-то карточки (появилось после построения таблицы) |
| `E_TARGET_ID_FORMAT` | `TARGET_CARD_ID` — не число |
| `E_TARGET_MISSING` | карточки с таким id нет |
| `E_TARGET_INACTIVE` | `ALIAS` на выключенную карточку |
| `E_TYPE` | `NEW` или `SET_TYPE` без типа `external` / `internal` |
| `E_EXTRA_FIELDS` | лишнее поле: например, у `ALIAS` указан тип или у `NEW` — id |
| `E_NEW_NAME_TAKEN` | `NEW`, но карточка с таким же названием уже есть — решить `ALIAS` |
| `E_SET_TYPE_KEY` | у `SET_TYPE` заполнен `normalized_key` |
| `E_SET_TYPE_GUARD` | имя карточки не совпадает с указанным (её переименовали после таблицы) |
| `HOLD` | при `--apply`: есть нерешённые написания |

## 4. Что проверяется после изменения (dry run — на копии в памяти, `--apply` — внутри транзакции записи)

1. `drone_works` побайтно прежняя: протокол работ не трогает.
2. Карточки, которые были, побайтно прежние; у карточек `SET_TYPE` меняется только `customer_type`.
3. Алиасы, которые были, побайтно прежние.
4. Новых карточек ровно столько, сколько `NEW`; новых алиасов — `NEW + ALIAS`.
5. **Импортёр, запущенный заново против изменённой базы**:
   - читает те же строки, гектары и деньги;
   - не создаёт ни одной карточки, кроме `HOLD`;
   - каждую строку кладёт ровно туда, куда решено: `ALIAS` — на указанную карточку, `NEW` — на новую, ранее сопоставленные строки — туда же, где были.

`--apply` выполняется одной транзакцией `BEGIN IMMEDIATE`:
- повторная проверка таблицы под блокировкой;
- изменения;
- постусловия;
- строка `schema_migrations` `DRONE_ALIAS_DECISIONS_<первые 16 hex SHA-256 таблицы>`;
- один `COMMIT`.

**Квитанция** двухфазная: `<receipt>.pending` до `COMMIT`, `<receipt>` и **контрольный дифф** `<receipt>.diff.csv` после. Дифф содержит действие, id карточки, имя, ключ и тип до/после. Повтор той же таблицы — `ALREADY APPLIED`. Прерванный запуск дописывается или откладывается повтором с той же `--receipt`.

## 5. Порядок (всё до окна записи — только на изолированных копиях)

1. Владелец снимает свежий бэкап; на сервере — копия ветки, как в репетиции.
2. Таблица на полном справочнике. Сначала последний бэкап, затем репетиция (команды — каждая одной строкой):
   ```powershell
   $backup = Get-ChildItem D:\transport-report-backups\production\daily\*.db | Sort-Object LastWriteTime -Descending | Select-Object -First 1
   ```
   ```powershell
   & "C:\Program Files\Python314\python.exe" .\tools\fin_recon_002_staging_check.py --backup $backup.FullName --books C:\VehicleSoft_Release\FIN_RECON_002_BOOKS --work C:\VehicleSoft_Release\FIN_RECON_002_REHEARSAL_TABLE
   ```
   Таблица появится в `C:\VehicleSoft_Release\FIN_RECON_002_REHEARSAL_TABLE\alias_decisions\NEW_CUSTOMER_DECISIONS.csv`.
3. Владелец заполняет `DECISION`, `TARGET_CARD_ID`, `NEW_CARD_TYPE`. Только он: автоматического выбора по сходству нет. Сохраняет как `C:\VehicleSoft_Release\FIN_RECON_002_DECISIONS.csv`.
4. Сухой прогон таблицы на копии (команда — одной строкой):
   ```powershell
   & "C:\Program Files\Python314\python.exe" .\tools\fin_recon_002_staging_check.py --backup $backup.FullName --books C:\VehicleSoft_Release\FIN_RECON_002_BOOKS --work C:\VehicleSoft_Release\FIN_RECON_002_REHEARSAL_DECISIONS --decisions C:\VehicleSoft_Release\FIN_RECON_002_DECISIONS.csv
   ```
   **Ожидание:**
   - `RESULT: PASS`;
   - строки «decision table dry run: OK, no HOLD» и «after the decision table the import creates no card of its own (got 0.0)»;
   - `decisions_receipt.json.diff.csv` — то, что будет сделано на production.
5. Окно записи (только по отдельному разрешению): миграция привязок → `tools/drone_alias_decisions.py --apply --receipt …` по той же таблице → загрузка двух книг через экран. Порядок и команды — в ранбуке окна.
6. Копии баз из папок репетиции после чтения отчётов удалить.

## 6. Чего протокол не делает

- **Не перепривязывает уже сохранённые работы.** Алиас действует только на новый импорт: импорт пропускает строки, которые уже есть. Если проверка 11 работ, автоматически привязанных к карточке 589, покажет другого юридического заказчика, нужна адресная миграция по образцу `migrate_drones_works_merged_customer_link_001.py`.
- **Не выбирает карточку по сходству.** Подсказки `nearest_*` только для владельца. Тест `test_a_similar_spelling_is_never_linked_to_the_similar_card_by_itself`.
- Не меняет суммы, тарифы, поступления, тип оплаты, май и остальные месяцы.
- Не трогает 598,11 га строк «только в своде»: они в импорт не входят.
