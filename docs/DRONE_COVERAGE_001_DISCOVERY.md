# DRONE-COVERAGE-001 — исследование источников данных

Написано 2026-08-25 по техзаданию владельца. Отвечает на разделы 3–7 и 23 ТЗ:
что на самом деле собирает `drone_collector`, что лежит в бинарном ответе DJI,
можно ли связать маршрут с вылетом, откуда взять полигон поля и чего в данных
нет.

**Правило этого документа.** Каждое утверждение помечено одним из четырёх
слов: **подтверждено** (проверено на данных, названа проверка),
**предположительно** (согласуется с данными, но различить альтернативу нечем),
**не найдено** (искали, нет), **невозможно проверить отсюда** (нужен доступ,
которого у сессии нет). Ничего не помечено «очевидно».

Всё воспроизводится двумя командами без сети, браузера и базы:

```
python tools/drone_route_probe.py --capture <ваш снимок>.json
python -m unittest drone_collector.tests.test_route_decode -v
```

## 0. Главное в семи строках

1. Бинарный ответ разобран. Это protobuf wire format, схема не нужна: **все 16
   именованных полей сверены с JSON-ответами того же кабинета и совпали 9 из 9**.
2. **Связь маршрута с вылетом однозначна и не требует угадывания:** поле 2
   записи маршрута — это `dji_flight_id`. Порядок не используется вовсе.
3. **Точка маршрута — это ровно две координаты.** Ни времени, ни высоты, ни
   скорости, ни состояния насоса. Все 961 точки выборки. Отсюда: «подтверждённое
   опрыскивание» из этого источника построить **нельзя**.
4. **Ширина захвата есть у вылета** (`spray_width`), и у двух вылетов из девяти
   её нет — DJI ставит `-1`. Подставлять туда значение нельзя.
5. Геометрическое объединение маршрутов **семи вылетов с известной шириной** —
   **7.4408 га** против **7.7678 га**, которые DJI даёт **этим же семи**.
   Отношение **1.044**. Сравнивать с 8.6911 га (девять вылетов) нельзя: см. §6.0,
   первая редакция этого документа именно так и ошиблась.
6. Два вылета без ширины (0.9233 га у DJI) проходят почти целиком по уже
   накрытой земле: у 622715275 вне полосы семи остаётся **0.4 метра из 108**.
   Он же — запись, которой не соответствует её маршрут: 40 секунд, 13 точек и
   0.594 га, в точности повторяющие площадь предыдущего вылета.
7. **В приложенном «безопасном» файле остались живые подписанные ссылки.** См.
   §8 — это единственный пункт, требующий действия сегодня.

## 1. Что делает текущий collector — проверено по исходникам

Утверждения §3 ТЗ проверены на HEAD ветки. Все верны, с двумя уточнениями.

**Подтверждено.** `drone_collector/browser.py` слушает ответы браузера и берёт
только список вылетов: `is_flight_list_url()` требует подстроку
`/flight_records?` и **отвергает** всё, где есть `/flight_records/`
(`browser.py:268`). Карточка отдельного вылета намеренно игнорируется и
считается отдельным счётчиком `_ignored_detail` (`browser.py:581`).

**Подтверждено.** Хранится полный ответ: `DroneFlight.raw_json` —
`nullable=False`, кладётся весь payload (`models.py:1887`). Производные колонки
пересчитываются из него, пересбор для этого не нужен.

**Уточнение 1 к ТЗ.** Одной координаты `lat`/`lng` в модели не «одна» — их две
колонки, и обе есть в списке. Но это **точка взлёта**, а не поле: измерено на
сентябре-2025, доля различных координат внутри группы «день × машина» 0.15
(`docs/tracks/drones.md`, §3). Для покрытия она бесполезна, для сшивки с полем —
тоже.

**Уточнение 2 к ТЗ, важное.** ТЗ перечисляет среди собираемого `manual_mode`,
`mode_name`, `work_speed`, `spray_width`, `radar_height` — это верно. Но
**`hardware_id` в списке НЕТ**: сверено по фактическому ответу списка из
приложенного снимка (35 ключей строки, `hardware_id` среди них отсутствует).
Он есть только в карточке отдельного вылета — и, как выяснилось ниже, **в
бинарном ответе маршрутов**. Это тот самый `Body Code`, из-за отсутствия
которого трек не смог разложить октябрь-2025 по бортам (`DRONE-BODYCODE-001`).

**Подтверждено.** Не собирается ничего из перечисленного в §3 ТЗ как
отсутствующее: последовательности GPS-точек, геометрии маршрута, времени точки,
состояния распыления и насоса, событий RTH/паузы/возобновления.

**Подтверждено.** Сбор контуров (`drone_collector/lands.py`) получает список
полей через `POST /ag-plot/api/graphql?name=lands`, а приёмник
`/drones/api/land_sync` вырезает подписанную ссылку перед записью:
`DRONE_LAND_VOLATILE_KEYS = ('signedURL',)` и `_drone_land_strip_volatile()`
(`drones.py:741,776`). Полигон не скачивается. `contentMd5` при этом
**сохраняется** внутри `raw_json` — то есть материал для обнаружения изменений
геометрии в базе уже есть, хотя отдельной колонки под него нет.

## 2. Бинарный ответ: формат (§5.1 ТЗ)

**Подтверждено: это настоящий protobuf wire format.** Не «похоже на». Тело
разобрано побайтно генерическим обходчиком, который знает только правила
кодирования и ничего не знает о схеме: 21 294 байта прочитаны без остатка,
без единого неизвестного типа провода, без переполнения длин. Реализация —
`drone_collector/route_decode.py`, функция `walk()`.

Структура:

```
1  varint   status            = 200
2  bytes    message           = "Success."        <- с точкой; у JSON-ответов "OK"
3  bytes    payload
     1  bytes  route          <- повторяется, ОДИН РАЗ НА ВЫЛЕТ
```

**Схема в JavaScript-бандле DJI не искалась и найдена быть не могла** — у
сессии нет доступа к сайту (см. §9). Но она и **не нужна**: имя message-типа
ничего не добавляет к тому, что уже доказано сверкой значений, а wire format
самодостаточен для чтения. Вывод §5.1 ТЗ «либо схема, либо ограниченный
декодер с жёсткой валидацией» разрешается в пользу второго, и не по бедности:
декодер, отказывающий на непонятной структуре, надёжнее сгенерированного,
который молча стерпит смену семантики поля при неизменном типе.

**Опровергнуто как метод.** ТЗ предупреждает не делать вывод по тому, что
первые два поля похожи на `status`/`Success`. Правильно: вывод сделан не по
ним. Он сделан по совпадению **шестнадцати** полей с независимым источником —
JSON-карточками тех же девяти вылетов.

### Чего в ответе нет — и это главный результат

| Что искали | Результат |
|---|---|
| время каждой точки | **не найдено** |
| высота, скорость, курс | **не найдено** |
| состояние распыления | **не найдено** |
| состояние насоса, клапанов | **не найдено** |
| расход | **не найдено** |
| события RTH, паузы, возобновления, возврата после дозаправки | **не найдено** |
| идентификатор дрона | **найден** — `hardware_id`, поле 9 |
| идентификатор вылета | **найден** — поле 2 |
| номер задания | **предположительно** — поле 14 |
| ширина обработки | **найдена** — поле 26, у 7 из 9 |

Проверка «точка — это ровно две координаты» не рассуждение, а перебор: каждая
из 961 точек разобрана отдельно, и любая, где полей не два или тип не
`fixed64`, обрывает разбор с ошибкой. Это же поведение закреплено тестом
`test_a_point_with_a_third_field_is_refused`: если DJI когда-нибудь добавит в
точку третье поле, декодер **откажет**, а не промолчит, и вывод «только
позиция» будет пересмотрен сознательно.

**Следствие для §10.3 ТЗ.** Показатель `Confirmed spraying area` из этого
источника создать нельзя. Разрешённые формулировки — «геометрическое
покрытие», «рабочий кандидат», «маршрут внутри поля».

## 4. Связь маршрута с вылетом (§5.3 ТЗ)

**Связь однозначна, детерминирована и не опирается на порядок.**

* Поле 2 каждой записи — `dji_flight_id`. Девять записей дали девять id, в
  точности те же, что вернул `/flight_records/only_all_ids` и что стоят на
  девяти карточках.
* Возвращаются маршруты **всех вылетов выборки**, не одного.
* Порядок ответа — по времени начала по возрастанию. Это видно на данных:
  `only_all_ids` в первом вызове снимка вернул id в **несортированном** порядке,
  а ответ маршрутов пришёл байт в байт таким же, как после двух других
  вызовов, где порядок был убывающим. То есть сервер сортирует сам, и **связь
  по порядковому номеру была бы случайно верной и потому особенно опасной**.
  Она не используется.

Что содержит тело POST-запроса — **невозможно проверить отсюда**: очистка
снимка удалила тела запросов. Но это и не нужно для связи: id приходит в
ответе. Для планирования сбора знать состав запроса всё же полезно — вопрос
вынесен в §9, В1.

**Правило, которое отсюда следует.** Маршрут без поля 2 или с id, которого нет
в `drone_flights`, идёт в карантин `UNLINKED`. Угадывание запрещено и не
понадобится ни разу, пока DJI не уберёт поле 2.

## 5. Повторные ответы (§5.4 ТЗ)

**Причина установлена.** Три тела **байт в байт одинаковы**: sha256
`c505e688b9c0a00e…`, 21 294 байта каждое. Порядок событий в снимке:

```
09:53:00.970  GET  only_all_ids          -> 9 id, порядок несортированный
09:53:01.697  POST flight_datas/…        -> маршруты
09:53:07.608  GET  only_all_ids          -> те же 9 id, порядок убывающий
09:53:08.349  POST flight_datas/…        -> те же байты
09:53:17.587  GET  only_all_ids          -> те же 9 id
09:53:18.292  POST flight_datas/…        -> те же байты
```

Каждому POST предшествует свой `only_all_ids`, и между ними лежат вызовы
`lands` с **разным** составом полей (2, 6, 2 контура). Это перерисовка карты:
пользователь менял вид, и клиент каждый раз заново запрашивал и список id, и
маршруты, и поля в новой рамке. Не «повторный запрос одного слоя», а полный
повтор цепочки.

**Дедупликация.** Ключ — sha256 сырого тела вместе с контекстом запроса
(набор id и период). Хеш уже реализован в `tools/drone_route_probe.py`
(`dedupe()`), проверен тестами в обе стороны: одинаковые тела схлопываются со
счётчиком, тело, отличающееся одним байтом, — нет.

## 6. Геометрия и площадь: что посчиталось на спорном дне

### 6.0 Исправление первой редакции, 2026-08-25

**В первой редакции этого раздела геометрический расчёт опирался на
подставленную ширину, и полученное отношение неверно.** Ошибку нашёл владелец.
Здесь она названа полностью, потому что исправленное число заметно меньше и
меняет вывод.

**Что именно было сделано неправильно — точная формулировка.** Обе стороны
сравнения содержали **одни и те же девять `dji_flight_id`**. Разными выборками
они не были. Дефект в другом: двум вылетам, у которых DJI ширину не записал
(`spray_width` = `-1`), **в геометрическом расчёте подставлялась ширина
5.95 м** — соседнее значение того же дня. Ровно эта подстановка запрещена §9 и
§4.2 архитектуры того же комплекта документов: документ противоречил
собственному правилу, а заглавное число было получено способом, который он же
и запрещает.

Исправленный расчёт **исключает эти два вылета из обеих сторон** и сравнивает
семь вылетов с известной шириной.

| | Первая редакция | Исправлено |
|---|---:|---:|
| Вылетов в геометрии | 9, **двум ширина подставлена (5.95 м)** | **7**, все с записанной шириной |
| Вылетов в площади DJI | 9, те же id | **7**, те же id |
| Геометрическое объединение | 7.4630 га | **7.4408 га** |
| Площадь DJI для сравнения | 8.6911 га | **7.7678 га** |
| **Отношение DJI / геометрия** | **1.165** | **1.044** |

Почему подстановка так сильно сместила результат: два вылета, у которых ширины
нет, добавляли к площади DJI **0.9233 га**, а к объединению — всего
**0.0222 га**. Их маршруты идут по уже накрытой земле, и новой площади они
почти не дают. Отношение росло не потому, что DJI завышает, а потому, что в
знаменателе стояла величина, посчитанная по выдуманной ширине.

**Что из-за этого отменяется.** Вывод «измеренные 1.165 попадают в порядок
1/(1−p) при перекрытии 15–25 %» **снят целиком**. Он был неверен дважды: число
неверно, и даже верное число так читать нельзя (§6.3).

### 6.1 Числа

Считалось так: точки → плоские метры (равнопромежуточная проекция вокруг
центра трека; на 400 метрах ошибка меньше метра) → буфер вокруг ломаной
радиусом `spray_width / 2`, торцы и стыки плоские → объединение буферов.
Библиотека — Shapely 2.1.2 (та же версия, что уже закреплена в
`gps/requirements.txt`).

**Когорта сравнения — семь вылетов, у которых DJI записал `spray_width`.**
Вылеты 622715274 и 622715275 исключены из ОБЕИХ сторон сравнения, а не из
одной.

| Величина | Значение |
|---|---:|
| Площадь DJI, **семь** вылетов когорты | **7.7678 га** |
| **Геометрическое объединение маршрутов этих же семи** | **7.4408 га** |
| Сумма буферов семи без объединения | 9.5829 га |
| Снято объединением | 2.1422 га |
| **Отношение DJI / геометрия, одна когорта** | **1.044** |

Справочно, вне сравнения — величины по всем девяти вылетам и по контуру:

| Величина | Значение |
|---|---:|
| Площадь DJI за день, девять вылетов | 8.6911 га |
| Плитка кабинета DJI за тот же день | 8.6913 га |
| Площадь DJI двух вылетов без ширины | 0.9233 га |
| Площадь контура `Karvon` P03335975 по справочнику DJI | 7.0437 га |

С контуром эти числа **сопоставимы лишь условно**: контур — это граница поля,
а не мера работы, и вылетов в нём не семь и не девять. Отношения «к контуру»
первая редакция приводила как измерение; здесь они не приводятся вовсе.

**Что именно посчитано под словом «геометрия».** Буферизована **вся ломаная
каждого вылета целиком**, включая подлёт к полю, возврат и развороты. Ни один
сегмент не исключён — исключать нечем, состояния насоса в данных нет (§3).
Поэтому 7.4408 га — это **верхняя оценка накрытой земли**, а не обработанная
площадь.

Насколько велика эта надбавка, **из данных не следует**: состояния насоса в
маршруте нет, и какие сегменты были холостыми — неизвестно. Оценить порядок
можно только **условно, приняв рабочую гипотезу** о том, как DJI считает
площадь (§6.3):

> *Если* верно, что `new_work_area` = длина пути, учтённой DJI как рабочая, ×
> заданный захват, *то* площади DJI хватает 13 062 м пути при суммарной длине
> семи ломаных 16 847 м, и оставшиеся 3 785 м (22 %) — это путь, который в
> площадь DJI не вошёл, а в нашу полосу вошёл.

Оба числа измерены, а вот их истолкование держится целиком на гипотезе. **Мы
не утверждаем, что 22 % пути пройдены с выключенным насосом** — это следствие
гипотезы, а не наблюдение. Опровергнуть или подтвердить его нечем: признака
насоса в источнике нет.

**Поле опознано предположительно, и сильнее сказать нельзя.** 99.3 % полосы
семи вылетов лежит в **рамке** контура `Karvon` `P03335975`, и рамка трека
(40.0807–40.0841 с. ш., 64.6288–64.6329 в. д.) практически совпадает с ней.

Но рамка — не поле. Рамка `Karvon` занимает 13.501 га при контуре в 7.044 га,
то есть вдвое больше; на `Karvon 2` полоса набирает 12.9 %, на `Karvon 1` —
1.7 %, **и обе цифры объясняются тем, что рамки этих контуров перекрываются с
рамкой `Karvon`**. Разделить их без полигонов нечем: тест «точка в рамке» не
умеет отличить соседнее поле от своего там, где рамки налезают друг на друга.

Поэтому:

* **гипотеза (не вывод):** работа шла на `Karvon` `P03335975`, на `Karvon 2`
  работы не было. Версия операторов ей не противоречит;
* **проверяется** пересечением полосы с настоящими полигонами — вопрос В2;
* до этого «внутри контура» и «вне контура» не считаются и на экране не
  показываются.

Ещё одно косвенное соображение в пользу гипотезы, тоже не доказательство: вне
рамки `Karvon` лежит 0.0541 га полосы, 0.7 %. Слабость его в том же — рамка
вдвое больше контура, и «внутри рамки» почти ничего не запрещает.

Заодно подтверждена и арифметика справочника: `totalArea` = 105.655 му,
делённое на 15, даёт ровно 7.0437 га — то самое «7.04», которое операторы
приняли за часть имени контура (`docs/DRONES_AREA_DISPUTE.md`, §2).

### 6.2 Найденная аномалия

Оба вылета, исключённые из когорты, летали по уже накрытой земле. Это
измеряется **без всякой ширины** — как доля длины их пути, лежащая вне полосы
семи вылетов:

| Вылет | Длина пути | Вне полосы семи |
|---|---:|---:|
| 622715274 (ручной) | 444.9 м | 19.6 м (4 %) |
| 622715275 | 107.7 м | **0.4 м (0 %)** |

DJI при этом даёт им 0.9233 га. Дальше — про второй из них отдельно, потому
что там расхождение другого рода.

**0.594 га приходятся на запись, которой её маршрут не соответствует.**

| Вылет | Точек | Длина пути | Площадь DJI | Ширина | Требуемый захват |
|---|---:|---:|---:|---:|---:|
| 622715273 | 111 | 1 463.9 м | 5 940 м² | 5.91 м | — |
| 622715274 (ручной) | 52 | 444.9 м | 3 293 м² | **нет** | 7.4 м |
| **622715275** | **13** | **107.8 м** | **5 940 м²** | **нет** | **55.1 м** |

Вылет 622715275 длился **40 секунд**, прошёл 108 метров и получил **ту же
площадь до последнего знака**, что вылет 622715273 (5940.000029700001 в обоих
JSON). Чтобы 108 метров пути дали 5 940 м², захват должен быть 55 метров —
в девять раз шире, чем на всех остальных вылетах того дня.

Это не оценка «на глаз»: требуемый захват вычисляется из двух чисел самого
DJI, никакая ширина не подставлялась. Считать 55 м реальным захватом T40
нельзя.

Осторожно: **что именно происходит — не установлено.** Повтор значения
похож на перенос площади предыдущей записи, но одного случая мало, чтобы
назвать это правилом DJI. Проверяется поиском по базе: вылеты короче ~60 с,
у которых `new_work_area` в точности равна площади предыдущего вылета той же
машины. Инструмента для этого пока нет; он в плане **этапом A2, и этап A2
обязателен до начала сбора** (`IMPLEMENTATION_PLAN`). Запрос к production без
отдельного разрешения владельца не выполняется.

### 6.3 Что это значит для спора о гектарах

Прежний разбор (`docs/DRONES_AREA_DISPUTE.md`, §2) вывел на литрах октября,
что `new_work_area` = длина пути, учтённой DJI как рабочая, × заданный захват,
а не площадь реально накрытой земли. **Это рабочая гипотеза, полученная из анализа
данных, а не установленный факт**: она выведена из постоянства л/га на
вылетах разного размера, и прямого подтверждения — признака работы насоса — у
неё нет ни там, ни здесь.

Маршруты гипотезу **не опровергают**. Проверка односторонняя, и данные могли
её провалить: если гипотеза верна, «требуемая длина» = `new_work_area /
spray_width` не может превышать длину маршрута — насос не может работать
дольше, чем дрон летел. На семи вылетах, где ширина известна, отношение вышло
**0.336…0.930, ни разу не выше единицы**.

Что это значит и чего не значит. Гипотеза выдержала проверку, которую могла не
выдержать, — это довод в её пользу. Но проверка **односторонняя**: её проходит
и любая другая гипотеза, дающая площадь не больше «длина × захват». Согласие
семи наблюдений гипотезу не доказывает.

Значит 7.7678 против 7.4408 га — это, вероятнее всего, не ошибка DJI, а
**разные величины**. Сформулировать эту разницу можно только условно:

> Если рабочая гипотеза верна, `new_work_area` соответствует длине пути,
> учтённой DJI как рабочая, умноженной на ширину. **Состояние насоса и
> алгоритм отбора сегментов источник не раскрывает.**

Наша же величина — земля, накрытая хотя бы раз, по всей ломаной без отбора.

**Но отношение 1.044 НЕ является измерением перекрытия, и читать его так
нельзя.** В нём одновременно живут два смещения противоположного знака, и ни
одно не измерено:

* **вверх для нас, вниз для отношения:** мы буферизуем весь маршрут, включая
  подлёт и возврат. Земля под ними в нашу полосу входит, а в площадь DJI, если
  верна гипотеза, — нет. Величина надбавки **не измерена**; при этой гипотезе
  она соответствовала бы 22 % пути (§6.1), но это следствие гипотезы, а не
  наблюдение;
* **вверх для DJI:** заданное перекрытие проходов и повторные заходы
  удлиняют путь. **Учитывает ли их DJI и в какой мере — неизвестно**: какой
  путь он засчитывает рабочим, из данных не видно. При гипотезе, что рабочим
  засчитывается весь путь с подачей, они вошли бы в площадь целиком, но и это
  следствие гипотезы, а не наблюдение.

Иными словами, 1.044 — это результат вычитания двух неизвестных величин.
Назвать по нему перекрытие 4.4 % так же неверно, как первая редакция называла
им 15–25 %. **Числа, подтверждающего или опровергающего диапазон 15–25 %, у
нас нет.**

Отделить одно от другого можно только классификацией сегментов на рабочие и
холостые, а она требует состояния насоса, которого в источнике нет (§3).
Поэтому опыт §6 из `DRONES_AREA_DISPUTE.md` — одно поле, один заход,
записанная настройка перекрытия — остаётся **единственным**, что различает
случаи. Ни маршруты, ни их геометрия его не заменяют.

## 7. Контуры полей: что удалось и что нет (§6–7 ТЗ)

**Подтверждено.** Полигон в ответе `lands` **отсутствует**. Есть только ссылка
`geometry.storage.signedURL` и рядом `geometry.storage.contentMd5` и
`geometry.storage.uuid`. Отдельно есть вторая такая же ссылка в
`parameter.storage.signedURL` — назначение не установлено.

**Подтверждено.** Ссылка ведёт на объектное хранилище Alibaba OSS
(`*.oss-ap-northeast-1.aliyuncs.com`), подписана параметрами `Expires`,
`OSSAccessKeyId`, `Signature`. Расширения в пути нет, поэтому **формат по
ссылке определить, не скачав, невозможно**.

**Подтверждено.** В самом ответе `lands` есть `bbox` (две угловые точки),
`position` (центр), `totalArea`/`workArea` в му, `serialNumber`,
`maxGeometryParameterOffset`, `totalObstacleArea`. Из них площадь контура
восстанавливается точно, а **граница — нет**: рамка `Karvon` даёт 13.50 га
против 7.04 га настоящего контура, то есть завышает в 1.9 раза. Правило ТЗ
«bounding box нельзя выдавать за точную границу поля» подтверждается числом.

**Не проверено, и намеренно: полигон по ссылке не скачивался.** Причина не в
осторожности вообще, а в конкретном факте: весь исходящий трафик этого
контейнера идёт через прокси, установленный средой исполнения. Скачивание
означало бы передачу подписанной ссылки владельца — то есть учётного
свидетельства — через посредника, которого владелец не выбирал. §21 ТЗ
запрещает и сохранять signed URL, и отправлять данные во внешние сервисы без
отдельного разрешения. Поэтому формат геометрии остаётся **невозможно
проверить отсюда**, и это вынесено вопросом В2 (§9).

Оценка, которую можно дать уже сейчас: `contentMd5` — это ключ кэша,
готовый и бесплатный. Скачивать полигон нужно только когда `contentMd5`
изменился, а не по расписанию. Ссылка живёт около шести часов
(`docs/tracks/drones.md`, §3), поэтому сбор геометрии обязан идти **в том же
прогоне**, что и сбор списка полей: сохранить ссылку «на потом» и нельзя, и
незачем.

## 8. Безопасность: одно, что требует действия сегодня

**В приложенном файле `DJI_2026-06-05_safe.json` остались живые подписанные
ссылки.** Шесть штук, по числу контуров, попавших в рамку карты, плюс столько
же в `parameter.storage`. Очистка удалила заголовки запросов, cookies, строки
запроса и тела запросов — но `signedURL` лежит **в теле ОТВЕТА**, и её это не
затронуло.

Что это значит на практике: у кого есть файл, у того до истечения `Expires`
есть доступ на чтение к геометрии этих полей. Токена сессии DJI там нет,
доступа к кабинету нет, ущерб ограничен шестью полигонами — но это всё же
свидетельство, а не безобидные данные.

Что сделано и что нужно:

* файл **не закоммичен** и не будет: ни в фикстуры, ни в документы, ни в
  примеры. Ни одна ссылка из него не воспроизведена ни в одном файле
  репозитория;
* фикстуры тестов **синтетические** — идентификаторы вымышлены
  (`900000001`, `FIXTURE0000000000000`), как это уже принято в
  `drone_collector/tests/fixtures/`;
* `tools/drone_route_probe.py` **проверяет входной файл на остатки секретов и
  предупреждает первой строкой**, ничего при этом не печатая и не сохраняя.
  Проверка имеет отрицательный контроль: на чистом файле она молчит, в том
  числе когда в описании файла упомянуто слово «cookies»;
* **владельцу:** удалите этот файл из чатов и переписок; при следующей выемке
  снимка вырезайте `signedURL` и `parameter` из тел ответов, а не только
  заголовки. Точный порядок — вопрос В2 в §9.

## 9. Вопросы владельцу — по форме §25 ТЗ

Было три. **Все три закрыты**: В3 — решением владельца 2026-08-25, В1 и В2 —

### ~~В1~~ — ОТВЕЧЕН 2026-08-26, `V1_REQUEST_BODY_CONFIRMED`

**Ответ.** Тело — **список идентификаторов вылетов**, периода и устройства в
нём нет:

```
POST /api/web/v2/flight_datas/flight_records
{"flight_record_ids": [622715275, 622715274, 622715273, 622712504,
                       622708921, 622704107, 622696758, 622689299,
                       622683215],
 "data_type": "simplified"}
```

**Что это разблокировало.** Маршруты запрашиваются по списку известных
`dji_flight_id`, а не по окну карты — то есть исторический бэкфилл идёт
пакетами идентификаторов и по дням карту открывать не надо. Так и устроен
`drone_collector/routes.py`.

**Что при этом НЕ доказано.** Наличие ключа `data_type` называет
**кандидата** в уровень подробности ответа, а не подтверждает, что бывают
другие уровни. Единственное наблюдавшееся значение — `simplified`; другие
значения исследуются **только по фактическому коду фронтенда или реальному
трафику**, и перебор запрещён (`OBSERVED_DATA_TYPES` в `routes.py`, отказ с
объяснением и тест на него).

**Прежняя формулировка вопроса:**

1. **Неизвестно:** тело `POST /api/web/v2/flight_datas/flight_records` —
   список ли это id, период, устройство, или что-то ещё.
2. **Почему не из репозитория:** тела запросов удалены при очистке снимка, а
   к живому кабинету у сессии доступа нет.
3. **Что нужно:** один снимок сети со **включёнными телами запросов** и
   **вырезанными** заголовками, cookies и `signedURL`. Достаточно двух
   запросов: `only_all_ids` и следующий за ним `flight_datas/flight_records`.
4. **Как безопасно:** DevTools → Network → правый клик на строке запроса →
   Copy → Copy request payload. Скопировать **только тело**, вставить в
   текстовый файл. Заголовки не копировать.
5. **Чего нельзя присылать:** заголовки, cookies, `Signature`, `Authorization`,
   `storage_state.json`, `.env`, пароль DJI.
6. **Что разблокирует:** можно ли забирать маршруты за произвольный период
   одним запросом или карту придётся открывать по дням. От этого зависит
   стоимость исторического бэкфилла, и только она.
7. **Можно ли без ответа:** да. Декодер, модель хранения и расчёт от него не
   зависят; неизвестна лишь скорость сбора.

### ~~В2~~ — ОТВЕЧЕН 2026-08-26, `V2_FIELD_GEOMETRY_CONFIRMED`

**Ответ.** По ссылке лежит **GeoJSON**. На контуре `P03335975`:
`FeatureCollection`; `Polygon` с `funcType=PlantZone`; 22 различные вершины;
кольцо замкнуто; самопересечений нет; `parameters.offset` — 22 значения по
2,5; присутствует **пустой** `MultiPoint` с `funcType=ReferencePoint`; MD5
совпал с `contentMd5`; площадь валидатора 7,0595 га против 7,0437 га у DJI,
расхождение **+0,22 %**; валидатор завершился кодом 0.

**Что это разблокировало.** Скачивание полных контуров
(`drone_collector/geometry.py`): проверка `contentMd5`, собственный sha256,
версии по `contentMd5`, `Polygon` и `MultiPolygon`, дословное сохранение
всего `FeatureCollection` вместе с `funcType`, `parameters.offset`,
`ReferencePoint` и любыми неизвестными properties.

**Что при этом НЕ доказано.** Смысл `parameters.offset` и назначение
`ReferencePoint` неизвестны — они сохраняются именно поэтому. `MultiPolygon`
поддержан, но в подтверждённом файле его не было. Содержимое
`parameter.storage.signedURL` (второй ссылки узла) по-прежнему не
исследовано.

**Прежняя формулировка вопроса:**

1. **Неизвестно:** что отдаёт `geometry.storage.signedURL` — GeoJSON, KML,
   protobuf или бинарный объект; и что такое `parameter.storage.signedURL`.
2. **Почему не из репозитория:** полигоны никогда не скачивались, ссылка живёт
   шесть часов, а скачать её из этой среды означало бы пропустить учётное
   свидетельство через сторонний прокси (§8).
3. **Что нужно:** открыть ссылку из своего браузера, где кабинет уже открыт,
   сохранить ответ в файл и прислать **файл**, а не ссылку. Достаточно одного
   поля — например `Karvon`.
4. **Как безопасно:** DevTools → Network → найти запрос к
   `*.oss-ap-northeast-1.aliyuncs.com` → правый клик → Save response as… →
   назвать `karvon_geometry.bin`. Прислать этот файл.
5. **Чего нельзя присылать:** саму ссылку (в ней подпись), заголовки запроса,
   cookies.
6. **Что разблокирует:** пересечение покрытия с настоящей границей поля.
   Сегодня «внутри контура» считается по рамке, а рамка `Karvon` завышает
   площадь в 1.9 раза.
7. **Можно ли без ответа:** частично. Уникальное покрытие считается и без
   полигона; «площадь внутри контура» и «площадь вне контура» — нет.

### ~~В3~~ — ЗАКРЫТО решением владельца 2026-08-25

**Решение: `spray_width` = `-1` даёт статус `DATA_UNAVAILABLE`. Подстановка
запрещена — ни медианной шириной машины или дня, ни паспортной шириной T40,
ни соседним значением того же дня.**

Такому вылету покрытие не считается вовсе; он не входит ни в геометрическую
сторону сравнения, ни в сторону DJI. Обе стороны всегда считаются по одному и
тому же множеству вылетов.

Решение принято после того, как первая редакция §6 нарушила его же и получила
1.165 вместо 1.044 (§6.0). Поэтому оно закрепляется не только текстом: в
`route_decode.py` уже есть `spray_width_known`, возвращающий False на `-1` и
на нуле, и `route_exceeds_path`, возвращающий `None`, а не `False`, когда
судить не о чем. Расчёт покрытия (этап E) обязан отказывать так же, и на это
стоит критерий приёмки.

Что остаётся неизвестным: **доля таких вылетов по всей базе**. В выборке 2 из
9, но один день одной машины ничего не говорит о парке. Меряется одним
read-only запросом на этапе A2, вместе с частотой аномалии §6.2.

## Поправки независимого ревью PR №109

Ревью нашло восемь блокирующих дефектов в первой редакции этих исправлений.
Все закрыты; ниже то, что меняет ранее записанные утверждения.

* **Неверная посадка браузера теперь ОТКАЗЫВАЕТ, а не предупреждает.**
  `/login` не пустая страница: она ставит свои cookie и localStorage, поэтому
  форма входа прошла бы структурную проверку и затёрла бы рабочую сессию.
  Обе проверки обязательны, и обе — до записи.
* **Право положить тело в карантин стало РАЗРЕШАЮЩИМ списком из одной
  строки** (`BINARY`). Прежний запрещающий список не включал `EMPTY` и
  `TOO_LARGE`, то есть молча разрешал им запись. JSON-подобное тело, не
  декодируемое как UTF-8, теперь `JSON_UNREADABLE`, а не `BINARY`.
* **Сверка идентификаторов сравнивает МНОЖЕСТВА, а не количества.** «Девять
  запросили, девять вернулось» больше не считается совпадением: множества
  сравниваются в оперативной памяти, наружу идут только булево и счётчики
  `missing` / `extra` / `duplicate`. Ни один идентификатор в отчёт и журнал не
  попадает. Дедупликация учитывает набор запрошенных ID, поэтому одинаковое
  тело при разных запросах остаётся двумя наблюдениями.
* **Код 0 у `--route-ui-probe` требует ПОДТВЕРЖДЁННОГО штатного POST:**
  ожидаемый HTTPS-origin, точный endpoint, метод POST, статус 2xx, двоичное
  тело, успешный разбор и совпадение множеств ID. Всё остальное — безопасный
  отчёт и **код 13**. `ROUTE_UI_PROBE=PASS` в ранбуке печатается только после
  такого полного успеха.
* **Признаки заголовков разведены:** cookie, token и authorization больше не
  означают «запрос подписан» — это удостоверение сессии, а не подпись.
  `only_all_ids` считается один раз на сетевой обмен.
* **Убрано утверждение «инструмент не сделал ни одного запроса».** Оно было
  неправдой: probe открывает кабинет, и это навигация. Гарантия, которую код
  действительно даёт, записана как
  `no_route_post_was_initiated_by_probe` — POST к эндпоинту маршрутов probe не
  инициирует.
* **Отказ `os.replace` больше не оставляет `.partial`** рядом с сессией.
* **Ответ сверх потолка сохраняет НАСТОЯЩИЙ размер.** Прежняя редакция
  подменяла тело пустым и записывала `response_bytes=0`, то есть утверждала,
  что огромный ответ был пуст; хеш пустоты не считается вовсе.

**Оговорка к утверждению «настоящих идентификаторов нет».** Оно относится к
идентификаторам вылетов, координатам, cookie, подписям, значениям заголовков и
`request_id` -- и НЕ относится к UUID контрольного поля
`baf71584-64e2-49c5-8a41-25fca4ad5f6e`. Этот идентификатор настоящий, назван
владельцем и присутствует в ранбуке НАМЕРЕННО: без него команда первого
пилота была бы неисполнимой. Его отсутствие за результат проверки не выдаётся.


## Живой прогон наблюдения 2026-08-27 (BAK-TEX11): что доказано и что нет

Прогон выполнен владельцем на изолированной рабочей машине, не на production.
Vehicle Soft и очередь не затронуты. Код выхода 13.

**Доказано.**

* `LIVE_UI_ROUTE_REQUEST_SHAPE_CONFIRMED` -- кабинет делает штатный POST сам:
  `kr-ag2-api.dji.com`, `/api/web/v2/flight_datas/flight_records`, HTTP 200,
  ключи тела `data_type` и `flight_record_ids`, целые идентификаторы без
  повторов. Пять ответов маршрутов, четыре различных наблюдения (один обмен
  повторился), пять `only_all_ids` перед ними.
* `LIVE_UI_SIGNATURE_HEADERS_CONFIRMED` -- у каждого штатного запроса есть
  signature-подобный, credential-подобный и timestamp-подобный заголовок. Это
  ответ на главный вопрос режима: штатный запрос НЕСЁТ подпись, которой не
  было у нашего нативного `fetch`. Значения не сохранялись -- только имена,
  длины и признаки.
* `LIVE_UI_DATA_TYPE_SIMPLIFIED_CONFIRMED` -- кабинет просит
  `data_type=simplified`.

Наблюдавшиеся `requested_count`: 39, 14, 127 и 54. **127 -- НЕ максимальный
размер пакета DJI**, а наибольшее число идентификаторов, попавшее в один
запрос в этом прогоне. Ни верхней границы, ни правила выбора размера прогон не
устанавливает.

**Не доказано.**

`LIVE_UI_RESPONSE_CAPTURE_BLOCKED_BY_PROBE_LIFECYCLE` -- ни одно тело ответа
прочитано не было: на всех пяти консоль показала
`The route response body could not be read (TargetClosedError)`. Причина в
наблюдателе, а не в кабинете: ожидание оператора стояло в голом `input()`,
который держал ПОТОК Playwright. Обработчики событий пошли в работу только
после Enter -- то есть на выходе из `with FlightCollector`, когда target уже
закрывался.

Отчёт того прогона **опровергнут**: он написал `response_body_was_read=true`,
`response_bytes=0`, sha256 ПУСТОГО тела, `payload_kind=EMPTY`,
`observation_errors=0` и «запрошенные ID отсутствуют». Ответы не были пустыми,
идентификаторы не отсутствовали -- **тела просто не были прочитаны**.

Исправлено в `DRONE-COVERAGE-001-B-PROBE-LIFECYCLE-FIX`: оператора спрашивает
отдельный демонический поток, поток Playwright крутит короткий цикл и отдаёт
управление библиотеке на каждом обороте.

Наблюдается ВЕСЬ жизненный цикл запроса -- `request`, `response`,
`requestfinished`, `requestfailed`, -- а тело читается на `requestfinished`, а
не на `response`: Playwright объявляет `response`, когда получены статус и
заголовки, а тело догружается позже. После сигнала оператора ожидание тишины
требует трёх условий сразу: ни одного незавершённого запроса маршрутов, ни
одного обработчика в работе и заданный интервал без сетевой активности; отсчёт
интервала начинается с момента сигнала, поэтому «ответов ещё не видели» не
означает тишину. Оборванный запрос (`requestfailed`) снимается с учёта,
увеличивает счётчик ошибок и даёт код 13; текст причины из браузера не
читается.

**Про drain сказано ровно то, что доказано.** Он ОГРАНИЧЕН по времени: и
ожидание человека, и ожидание тишины кончаются по сроку, вышедший срок даёт
код 13, а не успех, и зависнуть прогон не может. Гарантии, что за это время
успеет прийти КАЖДЫЙ ответ, нет и быть не может -- сеть и кабинет нам не
подчиняются. Незавершённый запрос честно остаётся незавершённым, попадает в
счётчик и в отчёт, и прогон объявляется неподтверждённым. Живьём это не
проверялось.

Непрочитанное тело получило собственный вид `UNREADABLE`: ни размера, ни
хеша, ни сверки идентификаторов оно не порождает. Сверка вообще делается
только после успешного декодирования маршрутов: у пустого тела, тела сверх
потолка, JSON-отказа и неразобранного protobuf вернувшегося списка не
существует, и объявлять запрошенные идентификаторы отсутствующими не за что.

`ROUTE_COLLECTION_BLOCKED_PENDING_CONFIRMED_RESPONSE_CAPTURE`,
`STAGE_C=BLOCKED`. Повторный живой прогон **не выполнялся**: исправление
проверено только синтетикой.
