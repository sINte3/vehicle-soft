# DRONE-COVERAGE-001 — исследование источников данных

Написано 2026-08-25 по техзаданию владельца. Отвечает на разделы 3–7 и 23 ТЗ:
что на самом деле собирает `drone_collector`, что лежит в бинарном ответе DJI,
можно ли связать маршрут с вылетом, откуда взять полигон поля и чего в данных
нет.

**Правило этого документа.** Каждое утверждение помечено одним из четырёх
слов: **подтверждено** (проверено на данных, названа проверка),
**предположительно** (согласуется с данными, но различить альтернативу нечем),
**не найдено** (искали, нет), **невозможно проверить отсюда** (нужен доступ,
которого у сессии нет). Ничего не помечено «очевидно».

Всё воспроизводится двумя командами без сети, браузера и базы:

```
python tools/drone_route_probe.py --capture <ваш снимок>.json
python -m unittest drone_collector.tests.test_route_decode -v
```

## 0. Главное в семи строках

1. Бинарный ответ разобран. Это protobuf wire format, схема не нужна: **все 16
   именованных полей сверены с JSON-ответами того же кабинета и совпали 9 из 9**.
2. **Связь маршрута с вылетом однозначна и не требует угадывания:** поле 2
   записи маршрута — это `dji_flight_id`. Порядок не используется вовсе.
3. **Точка маршрута — это ровно две координаты.** Ни времени, ни высоты, ни
   скорости, ни состояния насоса. Все 961 точки выборки. Отсюда: «подтверждённое
   опрыскивание» из этого источника построить **нельзя**.
4. **Ширина захвата есть у вылета** (`spray_width`), и у двух вылетов из девяти
   её нет — DJI ставит `-1`. Подставлять туда значение нельзя.
5. Геометрическое покрытие спорного дня посчитано: **7.46 га** против **8.69 га**
   у DJI и **7.04 га** площади контура. Расхождение с DJI — 16.5 %.
6. Внутри этих 8.69 га найдена запись, которой **не соответствует её маршрут**:
   вылет 622715275 — 40 секунд, 13 точек, 108 метров пути, и 0.594 га, число
   в точности повторяющее площадь предыдущего вылета.
7. **В приложенном «безопасном» файле остались живые подписанные ссылки.** См.
   §8 — это единственный пункт, требующий действия сегодня.

## 1. Что делает текущий collector — проверено по исходникам

Утверждения §3 ТЗ проверены на HEAD ветки. Все верны, с двумя уточнениями.

**Подтверждено.** `drone_collector/browser.py` слушает ответы браузера и берёт
только список вылетов: `is_flight_list_url()` требует подстроку
`/flight_records?` и **отвергает** всё, где есть `/flight_records/`
(`browser.py:268`). Карточка отдельного вылета намеренно игнорируется и
считается отдельным счётчиком `_ignored_detail` (`browser.py:581`).

**Подтверждено.** Хранится полный ответ: `DroneFlight.raw_json` —
`nullable=False`, кладётся весь payload (`models.py:1887`). Производные колонки
пересчитываются из него, пересбор для этого не нужен.

**Уточнение 1 к ТЗ.** Одной координаты `lat`/`lng` в модели не «одна» — их две
колонки, и обе есть в списке. Но это **точка взлёта**, а не поле: измерено на
сентябре-2025, доля различных координат внутри группы «день × машина» 0.15
(`docs/tracks/drones.md`, §3). Для покрытия она бесполезна, для сшивки с полем —
тоже.

**Уточнение 2 к ТЗ, важное.** ТЗ перечисляет среди собираемого `manual_mode`,
`mode_name`, `work_speed`, `spray_width`, `radar_height` — это верно. Но
**`hardware_id` в списке НЕТ**: сверено по фактическому ответу списка из
приложенного снимка (35 ключей строки, `hardware_id` среди них отсутствует).
Он есть только в карточке отдельного вылета — и, как выяснилось ниже, **в
бинарном ответе маршрутов**. Это тот самый `Body Code`, из-за отсутствия
которого трек не смог разложить октябрь-2025 по бортам (`DRONE-BODYCODE-001`).

**Подтверждено.** Не собирается ничего из перечисленного в §3 ТЗ как
отсутствующее: последовательности GPS-точек, геометрии маршрута, времени точки,
состояния распыления и насоса, событий RTH/паузы/возобновления.

**Подтверждено.** Сбор контуров (`drone_collector/lands.py`) получает список
полей через `POST /ag-plot/api/graphql?name=lands`, а приёмник
`/drones/api/land_sync` вырезает подписанную ссылку перед записью:
`DRONE_LAND_VOLATILE_KEYS = ('signedURL',)` и `_drone_land_strip_volatile()`
(`drones.py:741,776`). Полигон не скачивается. `contentMd5` при этом
**сохраняется** внутри `raw_json` — то есть материал для обнаружения изменений
геометрии в базе уже есть, хотя отдельной колонки под него нет.

## 2. Бинарный ответ: формат (§5.1 ТЗ)

**Подтверждено: это настоящий protobuf wire format.** Не «похоже на». Тело
разобрано побайтно генерическим обходчиком, который знает только правила
кодирования и ничего не знает о схеме: 21 294 байта прочитаны без остатка,
без единого неизвестного типа провода, без переполнения длин. Реализация —
`drone_collector/route_decode.py`, функция `walk()`.

Структура:

```
1  varint   status            = 200
2  bytes    message           = "Success."        <- с точкой; у JSON-ответов "OK"
3  bytes    payload
     1  bytes  route          <- повторяется, ОДИН РАЗ НА ВЫЛЕТ
```

**Схема в JavaScript-бандле DJI не искалась и найдена быть не могла** — у
сессии нет доступа к сайту (см. §9). Но она и **не нужна**: имя message-типа
ничего не добавляет к тому, что уже доказано сверкой значений, а wire format
самодостаточен для чтения. Вывод §5.1 ТЗ «либо схема, либо ограниченный
декодер с жёсткой валидацией» разрешается в пользу второго, и не по бедности:
декодер, отказывающий на непонятной структуре, надёжнее сгенерированного,
который молча стерпит смену семантики поля при неизменном типе.

**Опровергнуто как метод.** ТЗ предупреждает не делать вывод по тому, что
первые два поля похожи на `status`/`Success`. Правильно: вывод сделан не по
ним. Он сделан по совпадению **шестнадцати** полей с независимым источником —
JSON-карточками тех же девяти вылетов.

| Что искали | Результат |
|---|---|
| время каждой точки | **не найдено** |
| высота, скорость, курс | **не найдено** |
| состояние распыления | **не найдено** |
| состояние насоса, клапанов | **не найдено** |
| расход | **не найдено** |
| события RTH, паузы, возобновления, возврата после дозаправки | **не найдено** |
| идентификатор дрона | **найден** — `hardware_id`, поле 9 |
| идентификатор вылета | **найден** — поле 2 |
| номер задания | **предположительно** — поле 14 |

Проверка «точка — это ровно две координаты» не рассуждение, а перебор: каждая
из 961 точек разобрана отдельно, и любая, где полей не два или тип не
`fixed64`, обрывает разбор с ошибкой. Это же поведение закреплено тестом
`test_a_point_with_a_third_field_is_refused`: если DJI когда-нибудь добавит в
точку третье поле, декодер **откажет**, а не промолчит, и вывод «только
позиция» будет пересмотрен сознательно.

**Следствие для §10.3 ТЗ.** Показатель `Confirmed spraying area` из этого
источника создать нельзя. Разрешённые формулировки — «геометрическое
покрытие», «рабочий кандидат», «маршрут внутри поля».

## 4. Связь маршрута с вылетом (§5.3 ТЗ)

**Связь однозначна, детерминирована и не опирается на порядок.**

* Поле 2 каждой записи — `dji_flight_id`. Девять записей дали девять id, в
  точности те же, что вернул `/flight_records/only_all_ids` и что стоят на
  девяти карточках.
* Возвращаются маршруты **всех вылетов выборки**, не одного.
* Порядок ответа — по времени начала по возрастанию. Это видно на данных:
  `only_all_ids` в первом вызове снимка вернул id в **несортированном** порядке,
  а ответ маршрутов пришёл байт в байт таким же, как после двух других
  вызовов, где порядок был убывающим. То есть сервер сортирует сам, и **связь
  по порядковому номеру была бы случайно верной и потому особенно опасной**.
  Она не используется.

Что содержит тело POST-запроса — **невозможно проверить отсюда**: очистка
снимка удалила тела запросов. Но это и не нужно для связи: id приходит в
ответе. Для планирования сбора знать состав запроса всё же полезно — вопрос
вынесен в §9, В1.

**Правило, которое отсюда следует.** Маршрут без поля 2 или с id, которого нет
в `drone_flights`, идёт в карантин `UNLINKED`. Угадывание запрещено и не
понадобится ни разу, пока DJI не уберёт поле 2.

## 5. Повторные ответы (§5.4 ТЗ)

**Причина установлена.** Три тела **байт в байт одинаковы**: sha256
`c505e688b9c0a00e…`, 21 294 байта каждое. Порядок событий в снимке:

```
09:53:00.970  GET  only_all_ids          -> 9 id, порядок несортированный
09:53:01.697  POST flight_datas/…        -> маршруты
09:53:07.608  GET  only_all_ids          -> те же 9 id, порядок убывающий
09:53:08.349  POST flight_datas/…        -> те же байты
09:53:17.587  GET  only_all_ids          -> те же 9 id
09:53:18.292  POST flight_datas/…        -> те же байты
```

Каждому POST предшествует свой `only_all_ids`, и между ними лежат вызовы
`lands` с **разным** составом полей (2, 6, 2 контура). Это перерисовка карты:
пользователь менял вид, и клиент каждый раз заново запрашивал и список id, и
маршруты, и поля в новой рамке. Не «повторный запрос одного слоя», а полный
повтор цепочки.

**Дедупликация.** Ключ — sha256 сырого тела вместе с контекстом запроса
(набор id и период). Хеш уже реализован в `tools/drone_route_probe.py`
(`dedupe()`), проверен тестами в обе стороны: одинаковые тела схлопываются со
счётчиком, тело, отличающееся одним байтом, — нет.

## 6. Геометрия и площадь: что посчиталось на спорном дне

### 6.1 Числа

Считалось так: точки → плоские метры (равнопромежуточная проекция вокруг
центра трека; на 400 метрах ошибка меньше метра) → буфер вокруг ломаной
радиусом `spray_width / 2`, торцы и стыки плоские → объединение буферов.
Библиотека — Shapely 2.1.2 (та же версия, что уже закреплена в
`gps/requirements.txt`).

| Величина | Значение |
|---|---:|
| Площадь DJI за день (сумма девяти `new_work_area`) | **8.6911 га** |
| Плитка кабинета DJI за тот же день | 8.6913 га |
| **Геометрическое объединение буферов** | **7.4630 га** |
| Сумма буферов без объединения | 9.9201 га |
| Снято объединением (перекрытие проходов и заходов) | 2.4571 га |
| Выпуклая оболочка всех точек | 7.7188 га |
| Площадь контура `Karvon` P03335975 по справочнику DJI | 7.0437 га |

Отношения: DJI / контур = **1.234**; геометрия / контур = **1.059**;
DJI / геометрия = **1.165**.

**Поле опознано.** 99.3 % площади покрытия лежит в рамке контура `Karvon`
серийный `P03335975`, и рамка трека (40.0807–40.0841 с. ш., 64.6288–64.6329
в. д.) практически совпадает с рамкой контура. Соседний `Karvon 2`
(`P02839704`, 2.3836 га) набирает 12.8 % только потому, что его рамка
**перекрывается** с рамкой `Karvon`; собственной работы там нет. Версия
операторов «на Karvon 2 не работали» — **подтверждена**.

Заодно подтверждена и арифметика справочника: `totalArea` = 105.655 му,
делённое на 15, даёт ровно 7.0437 га — то самое «7.04», которое операторы
приняли за часть имени контура (`docs/DRONES_AREA_DISPUTE.md`, §2).

### 6.2 Найденная аномалия

Из 8.69 га DJI **0.594 га приходятся на запись, которой её маршрут не
соответствует**.

| Вылет | Точек | Длина пути | Площадь DJI | Ширина | Требуемый захват |
|---|---:|---:|---:|---:|---:|
| 622715273 | 111 | 1 463.9 м | 5 940 м² | 5.91 м | — |
| 622715274 (ручной) | 52 | 444.9 м | 3 293 м² | **нет** | 7.4 м |
| **622715275** | **13** | **107.8 м** | **5 940 м²** | **нет** | **55.1 м** |

Вылет 622715275 длился **40 секунд**, прошёл 108 метров и получил **ту же
площадь до последнего знака**, что вылет 622715273 (5940.000029700001 в обоих
JSON). Чтобы 108 метров пути дали 5 940 м², захват должен быть 55 метров —
в девять раз шире, чем на всех остальных вылетах того дня.

Это не оценка «на глаз»: требуемый захват вычисляется из двух чисел самого
DJI, никакая ширина не подставлялась. Считать 55 м реальным захватом T40
нельзя.

Осторожно: **что именно происходит — не установлено.** Повтор значения
похож на перенос площади предыдущей записи, но одного случая мало, чтобы
назвать это правилом DJI. Проверяется поиском по базе: вылеты короче ~60 с,
у которых `new_work_area` в точности равна площади предыдущего вылета той же
машины. Инструмента для этого пока нет — он в плане, этап A.

### 6.3 Что это значит для спора о гектарах

Прежний разбор (`docs/DRONES_AREA_DISPUTE.md`, §2) вывел на литрах октября,
что `new_work_area` = длина пути с работающим насосом × заданный захват, а не
площадь реально накрытой земли. **Маршруты этот вывод не опровергают и
согласуются с ним численно.**

Проверка односторонняя и данные могли её провалить: если модель верна, то
«требуемая длина» = `new_work_area / spray_width` не может превышать длину
маршрута — насос не может работать дольше, чем дрон летел. На семи вылетах,
где ширина известна, отношение вышло **0.336…0.930, ни разу не выше единицы**.
Модель выдержала проверку, которую могла не выдержать.

Значит разница 8.69 против 7.46 га — это не ошибка DJI, а **разные величины**:
DJI считает пройденный с распылением путь (в него входит заданное перекрытие
проходов, обычно 15–25 %, и опрыскиваемые развороты), геометрия считает
землю, накрытую хотя бы раз. Ожидаемый множитель 1/(1−p) при p = 15 % даёт
1.18 — измеренные 1.165 попадают в этот порядок. **Это согласие, а не
доказательство:** настройка перекрытия в данных вылета не лежит, и сверить
множитель с ней не с чем. Опыт §6 из `DRONES_AREA_DISPUTE.md` остаётся
единственным, что различает случаи.

## 7. Контуры полей: что удалось и что нет (§6–7 ТЗ)

**Подтверждено.** Полигон в ответе `lands` **отсутствует**. Есть только ссылка
`geometry.storage.signedURL` и рядом `geometry.storage.contentMd5` и
`geometry.storage.uuid`. Отдельно есть вторая такая же ссылка в
`parameter.storage.signedURL` — назначение не установлено.

**Подтверждено.** Ссылка ведёт на объектное хранилище Alibaba OSS
(`*.oss-ap-northeast-1.aliyuncs.com`), подписана параметрами `Expires`,
`OSSAccessKeyId`, `Signature`. Расширения в пути нет, поэтому **формат по
ссылке определить, не скачав, невозможно**.

**Подтверждено.** В самом ответе `lands` есть `bbox` (две угловые точки),
`position` (центр), `totalArea`/`workArea` в му, `serialNumber`,
`maxGeometryParameterOffset`, `totalObstacleArea`. Из них площадь контура
восстанавливается точно, а **граница — нет**: рамка `Karvon` даёт 13.50 га
против 7.04 га настоящего контура, то есть завышает в 1.9 раза. Правило ТЗ
«bounding box нельзя выдавать за точную границу поля» подтверждается числом.

**Не проверено, и намеренно: полигон по ссылке не скачивался.** Причина не в
осторожности вообще, а в конкретном факте: весь исходящий трафик этого
контейнера идёт через прокси, установленный средой исполнения. Скачивание
означало бы передачу подписанной ссылки владельца — то есть учётного
свидетельства — через посредника, которого владелец не выбирал. §21 ТЗ
запрещает и сохранять signed URL, и отправлять данные во внешние сервисы без
отдельного разрешения. Поэтому формат геометрии остаётся **невозможно
проверить отсюда**, и это вынесено вопросом В2 (§9).

Оценка, которую можно дать уже сейчас: `contentMd5` — это ключ кэша,
готовый и бесплатный. Скачивать полигон нужно только когда `contentMd5`
изменился, а не по расписанию. Ссылка живёт около шести часов
(`docs/tracks/drones.md`, §3), поэтому сбор геометрии обязан идти **в том же
прогоне**, что и сбор списка полей: сохранить ссылку «на потом» и нельзя, и
незачем.

## 8. Безопасность: одно, что требует действия сегодня

**В приложенном файле `DJI_2026-06-05_safe.json` остались живые подписанные
ссылки.** Шесть штук, по числу контуров, попавших в рамку карты, плюс столько
же в `parameter.storage`. Очистка удалила заголовки запросов, cookies, строки
запроса и тела запросов — но `signedURL` лежит **в теле ОТВЕТА**, и её это не
затронуло.

Что это значит на практике: у кого есть файл, у того до истечения `Expires`
есть доступ на чтение к геометрии этих полей. Токена сессии DJI там нет,
доступа к кабинету нет, ущерб ограничен шестью полигонами — но это всё же
свидетельство, а не безобидные данные.

Что сделано и что нужно:

* файл **не закоммичен** и не будет: ни в фикстуры, ни в документы, ни в
  примеры. Ни одна ссылка из него не воспроизведена ни в одном файле
  репозитория;
* фикстуры тестов **синтетические** — идентификаторы вымышлены
  (`900000001`, `FIXTURE0000000000000`), как это уже принято в
  `drone_collector/tests/fixtures/`;
* `tools/drone_route_probe.py` **проверяет входной файл на остатки секретов и
  предупреждает первой строкой**, ничего при этом не печатая и не сохраняя.
  Проверка имеет отрицательный контроль: на чистом файле она молчит, в том
  числе когда в описании файла упомянуто слово «cookies»;
* **владельцу:** удалите этот файл из чатов и переписок; при следующей выемке
  снимка вырезайте `signedURL` и `parameter` из тел ответов, а не только
  заголовки. Точный порядок — вопрос В2 в §9.

## 9. Вопросы владельцу — по форме §25 ТЗ

Все три можно задать консультанту как есть. Ни один не блокирует работу
целиком: что можно делать без ответов, сказано в каждом.

### В1. Что уходит в теле запроса маршрутов

1. **Неизвестно:** тело `POST /api/web/v2/flight_datas/flight_records` —
   список ли это id, период, устройство, или что-то ещё.
2. **Почему не из репозитория:** тела запросов удалены при очистке снимка, а
   к живому кабинету у сессии доступа нет.
3. **Что нужно:** один снимок сети со **включёнными телами запросов** и
   **вырезанными** заголовками, cookies и `signedURL`. Достаточно двух
   запросов: `only_all_ids` и следующий за ним `flight_datas/flight_records`.
4. **Как безопасно:** DevTools → Network → правый клик на строке запроса →
   Copy → Copy request payload. Скопировать **только тело**, вставить в
   текстовый файл. Заголовки не копировать.
5. **Чего нельзя присылать:** заголовки, cookies, `Signature`, `Authorization`,
   `storage_state.json`, `.env`, пароль DJI.
6. **Что разблокирует:** можно ли забирать маршруты за произвольный период
   одним запросом или карту придётся открывать по дням. От этого зависит
   стоимость исторического бэкфилла, и только она.
7. **Можно ли без ответа:** да. Декодер, модель хранения и расчёт от него не
   зависят; неизвестна лишь скорость сбора.

### В2. Формат геометрии по подписанной ссылке

1. **Неизвестно:** что отдаёт `geometry.storage.signedURL` — GeoJSON, KML,
   protobuf или бинарный объект; и что такое `parameter.storage.signedURL`.
2. **Почему не из репозитория:** полигоны никогда не скачивались, ссылка живёт
   шесть часов, а скачать её из этой среды означало бы пропустить учётное
   свидетельство через сторонний прокси (§8).
3. **Что нужно:** открыть ссылку из своего браузера, где кабинет уже открыт,
   сохранить ответ в файл и прислать **файл**, а не ссылку. Достаточно одного
   поля — например `Karvon`.
4. **Как безопасно:** DevTools → Network → найти запрос к
   `*.oss-ap-northeast-1.aliyuncs.com` → правый клик → Save response as… →
   назвать `karvon_geometry.bin`. Прислать этот файл.
5. **Чего нельзя присылать:** саму ссылку (в ней подпись), заголовки запроса,
   cookies.
6. **Что разблокирует:** пересечение покрытия с настоящей границей поля.
   Сегодня «внутри контура» считается по рамке, а рамка `Karvon` завышает
   площадь в 1.9 раза.
7. **Можно ли без ответа:** частично. Уникальное покрытие считается и без
   полигона; «площадь внутри контура» и «площадь вне контура» — нет.

### В3. Ширина захвата, когда DJI её не записал

1. **Неизвестно:** чем считать ширину у вылета, где `spray_width` = `-1`.
   В выборке это 2 вылета из 9, оба в конце дня, оба без `geometry_md5`.
2. **Почему не из репозитория:** это правило учёта, а не факт данных. Устав
   запрещает выдумывать такие правила.
3. **Что нужно:** решение владельца из трёх: (а) не считать покрытие вовсе,
   статус `DATA_UNAVAILABLE`; (б) считать медианной шириной той же машины за
   тот же день и помечать результат как оценку; (в) считать паспортной шириной
   T40 и помечать так же.
4. **Как безопасно:** ответ словами, никаких файлов.
5. **Чего нельзя присылать:** ничего.
6. **Что разблокирует:** поведение расчёта на ~2 вылетах из 9 в этой выборке.
   Доля по всей базе не измерена — она измеряется на живой базе одним запросом
   (этап A плана).
7. **Можно ли без ответа:** да, по варианту (а). Он единственный ничего не
   выдумывает, и до ответа принят именно он.

## 10. Риски и блокеры

| Риск | Оценка | Что делать |
|---|---|---|
| Ответ маршрутов перехватывается тем же слушателем, что и список | **Низкий, но проверяемый.** URL `…/v2/flight_datas/flight_records` совпал бы с фильтром `is_flight_list_url()`, только если несёт строку запроса. Тогда `response.json()` на octet-stream упал бы и дал `unparsable-body` — счётчик отказов, не потеря данных | Сбор маршрутов делать **отдельным прогоном** и отдельным слушателем; фильтр списка не трогать |
| Смена версии API DJI (`v2` → `v3`) | Средний | Маркер по имени эндпоинта, не по версии — как уже сделано для списка (`FLIGHT_LIST_URL_MARKER_LOOSE`) |
| DJI меняет структуру точки | Низкий | Декодер откажет, а не промолчит; тест зафиксирован |
| Полигон недоступен | **Реализован сегодня** | Считать уникальное покрытие без обрезки, «внутри контура» не показывать вовсе, а не подменять рамкой |
| Объём данных | Измерен, не риск | См. §11 |
| Порча существующего сбора | Управляемый | Ни одна строка `browser.py`, `sender.py`, `main.py` в этой работе не изменена |

## 11. Объём хранения — измерено, не оценено

Выборка: 961 точка на 9 вылетов = **106.8 точки на вылет**. Парк на 2026-08-08 —
30 702 вылета, то есть порядка **3.3 млн точек**.

| Способ | Байт на точку | На 30 702 вылета |
|---|---:|---:|
| Отдельные строки в SQLite (+индекс), замерено на настоящей вставке | 55.4 | **182 МБ** |
| GeoJSON-текст | 38.9 | 128 МБ |
| Упакованные `double` без обвязки | 16.0 | 53 МБ |
| Дельты `int32` с шагом 1e-7° (≈1.1 см) | 8.0 | 26 МБ |
| То же + zlib | **4.3** | **14 МБ** |

Строки на точку дороже сжатой ломаной в **13 раз** и не покупают ничего: ни
одного запроса «найди точку» в задаче нет, работа всегда идёт целой ломаной.
Решение — хранить ломаную одним полем; обоснование и формат — в архитектуре.

## 12. Что доказано, что опровергнуто, что осталось неизвестным

**Доказано.** Формат ответа; 16 полей записи; связь маршрута с вылетом по
`dji_flight_id`; точка = только координаты; ширина захвата есть у вылета и
бывает отсутствующей; причина троения ответа; отсутствие полигона в ответе
`lands` и наличие `contentMd5`; `hardware_id` приходит вместе с маршрутом;
объём хранения; поле спорного дня — `Karvon` P03335975; геометрическое
покрытие дня 7.46 га.

**Опровергнуто.** «970 точек» из ТЗ — их **961**: предварительный ручной
разбор посчитал за точку маршрута ещё и поле 7 (точка взлёта), по одному
лишнему на каждую из девяти полилиний. Число полилиний (9) подтвердилось.
Опасение ТЗ, что связь маршрута с вылетом установить не удастся, не
подтвердилось — она явная. Предположение, что на `Karvon 2` не работали,
подтвердилось геометрически.

**Осталось неизвестным.** Тело POST-запроса (В1); формат геометрии по ссылке
(В2); правило ширины при `-1` (В3); смысл полей 14 и 27; глубина хранения
маршрутов в DJI и лимиты запросов — **невозможно проверить отсюда**, меряется
первым же прогоном на живом кабинете; частота аномалии «площадь повторяет
предыдущую» по всей базе; настоящий множитель перекрытия — он не измеряется
телеметрией вовсе и требует полевого опыта.

## 13. Как это перепроверить

```
python -m unittest drone_collector.tests.test_route_decode -v     # 23 теста
python tools/test_drone_route_probe.py                            # 6 тестов
python tools/drone_route_probe.py --capture <ваш снимок>.json
python tools/drone_route_probe.py --capture <снимок>.json --geojson routes.json
```

Файл `routes.json` открывается любым просмотрщиком GeoJSON и содержит девять
ломаных с их `dji_flight_id`, ником, `hardware_id`, площадью DJI и шириной.
Секретов в нём нет по построению.
