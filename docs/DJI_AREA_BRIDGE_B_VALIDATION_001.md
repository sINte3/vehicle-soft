# DJI-AREA-BRIDGE-B-VALIDATION-001 — надо ли вместе с C корректировать мостик B

Исследование, а не правило. Один вопрос: промежуточная запись B в цепочке
A → B → C — такая же ложная площадь, как фантом C, или нет. Ничего не внедрено:
алгоритм площади, структурное правило и учётные классы не менялись.

**Ответ: нет.** B — не артефакт записи, а отдельный отрезок полёта с включённым
насосом и собственным приростом счётчика. Автоматическая коррекция остаётся
только у C.

## 1. На чём посчитано

Период 01.09–18.09.2026. Вход — локальная реплика площадки, собранная из тех же
конвертов сборщика, что ушли на площадку, с применёнными пересборкой улик и
пересчётом `impl-4`. Реплика совпадает с живым блоком R число в число: 4623
расчёта, RAW 44 132 825 м², 233 структурных кандидата. SHA-256 базы
`9ab29e700cf1ba69…`, до и после прогона один и тот же — база открывается
`mode=ro`.

К кабинету DJI обращений не было. Площадка и production не затрагивались.

Инструмент — `tools/dji_area_bridge_b_validation.py`. Цепочки строит
**замороженный** `dji_area.structural`, на тех же группах и в том же порядке,
что и конвейер; собственной копии правила в инструменте нет, и это проверено
тестом (экран подменяется — цепочки исчезают).

Восстановленный набор целей C сверен дважды и совпал: с расчётными строками
(233) и с замороженным планом holdout (233).

Мостик — это любая запись цепочки, кроме «mode 4 с шириной». Поэтому в двух
цепочках вида A → M → N → M → N средняя запись N сама есть цель собственной
цепочки. Она **уже исправляется как C** и входит в 167,8088 га; считать её ещё
и как B значило бы задвоить коррекцию. Оба таких B помечены `B_IS_ITSELF_C`.

По бортам (цепочек / RAW мостиков, га): 14 Servis 50 / 7,26; 8 GardenU 42 /
2,65; 10 Kogon 38 / 5,27; 5 Shofirko 30 / 1,35; 3 Gijduvon 26 / 2,76; 12 Servis
23 / 2,25; 15 Servis 17 / 0,55; 6 Shofirko 5 / 0,73; 13 Peshku 2 / 0,15.

## 4. Что говорит V4

V4 для B специально не собирался. Он есть у **55 из 233** ручных B — они попали
в контрольные страты плана holdout: 39 из случайной `N5_RANDOM`, 15 из
`N3_SHORT_HIGH_RATE`, 1 из `N1_EQUAL_RECENT`. Случайная страта — несмещённая
выборка; `N3` отбирает короткие записи с высокой площадью, то есть как раз те,
где завышение было бы заметнее всего.

| По 55 ручным B с V4 | Значение |
|---|---|
| Статус резолвера | `RAW_CORROBORATED` — **55 из 55** |
| Счётчик плоский | **0 из 55**; верхняя граница доли 95 % — 5,3 % |
| Применение наблюдалось | 50; не наблюдалось 5 |
| Доля пути с включённым насосом | медиана **84,7 %**, p90 98,9 % |
| Расход LIST / расход V4 | n = 50, минимум 0,936, медиана **1,000**, максимум 1,033 |
| Преобладающий рабочий режим в кадрах | 1 (ручной) — 55 из 55 |

Для сравнения у C (V4 есть у всех 233): доля пути с включённым насосом —
медиана **0 %**, p90 0 %; преобладающий рабочий режим — «поле отсутствует» у 207
и режим 4 у 26.

Это принципиальное отличие. У C счётчик стоит, а площадь повторяет A — запись
ложная. У B счётчик вырос ровно на записанную площадь, и два независимых канала
(расход в LIST и расход в телеметрии) сходятся с отношением 1,000.

Площадь B воспроизводится арифметикой: «путь с включённым насосом × ширина».
Пример: `701512751` — путь 336 м, насос включён на 60 % (202 м), ширина в кадрах
до 8 м → 1613 м² при записанных 1600 м².

### Пять случаев без наблюдённого применения

`703900135`, `704505125`, `704600007`, `705149221`, `706135217` — 0,5211 га.
Счётчик вырос на RAW, но кадров потока нет. Все пять — **один борт**
(`…0100PQ`), и в их телеметрии поля потока и расхода отсутствуют вовсе, хотя
ширина в каждом кадре есть. Это провал канала телеметрии у конкретной машины, а
не поведенческий паттерн. Категория `B_EVIDENCE_CONFLICT`, все пять вынесены
владельцу на просмотр.

## 7. Наблюдаемая модель A → B → C

Сигнатуры взлётов периода (взлёт — серия записей борта с зазором в пределах
правила; A — mode 4 с шириной, M — иное, N — mode 4 без ширины):

`A` 3435, `AMN` 217, `M` 147, `AA` 82, `AM` 70, `N` 8, `AAMN` 8, `AAM` 4,
`AMNMN` 2, `AAMNM` 2, `AMNM` 1, `AMAAM` 1, `AAAMN` 1 — всего 3978 взлётов.

- Взлётов с переходом Auto → ручной: **306**. Из них продолжаются записью N —
  **231 (75,5 %)**; 75 до N не доходят.
- Запись N внутри взлёта **никогда** не идёт сразу после A: ей всегда
  предшествует ручной отрезок.
- Записей N в периоде 241 = 233 кандидата + 8 одиночных (без цепочки).

Последовательность «Auto → ручной → Auto без ширины» — обычная, но не всеобщая:
четверть ручных отрезков после Auto записью C не заканчивается.

## 8. Механизм DJI: факт, вывод, неизвестное

**FACT — следует из данных.**

1. B — ручной режим в 233 из 235; в кадрах V4 рабочий режим 1 у 55 из 55.
2. C повторяет площадь A в **233 из 233**.
3. A, B и C — один взлёт: `lat/lng` записи LIST совпадают до последнего знака в
   233 из 233. Контроль признака: у соседних записей с зазором в пределах
   правила совпадение 645 из 645, у соседних с зазором больше минуты — **0 из
   3915**. Признак различает.
4. B и C — два куска одной непрерывной траектории: конец B и начало следующей
   записи совпадают в пределах 0,13 м (55 пар по кадрам V4).
5. C начинается сразу за B: зазор 0 с либо 1 с.
6. Расход у C накопительный: `spray_usage(C) = spray_usage(A) + Σ spray_usage(B)`
   точно в 199 цепочках, в остальных 34 больше на 1–145 мл (столько вылито за
   сам C). У B расход собственный.
7. Площадь у C **не** накопительная: она равна площади A, а не A + B.
8. На отрезке B насос включён на 84,7 % пути (медиана), на отрезке C — на 0 %.
9. Оба отрезка почти прямые: прямолинейность — медиана 0,97.

**INFERENCE — наиболее вероятное объяснение.** Визуальное впечатление владельца
верно геометрически: B и C действительно выглядят как один прямой перелёт,
потому что это и есть одна траектория. Но первую её часть борт летит с
включённым насосом в ручном режиме, и контроллер честно считает площадь «путь ×
ширина»; вторую — с выключенным, и запись C наследует площадь Auto-задачи.
Запись вида C несёт накопительные величины взлёта для расхода и величину
Auto-отрезка для площади.

**UNKNOWN — данных недостаточно.**

- Почему DJI при возврате в состояние mode 4 заводит отдельную запись и кладёт в
  неё площадь A. Внутренней логики прошивки и облака в данных нет.
- Почему четверть переходов Auto → ручной записью C не заканчивается.
- **Агрономическая полезность B.** Полив по прямой на пути от поля может быть и
  обработкой пропущенной полосы, и проходом вне контура поля. Это отличает
  только контур, а контуры полей не захвачены (`TIER5_UNKNOWN` у всех записей).
  V4 на этот вопрос ответить не может в принципе.

## 9. Нужен ли новый сбор V4

`NEW_DJI_CALL_REQUIRED = NO`.

Вопрос этапа — корректировать ли B автоматически — существующими данными уже
закрыт: среди 55 B с V4 (39 из них случайные) нет ни одного с плоским
счётчиком, а расход жидкости записан у 213 из 233. Адресный сбор V4 по
оставшимся 12 записям без всяких признаков применения уточнил бы не более 0,69
га и решения изменить не может. Файл `bridge_b_v4_capture_ids.txt` поэтому не
составлялся; сами 12 идентификаторов лежат в `bridge_b_summary.json` и целиком
включены в лист выборочной проверки.

## 11. Чего это исследование НЕ устанавливает

- Что площадь B агрономически полезна. Установлено только, что она **не
  артефакт записи**: счётчик рос, насос работал, жидкость расходовалась.
- Что поведение одинаково вне сентября. Август не пересчитывался.
- Что 165 записей без V4 устроены так же, как 55 с V4. Это подкреплено
  расходом LIST и случайностью 39 из 55, но не доказано по каждой записи.

## 12. Решение

Из двух исходов, названных в постановке, данные поддерживают второй: **C
остаётся автоматической коррекцией, B автоматически не трогается.**

Считать ли ручной полив на пути от поля оплачиваемой работой — бизнес-правило.
Код его не выводит и выводить не должен; если владелец захочет его ввести, это
отдельное решение с отдельным основанием, а не продолжение коррекции фантомов.
