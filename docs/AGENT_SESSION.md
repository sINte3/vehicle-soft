# Как работает сессия Claude Code в этом репозитории

Читается **после** `CLAUDE.md` и **до** трекового файла. `CLAUDE.md` — устав:
что в проекте нельзя и почему. Этот файл — порядок работы: где ты находишься,
что решаешь сам, чем доказываешь, что сделал.

Владелец ведёт разработку через облачные сессии и прикладывает задание текстом
и файлами в чат. Сессия обязана довести задание до смерженного PR, **не
задавая вопросов там, где ответ можно принять самому**, и не выдумывая там,
где принимать его нельзя. Граница между этими случаями — §3.

---

## 1. Где ты находишься

Одноразовый Linux-контейнер со свежим клоном репозитория. Всё, что не
закоммичено и не запушено, исчезает вместе с ним.

**Ни staging, ни production из этой среды недостижимы и достигаться не
должны.** Площадка `10.103.25.14:5051` и боевой сервер `10.103.25.14:5050`
живут во внутренней сети заказчика. Инструкции на PowerShell в `CLAUDE.md` и
в ранбуках — **для владельца**, не для тебя: ты их пишешь, он их выполняет.

Отсюда следует главное: **твоя работа заканчивается смерженным PR.** Деплой,
прогон на площадке и приёмку делает человек. Если задание требует чего-то на
сервере — опиши это командами, готовыми к вставке, без плейсхолдеров.

### Клон в контейнере ОБРЕЗАН — это ловушка на суждениях об истории

`git rev-parse --is-shallow-repository` возвращает `true`: в контейнер приезжает
не вся история, а последние сотни коммитов. Всё, что старше границы, git не
видит вовсе.

Отсюда молчаливо неверные ответы там, где кажется, что вопрос простой:

```
git branch -r --merged origin/main      # ветка старше границы -> "не влита"
git log A..B                            # A старше границы -> диапазон неполон
git merge-base --is-ancestor A B        # ложное "нет"; ложного "да" не бывает
```

Случай из жизни: сессия насчитала «10 влитых веток из 44» и назвала владельцу
это число. На его полном клоне влитых оказалось **43**. Команда была верной,
неверным был клон — а вывод выглядел совершенно правдоподобно, потому что
ответ «не влита» проверка даёт и для действительно невлитой ветки, и для
влитой, но старой.

**Правило.** Прежде чем утверждать что-либо об истории старше нескольких
недель — углубить клон:

```
git fetch --unshallow        # или: git fetch --deepen=2000
```

Либо не утверждать вовсе, а отдать владельцу команду, которая посчитает на
его полном клоне, и сказать, что число не проверено здесь.

Утверждения о свежих коммитах (то, что сессия сама только что запушила)
обрезкой не задеты — они внутри окна по построению.

Что в контейнере есть: Python с зависимостями из `requirements.txt`, Node,
Playwright с уже установленными браузерами (`playwright install` запускать
**нельзя**), и одноразовый стенд `tools/ux/serve_ephemeral.py` — настоящее
приложение на выбрасываемой базе. Проверять UI надо на нём, а не рассуждением.

## 2. Первые действия

Брифинг среды печатается автоматически при старте сессии
(`.claude/hooks/session-start.sh`): ветка, состояние гейта, занятость
площадки, что стоит на проде, готовность зависимостей. Перечитывать это
командами не нужно.

Дальше, по порядку:

1. **Определи трек** по заданию и прочитай `docs/tracks/<трек>.md` — это точка
   входа, в нём цель, границы, сделанные инкременты и открытые хвосты.
   Треки: `drones`, `fuel`, `spare-parts`, `gps-plan-fakt`, `ui`.
2. **Прочитай приложенные файлы целиком**, а не по диагонали. Отчёт агента,
   выгрузка, скриншот, лог — это вход задачи.
3. **Заведи ветку** от свежего `origin/main`. Работа прямо в `main` запрещена.
4. `docs/AGENT_STATE.md` и `docs/TASKS.md` — летопись на сотни килобайт.
   Читать **точечно поиском** по коду задачи, никогда целиком.

**Если приложенный отчёт расходится с репозиторием — прав репозиторий.**
Отчёт, в том числе твой собственный из прошлой сессии, доказательством не
является; принимается дифф и артефакт.

## 3. Что решаешь сам, а что нельзя выдумывать

Владелец просит не переспрашивать. Это выполнимо не полностью, и вот точная
граница.

**Решай сам и не спрашивай** — технические выборы: имена, структура файлов,
какой токен взять, где провести границу модуля, размер окна выдачи, состав
тестов, формулировки на двух языках, порядок коммитов. Выбор назови в описании
PR вместе с причиной — тогда владелец может его оспорить, не разбирая диффа.

**Неоднозначность задания** толкуй так, как истолковал бы внимательный
коллега: возьми ближайшее разумное прочтение, **объяви допущение** и работай
дальше. Не останавливайся ради уточнения, от которого работа не меняется.

**Не выдумывай бизнес-правила** — учёт, утверждение заявок, топливный учёт,
нормы, порядок расчётов. Устав запрещает это прямо, и запрет остаётся в силе.
Но «не выдумывать» не значит «встать»:

1. сделай всё, что от неизвестного правила не зависит, и доведи до PR;
2. недостающую часть **не реализуй правдоподобно** — оставь незакрытой;
3. вопрос запиши в двух местах: в описании PR и в разделе «Что открыто»
   трекового файла;
4. в отчёте назови прямо, что именно не сделано и почему.

**Останавливаться, ничего не сделав, можно только когда** любое допущение
приводит к порче данных, к неверному числу в отчёте, по которому примут
решение, или к необратимому действию.

## 4. Что значит «сделано»

Полное определение — в `CLAUDE.md`, раздел «Что значит „готово“». Здесь
команды, все обязаны быть чистыми до отчёта:

```
python -m compileall -q .
python tools/check_templates.py
python tools/test_check_templates.py
python tools/check_design_system.py
python tools/test_check_design_system.py
python -m unittest discover -s tests
```

Первые пять — блокирующие проверки CI, они же стоят в `.github/workflows/checks.yml`.
`check_design_system.py` — храповик: счётчики имеют право только уменьшаться.
Осознанный рост объявляется в описании PR и фиксируется `--update-baseline`
**отдельным коммитом**, а не молча.

Если трогал шаблоны — прогони UI-проверки на одноразовом стенде:

```
python tools/ux/serve_ephemeral.py --port 5099 &
cd tools/ux && node check_a11y_all.mjs --base http://127.0.0.1:5099
cd tools/ux && node check_overflow.mjs --base http://127.0.0.1:5099
```

Если писал миграцию — четыре пути из `CLAUDE.md`: чистая база, повтор,
отсутствие базы (код 2), непройденное предусловие (код 1).

**Для каждого критерия приёмки скажи, чем именно он проверен**: имя теста,
команда, число. Непроверенное называй непроверенным.

**Проверка, дающая одинаковый результат при верном и неверном коде, проверкой
не является.** Прежде чем объявить контроль доказательством, убедись, что он
способен различить два случая — по возможности прогони отрицательный контроль
и покажи оба числа.

## 5. Ветка, коммиты, PR

- Ветка от свежего `origin/main`, имя даёт владелец или задача.
- **`git add -A` и `git add .` запрещены всегда** — только поимённо. В рабочих
  копиях десятки чужих untracked-файлов. Перед коммитом — `git status --short`
  и проверка индекса.
- **`git reset --hard` как откат запрещён.** Откат — `git revert` в обратном
  порядке.
- Коммит объясняет **почему**, а не пересказывает дифф. Дефект называется
  вместе с тем, как он проявлялся и чем закрыт.
- Мерж — «Create a merge commit», не squash.
- PR не создавай, пока владелец не попросит. Когда просит — в описании:
  что сделано, какие решения приняты самостоятельно и почему, **чем именно
  проверено** (числа), что осталось непроверенным, какие общие файлы задеты.

**Общие файлы — `app.py`, `models.py`, `templates/base_next.html`,
`static/css/design-system.css`, `migration_utils.py`, `excel_export.py`.**
Правка любого выходит за границы трека и объявляется в описании PR отдельным
абзацем. Молча — нельзя.

## 6. Гейт релиза и площадка

`docs/RELEASE_GATE.md` — единственный на проект список того, что влито в
`main`, но не провалидировано. Пока таблица «Открытые пункты» не пуста,
прод-деплой закрыт **для всего проекта**, а не только для твоего трека.

Влил непроверенное — положи строку **последним коммитом внутрь PR**: мерж-коммит,
созданный кнопкой GitHub, правок файлов содержать не может, и иначе строка не
приедет. Одна запись — ровно одна строка; таблицу не переформатировать,
столбцы пробелами не выравнивать.

`docs/STAGING.md` — кто занимает площадку. Занимая, **заменяй строку целиком**
и коммить отдельно. Прогон на площадке делает владелец: ты пишешь ему задание
и порядок, он выполняет и приносит отчёт.

`docs/DEPLOYED.md` — что развёрнуто. Пишет только та сессия, которой поручен
релиз; трековые сессии его не трогают.

## 7. Чего не делать никогда

- Не ходить на `10.103.25.14` — ни на `:5050`, ни на `:5051`.
- Не удалять и не пересоздавать `instance/transport.db`; `init_data.py` — только
  для локальной базы.
- Не удалять продовые данные автоматически, ни одной операцией.
- Не менять схему БД без миграции и записанного порядка отката.
- Не добавлять зависимости Python без объяснения и правки `requirements.txt`.
- Не подключать внешние фронтенд-фреймворки: только Jinja2, ванильный JS и
  дизайн-система.
- Не менять деловое содержание выгрузок Excel.
- Не трогать `_perform_fuel_sync`.
- Не запускать `playwright install`.
- Не печатать секреты и токены — только имена переменных.
- Не расширять границы инкремента «заодно» и не переименовывать сущности
  частично.

## 8. Классы дефектов, на которых проект уже обжигался

Полный список — в `CLAUDE.md`. Здесь то, что чаще всего ловит именно агента:

- **`tojson` только внутри `<script>` или в атрибуте с ОДИНАРНЫМИ кавычками.**
  В атрибуте с двойными парсер обрывает значение, обработчик молча не ставится.
- **Jinja заканчивает комментарий на ПЕРВОМ `#}`** — комментарий, внутри
  которого написано `{# … #}`, обрывается раньше, чем кажется.
- **`{% set %}`, использованный до объявления, рендерится пустой строкой молча.**
- **`app = create_app()` вызывает `db.create_all()` на импорте** — любой скрипт
  с `from app import app` писатель, а не читатель. Диагностика — через stdlib
  `sqlite3`.
- **`db.create_all()` никогда не добавляет колонку** — дрейф не падает, а тихо
  деградирует.
- **Проверка использования переменной подстрокой врёт**: `L_initial` совпадает
  с `L_initial_missing`.
- **Цветовые токены сверять по значениям, а не по именам.**
- `User.is_active_user` — колонка, `User.is_active` — property.

## 9. Язык интерфейса

Все пользовательские строки двуязычны: русский и узбекский, **узбекский только
кириллицей**. Латиница — лишь в названиях продуктов: Topaz, RFID, DJI, Wialon,
Excel, PDF.

Общие модули — через `t()`, запчасти — через `_spare_t()`, дроны и АЗС — через
`{% set is_ru = (lang == 'ru') %}`. Ключ, которого нет в словаре, `t()` вернёт
как есть — и подпись останется на языке исходника в обоих интерфейсах; это
ловит проверка `t-key-missing`. Текст, написанный прямо в разметке, через
словарь не проходит вовсе — это проверка `raw-text`.

Совпадение русского и узбекского написания дефектом **не является**, если пара
объявлена в обоих языках намеренно: «Сумма», «Оператор», «Артикул», «Бренд»,
единицы и бренды совпадают по существу.
