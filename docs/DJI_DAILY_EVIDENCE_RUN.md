# Ежедневный сбор доказательств DJI — рекомендованная конфигурация

Подготовлено DRONE-AREA-CAPTURE-001. **Это предложение, а не применённое
изменение.** `DroneCollectorDaily` на production этим инкрементом не
трогался; включать после merge и деплоя, руками владельца.

## Что уже есть

| | |
|---|---|
| Scheduled Task | `DroneCollectorDaily`, около 06:00 |
| Корень | `C:\transport-report\drone_collector` |
| Baseline контуров | 6171, снят 11.09.2026 (`dji_land_revisions = 6171`, `dji_land_geometries = 6171`) |

Второй параллельный collector или второй планировщик **не нужен**. Ниже —
одна задача и два вызова внутри неё.

## Рекомендованная команда

```powershell
$py = 'C:\Program Files\Python314\python.exe'
Set-Location C:\transport-report
& $py -m drone_collector.main
& $py -m drone_collector.main --sources --from (Get-Date).AddDays(-2).ToString('yyyy-MM-dd') --to (Get-Date).ToString('yyyy-MM-dd') --send-sources
& $py -m drone_collector.main --land-snapshot --with-geometry --send-snapshot
```

Порядок именно такой: сначала вылеты, потом их источники, потом каталог.

**Первый вызов** собирает скользящее окно вылетов и, начиная с этого
инкремента, кладёт в очередь их СПИСОЧНОЕ доказательство — сырые байты
ответа DJI, из которых потом читаются площадь, ширина и режим. Раньше эти
поля приходили из изменяемой `drone_flights.raw_json`.

**Второй вызов** забирает ПОСТРОЧНЫЕ источники каждого вылета — card,
route, airlines и телеметрию **V4**. Без него V4 не появляется ни у одного
вылета, а `dji_v4_summaries` остаётся пустой: расчёт площади тогда не может
отличить внесение от перелёта и весь период остаётся `TIER5_UNKNOWN`.

Окно взято с запасом в два дня, потому что вылет попадает в кабинет с
задержкой. Повтор дёшев: `--sources` возобновляем, уже поставленный в
очередь вылет второй раз не открывается. Частичный сбор — код 18, и
следующий прогон доберёт только недостающие.

**Третий вызов** обновляет каталог полей. После baseline он скачивает
только те полигоны, `contentMd5` которых приёмник ещё не хранит.

## Что считать нормальным прогоном

```
Catalog 6171/6171: captured 71 contour(s) on this page; cursor=..., hasNext=False
Geometry manifest: asked about 6171 polygon(s), the receiver already stores 6158.
Geometry 6171/6171 done: known=6158 new=13 no-polygon=0 failed=0
Snapshot chunk 7/7 answered: status=ok ... geometries_new=13 geometries_unchanged=0
```

| Признак | Что значит |
|---|---|
| `geometry_known_skipped` ≈ размеру каталога | инкрементальность работает |
| `geometry_downloaded` = десятки | столько полигонов реально изменилось |
| `geometry_manifest: unavailable` | манифест не ответил; прогон корректен, но снова длинный. Разобраться с сетью/токеном |
| `referenced_but_absent` ≠ 0 в строке чанка, или `snapshot_geometries_referenced_but_absent` ≠ 0 в сводке | **команда завершается кодом 21** и разбираться надо в тот же день: ссылка на полигон есть, тела нет. Привязка поля тихо съедет с `TIER1_EXACT`, сохранив HIGH-уверенность. Считается по ТЕКУЩИМ ревизиям, поэтому после замены полигона новым число возвращается к нулю |
| `list_sources_queued` = числу вылетов окна | A13 закрыт на этих данных |
| `list_pages_without_raw` ≠ 0 | столько страниц осталось без неизменяемого источника |
| `list_sources_left_pending` ≠ 0 | не доставлено; уйдёт следующим прогоном, терять нечего |

## Что именно восстанавливается после обрыва

Формулировка важна, потому что уровней два.

**Восстанавливается — на уровне кусков снимка.** Куски, которые приёмник
принял, лежат в `sent/` и второй раз не уходят. Непринятые остаются в
`pending/`, и следующий прогон дошлёт именно их, причём старый незавершённый
снимок уходит раньше нового (сортировка по `<run_id>:<chunk>`). Доказано
тестом `AnInterruptedSnapshotSendIsResumable`.

**НЕ восстанавливается — отдельные полигоны внутри одного оборванного цикла
загрузки.** Они живут в памяти до момента нарезки на куски; если процесс
убит на середине, эти байты потеряны и будут скачаны заново. Такого уровня
восстановления нет, и заявлять его не следует. На практике это не страшно:
после baseline качается десяток полигонов, а не шесть тысяч.

## Повторный запуск и восстановление

Обе команды безопасно повторяются.

* Снимок идемпотентен по `capture_run_id` на приёмнике и по ключу
  дедупликации в очереди.
* Оборванная отправка оставляет куски в `pending/`; следующий прогон их
  дошлёт. Ничего не теряется и ничего не дублируется.
* Повторный обход каталога после обрыва создаёт НОВЫЙ снимок — это
  правильно: это новое наблюдение каталога, а не починка прежнего.
* Неполный обход помечается `INCOMPLETE`, и отсутствие контура в нём
  **никогда** не читается как удаление.
* Код **21** (ссылка на полигон без тела) отличается от **20**
  (пакет не принят) тем, что повторять отправку нечего: куски приняты и
  лежат в `sent/`. Недостающее тело привезёт ближайший ночной обход сам:
  манифест отвечает «знаю» только по строкам `dji_land_geometries`, а пропавший
  md5 именно тем и пропал, что строки там нет — значит он будет скачан.

## Первая live qualification после деплоя

Минимальная и безопасная. Она НЕ должна снова качать 6171 полигон.

```powershell
& $py -m drone_collector.main --land-snapshot --with-geometry --send-snapshot
```

Что смотреть в выводе:

1. `Geometry manifest: ... the receiver already stores N` — N близко к 6171.
   Если `unavailable` — манифест не доехал, и это первое, что надо чинить.
2. `known=` близко к 6171, `new=` — десятки. Если `new=6171`, инкрементальность
   не сработала: прислать вывод.
3. `geometries_referenced_but_absent=0` в ответе приёмника.
4. Время прогона — минуты, не час с лишним.

Отдельная проверка A13 — на следующем обычном прогоне вылетов:

```sql
SELECT COUNT(*) FROM dji_source_revisions WHERE source_type='list';
SELECT COUNT(*) FROM dji_flight_evidence WHERE list_revision_id IS NOT NULL;
```

Оба должны стать ненулевыми. До этого инкремента первое было нулём всегда.

Проверка покрытия V4 — то, чем в итоге держится отличие внесения от
перелёта:

```sql
SELECT COUNT(*) FROM dji_source_revisions WHERE source_type='v4';
SELECT COUNT(*) FROM dji_v4_summaries;
```

На 11.09.2026 первое было **87** при 11 631 вылете за полные месяцы
августа-сентября, то есть V4 имелся у 0.7% работ, и `v4_summaries_decoded`
пересчёта равнялся нулю. Причина — в ежедневном прогоне не было вызова
`--sources`. С ним число обязано расти на объём суточных вылетов; если не
растёт, смотреть код 18 и `DJI_SOURCE_WAIT_MS`.

## Чего эта конфигурация НЕ делает

* не трогает `field_contours` — изменяемый справочник живёт своей жизнью;
* не пишет ничего в production из сессии разработки;
* не меняет Scheduled Task — это ручной шаг владельца;
* не проверяет геометрию на осмысленность: разбор GeoJSON и сверка площади
  живут в `GeometryRun`, который в неизменяемое хранилище не отправляет
  (зафиксировано как A21).
