# DRONE-COVERAGE-001 — архитектура

Читается **после** `docs/DRONE_COVERAGE_001_DISCOVERY.md`. Там факты, здесь
решения. Каждое решение названо вместе с отвергнутой альтернативой и причиной
отказа; решение без альтернативы — это не решение, а умолчание.

Ничего из описанного здесь не написано и не применено. Порядок работ — в
`docs/DRONE_COVERAGE_001_IMPLEMENTATION_PLAN.md`.

---

## 1. Что система обещает и чего не обещает

**Обещает:** показать маршрут вылета, границу поля, посчитанную геометрию
покрытия и площадь DJI рядом, назвать расхождение и его причину, дать нажать
на вылет и увидеть, из чего число получилось.

**Не обещает:** сказать, что было опрысканo. Маршрут несёт только координаты
(DISCOVERY §3). Слов «подтверждённое опрыскивание» в интерфейсе не будет ни
на одном экране.

**Не трогает:** ни одного существующего начисления. Площадь DJI остаётся
единственной величиной, попадающей в отчёты и в деньги, пока владелец не
решит иначе отдельным решением.

---

## 2. Общая схема

```
браузер DJI (Playwright, существующая сессия)
   |
   |  прогон 1: список вылетов        -- НЕ ТРОГАЕТСЯ, работает с 2026-08-08
   |  прогон 2: маршруты (новый)      -- отдельная команда, отдельный слушатель
   |  прогон 3: контуры + геометрия   -- расширение существующего --lands
   v
drone_collector/  (свой venv, Playwright, БЕЗ shapely)
   |  route_decode.py  -- разбор, отказ вместо догадки
   |  очередь на диске -- прогон переживает сбой
   v
POST /drones/api/route_sync, /drones/api/field_geometry_sync   (токен, как flight_sync)
   v
transport.db  -- сырьё: ломаная, полигон, хеши. НИ ОДНОГО расчёта
   ^
   |  stdlib sqlite3, пишет ТОЛЬКО пересчёт
   |
drone_coverage/  (свой venv: shapely, pyproj, numpy. БЕЗ Flask)
   |  считает покрытие, кладёт результат с версией алгоритма
   v
Flask-приложение -- ТОЛЬКО читает: карточка вылета, экран доказательств,
                    очередь проверки
```

**Р1. Три процесса, а не один.** Сбор, расчёт и показ разделены. Причина не
эстетическая: расчёт требует shapely/pyproj/numpy, а служба Vehicle Soft не
должна их тащить — это уже установленное правило проекта, записанное в
`gps/requirements.txt` и `drone_collector/requirements.txt` и соблюдённое
дважды. Отвергнуто: считать покрытие в приёмнике на лету. Это добавило бы
службе стек численных библиотек ради работы, которая делается раз в сутки
пакетом.

**Р2. Сбор маршрутов — отдельный прогон, а не довесок к сбору вылетов.**
Существующий сбор работает по расписанию с 2026-08-08 и является production-
процессом. Новый слушатель ставится на свой экземпляр браузера в своей
команде. Отвергнуто: слушать оба ответа в одном прогоне. Ответ маршрутов —
`octet-stream`, а действующий слушатель делает `response.json()` на всём, что
прошло фильтр списка; при неудачном совпадении URL это дало бы рост счётчика
`unparsable-body` в живом прогоне. Ценой одного лишнего открытия страницы
покупается невозможность задеть работающее.

## 3. Модель данных

Шесть таблиц вместо десяти из ТЗ. Что выброшено и почему — в §3.7; это часть
решения, а не умолчание.

Общее для всех: `created_at` UTC; исходные значения DJI неизменяемы; повторный
приём того же ответа не создаёт строк; расчёт хранит версию алгоритма и хеши
входов, чтобы его можно было воспроизвести и объяснить.

### 3.1 `drone_route_fetches` — один принятый ответ

| Колонка | Тип | Смысл |
|---|---|---|
| `id` | PK | |
| `response_sha256` | TEXT, **UNIQUE** | хеш сырого тела. Ключ идемпотентности |
| `endpoint` | TEXT | путь без строки запроса |
| `requested_flight_ids` | TEXT | id, которые просили (JSON-массив), если известны |
| `period_from`, `period_to` | DATE | окно, за которое открывалась карта |
| `byte_size`, `route_count`, `point_count` | INTEGER | что пришло |
| `dji_status`, `dji_message` | INTEGER, TEXT | внутренний статус ответа, не HTTP |
| `decoder_version` | TEXT | версия `route_decode.py` |
| `fetched_at`, `ingested_at` | DATETIME | |

**Троение из DISCOVERY §5 гасится здесь и бесплатно:** второй и третий одинаковые

| Колонка | Тип | Смысл |

пользователю можно только вторую.

### 3.3 `field_contour_geometries` — полигон поля, с версиями

| Колонка | Тип | Смысл |
|---|---|---|
| `id` | PK | |
| `field_contour_id` | INTEGER FK → `field_contours.id` | |
| `content_md5` | TEXT | `geometry.storage.contentMd5` от DJI. Версия |
| `sha256` | TEXT | **наш** хеш скачанного тела |
| `source_format` | TEXT | что реально пришло — заполняется по факту (вопрос В2) |
| `geometry_geojson` | TEXT | нормализованный полигон, WGS84, longitude-latitude |
| `area_ha_computed` | REAL | **наша** площадь по полигону |
| `area_ha_dji` | REAL | `totalArea` / 15 |
| `is_valid`, `validation_note` | | результат `make_valid`, самопересечения, кольца |
| `downloaded_at`, `superseded_at` | DATETIME | |

Уникальность: (`field_contour_id`, `content_md5`). **Старая версия никогда не
перезаписывается** — ей проставляется `superseded_at`. Расчёт хранит id
версии, по которой считал, поэтому перерисовка контура задним числом не
меняет старые результаты молча.

`area_ha_computed` против `area_ha_dji` — встроенный контроль формата: если
наш разбор полигона расходится с площадью DJI больше чем на процент, разобрали
неправильно.

**Существующая таблица `field_contours` не меняется.** У неё уже есть
`geometry_geojson`, но она одна на контур и без версий; заполнять её —
значит потерять историю. Правку общего `models.py` это всё же требует (новая
модель), и это объявляется отдельно.

### 3.4 `drone_coverage_runs` — один пакет пересчёта

`id`, `started_at`, `finished_at`, `algorithm_version`, `parameters_json`,
`routes_seen`, `routes_computed`, `routes_skipped`, `routes_error`, `status`,
`error_text`.

Счётчики по образцу `DroneSyncLog`: `seen = computed + skipped + error`.
Инвариант заявляется в докстринге модели и проверяется тестом — так же, как
для приёма вылетов.

| Колонка | Смысл |
|---|---|
| `route_id`, `run_id` | FK |

| `unique_coverage_ha` | объединение буферов допустимых сегментов |
| `inside_contour_ha` | пересечение с полигоном. NULL, если полигона нет |
| `outside_contour_ha` | остаток. NULL, если полигона нет |
| `overlap_estimate_ha` | сумма буферов минус объединение |

Уникальность: (`route_id`, `algorithm_version`). Пересчёт с тем же
`input_hash` — no-op; это и есть идемпотентность.

**`difference_pct` не имеет порога.** Порог — бизнес-правило, его назначает
владелец после полевых испытаний (ТЗ §13). До тех пор очередь сортируется по
величине расхождения, а не фильтруется по нему.

### 3.6 Формат ломаной — и почему не строки на точку

Измерено на выборке (DISCOVERY §11): строки в SQLite — 55.4 байта на точку,
**182 МБ** на текущий парк; дельты `int32` с шагом 1e-7° плюс zlib — 4.3 байта,
**14 МБ**. Разница в тринадцать раз.

Разрешение 1e-7 градуса — около 1.1 см по широте. Точность GPS дрона на два
порядка хуже, так что округление ничего не теряет; при этом целые числа
исключают дрейф float при повторном чтении.

**Отвергнуто: `drone_route_points` строками.** Она оправдана, только если есть
запросы к отдельной точке. Их нет: и расчёт, и карта работают целой ломаной.
Платить 168 МБ и 3.3 млн строк за возможность, которой не пользуются, нельзя.

**Отвергнуто: WKB.** Тот же порядок, что упакованные `double` (16 байт на
точку), плюс зависимость от shapely в приёмнике.

### 3.7 Чего из ТЗ нет и почему

| Таблица ТЗ | Решение | Причина |
|---|---|---|
| `drone_route_points` | **нет** | §3.6, разница в 13 раз без выигрыша |
| `drone_route_flight_links` | **нет** | связь один-к-одному и явная (поле 2). Таблица связей моделирует неоднозначность, которой в данных нет, и создаёт место, где она может завестись |
| `drone_coverage_segments` | **нет пока** | классификация — эвристика (§6), и она пересчитывается из ломаной за миллисекунды. Хранить 3.3 млн строк ради значения, которое меняется с каждой версией правил, преждевременно. Заводится, когда правило застынет |
| `field_contour_geometry_versions` | **слита** с `field_contour_geometries` | версия и есть строка: `content_md5` уникален в паре с контуром. Две таблицы дали бы то же самое через join |

### 3.8 Побочная находка, которую надо забрать

`hardware_id` приходит вместе с маршрутом (DISCOVERY §3), а в списке вылетов
его **нет**. Это идентификатор борта — тот самый `Body Code`, из-за нехватки
которого `DRONE-BODYCODE-001` не смог разложить октябрь-2025 по машинам
(205.98 га уехали не на те борта).

Значит сбор маршрутов **попутно закрывает вопрос принадлежности вылета
борту**, независимо от того, чем кончится история с площадью. Это отдельная
ценность, и она достаётся бесплатно: колонка уже в `drone_routes`.

## 4. Расчёт площади

### 4.1 Проекция

**EPSG:32641, UTM зона 41N.** Бухарская область на 64.6° в. д. попадает в
41-ю зону, и та же проекция уже используется движком `gps/area.py` — то есть
выбор не новый, а согласованный с действующим кодом проекта.

Порядок координат: внутри расчёта — `(x, y)`; в GeoJSON — `[longitude,
latitude]`; в ответе DJI — `(lat, lng)`. Перестановка делается ровно в двух
местах и покрыта тестом с несимметричной точкой (широта и долгота заведомо
разные), иначе тест пройдёт при перепутанном порядке.

Гектары считать в градусах запрещено; проверка — площадь известного полигона,
посчитанная двумя способами.

### 4.2 Формула

```
покрытие = union( buffer(допустимый сегмент, width/2, flat, flat) )
внутри   = покрытие ∩ полигон поля
снаружи  = покрытие − полигон поля
```

Параметры и почему именно они:

* **`width` — только `spray_width` самого вылета.** `NULL` → покрытие не
  считается вовсе, статус `DATA_UNAVAILABLE`. **Решение владельца 2026-08-25:**
  подстановка запрещена — ни медианной шириной машины или дня, ни паспортной
  шириной T40, ни соседним значением того же дня. Правило не декоративное:
  первая редакция DISCOVERY §6 нарушила его и получила отношение 1.165 вместо
  1.044 (DISCOVERY §6.0).
* **торцы плоские (`cap_style=flat`).** Круглый торец добавляет полукруг
  радиусом 3 м на каждом конце сегмента — на ломаной из ста сегментов это
  сотни лишних квадратных метров из ничего.
* **стыки плоские (`join_style=mitre` с ограничением).** Скруглённый стык на
  развороте раздувает площадь там, где её как раз спорят.
* **самопересечения** снимаются `make_valid` до объединения, а не после.
* **минимальная длина сегмента** — сегменты короче 0.5 м отбрасываются: они
  дают только шум GPS, а буфер вокруг них всё равно поглощается соседним.
* **разрыв маршрута.** Медианный шаг точек в выборке 2.6 м, но 45 % длины
  лежит в сегментах 150–300 м — это прямые рабочие проходы, а не пропуски
  (DISCOVERY §6). Поэтому **длинный сегмент не разрывается и не отбрасывается**.
  Порог, за которым сегмент считается недостоверным, назначается по данным на
  этапе E, а не выдумывается сейчас.

**Формула ТЗ принята с одной поправкой.** ТЗ предлагает буферить «допустимые
сегменты». Пока состояния насоса нет, «допустимый» определить нечем, и на
этапе наблюдения буферится **вся ломаная**. Это осознанно завышает покрытие
на величину подлётов — и именно поэтому число называется «геометрическим
покрытием», а не обработкой.

### 4.3 Что уже посчиталось

На спорном дне (DISCOVERY §6.1), **когорта из семи вылетов с записанной
шириной**: геометрическое объединение **7.4408 га** против **7.7678 га**,
которые DJI даёт этим же семи. Отношение **1.044**.

Три оговорки, без которых это число нельзя пересказывать:

1. **Обе стороны считаются по одному множеству вылетов.** Два вылета без
   ширины исключены из обеих, а не из одной. Сравнение 7.4408 с 8.6911 (девять
   вылетов) — ошибка первой редакции, разобранная в DISCOVERY §6.0.
2. **Буферизуется вся ломаная**, включая подлёт и возврат: исключать нечем,
   состояния насоса нет. Значит это **верхняя оценка накрытой земли**, а не
   обработанная площадь. Насколько велика надбавка — не измерено и из данных не
   следует.
3. **1.044 не измеряет перекрытие.** В нём два несмеренных смещения разного
   знака (DISCOVERY §6.3). Диапазон 15–25 % оно не подтверждает и не
   опровергает.

Это **не калибровка**: одна машина, один день, одно поле.

## 5. Модель доверия

Четыре статуса ТЗ плюс один. Пятый добавлен не для полноты, а потому что без
него очередь проверки бесполезна.

| Статус | Когда | Может ли влиять на деньги |
|---|---|---|
| `DATA_UNAVAILABLE` | нет маршрута, нет ширины, нет полигона | нет |
| `UNKNOWN` | маршрут есть, но данных для вывода не хватает | нет |
| `REVIEW_REQUIRED` | расхождение, ручной режим, маршрут по нескольким полям, аномалия §6.2, ширина не подтверждена, связь под сомнением | нет |
| `GEOMETRY_ONLY` | посчиталось, противоречий нет, но подтверждения химией нет | **нет** |
| `VERIFIED` | **недостижим до полевых испытаний** | по отдельному решению владельца |

**Почему `GEOMETRY_ONLY` необходим.** Без него всякий успешно посчитанный
вылет обязан лечь в `REVIEW_REQUIRED` — ведь подтверждения опрыскивания нет
никогда. Очередь, в которой сто процентов строк, — это не очередь, а список
всего. Пятый статус отделяет «посчитано и непротиворечиво» от «нужно
посмотреть глазами», и только второе попадает в очередь.

**`VERIFIED` заблокирован в коде, а не в договорённости.** Пока константа
`VERIFIED_ENABLED` равна `False`, ни один путь не может его проставить, и на
это стоит тест. Разблокировка — отдельный коммит с отдельным решением.

## 6. Классификация сегментов — честная граница

ТЗ перечисляет двенадцать статусов. **Из них геометрией решаются четыре, и
это надо сказать прямо, а не выдать эвристику за правило.**

| Статус ТЗ | Решается? | Чем и с какой уверенностью |
|---|---|---|
| `OUTSIDE_FIELD` | **да, детерминированно** | точка вне полигона. Требует полигона (вопрос В2) |
| `OVERLAP` | **да, детерминированно** | буфер сегмента пересекается с уже накрытым |
| `UNLINKED` | **да, детерминированно** | нет поля 2 или нет такого вылета |
| `DATA_UNAVAILABLE` | **да, детерминированно** | нет ширины, нет маршрута |
| `TRANSFER` / `RETURN` | **частично, эвристика** | первый и последний сегменты, примыкающие к точке взлёта. В выборке 7 вылетов из 9 начинались и заканчивались в пределах 0.6 м от неё. Уверенность средняя, отдельно помечается |
| `WORK_CANDIDATE` | **нет** | прямой длинный проход и холостой перелёт геометрически неразличимы. ТЗ прямо это и запрещает утверждать |
| `TURN` | **нет надёжно** | плотный сгусток точек похож на разворот, но так же выглядит зависание |
| `PAUSE` / `RESUME` | **нет** | нужны времена точек. Их нет |
| `INVALID_GPS` | **почти нет** | скачок отличают от прямого прохода по времени, а времени нет. Ловятся только грубые выбросы — точка за десятки километров |

**Вывод.** На этапе наблюдения система классифицирует то, что решается, и
честно помечает остальное как `UNKNOWN`. Экран доказательств показывает эту
границу, а не прячет её: сегмент без надёжного класса рисуется пунктиром, и в
легенде написано, почему.

## 7. Карта

### Р2. Никакой внешней картографической библиотеки на первом шаге

Проверено: в Vehicle Soft карт **нет ни одной**. Весь фронтенд — три
рукописных файла в `static/js` и одна дизайн-система; ни одной внешней
зависимости, ни сборки, ни `package.json` в приложении. Устав запрещает
внешние фронтенд-фреймворки и оставляет Jinja2, ванильный JS и дизайн-систему.

**Решение: экран доказательств рисуется как inline-SVG.** Полигон поля,
ломаная маршрута, полоса покрытия, точка взлёта — всё это плоские фигуры в
UTM 41N, а метры мы уже считаем. Пан и зум — три десятка строк ванильного JS
через `viewBox`. Печать и экспорт — бесплатно, SVG печатается как есть.

Что теряется: спутниковая подложка. ТЗ §8 прямо допускает «работу без базовой
подложки», и для сравнения маршрута с контуром она не нужна — обе фигуры
рисуем мы.

**Отвергнутые варианты, с причиной:**

| Вариант | Почему нет |
|---|---|
| **Leaflet** | ~42 КБ, самый лёгкий из настоящих. Против: внешняя зависимость, которую надо вендорить и обновлять; **предположительно** нет доступа к тайлам OSM с рабочих мест (см. ниже — не проверено); без тайлов Leaflet сводится к рисованию поверх пустоты, то есть к тому же SVG, но с библиотекой |
| **MapLibre GL** | WebGL, ~200 КБ, требует style JSON и векторных тайлов, то есть **своего тайл-сервера**. Инфраструктура ради подложки, которой не просили |
| **OpenLayers** | тяжелее Leaflet, API сложнее, тот же вопрос с тайлами |
| **Коммерческий сервис** | лицензия, квоты, и главное — маршруты предприятия ушли бы наружу. ТЗ §21 это запрещает |

**Довод о недоступности тайлов НЕ ПРОВЕРЕН, и решение на него не опирается.**
Ни один запрос к OSM с рабочего места не делался: из этого контейнера
внутренняя сеть предприятия недостижима. Утверждение взято из общего свойства
среды («всё on-premises») и остаётся **предположением**. Проверяется одной
командой с любого рабочего места:

```
Invoke-WebRequest -Uri "https://tile.openstreetmap.org/10/676/389.png" -OutFile "$env:TEMP\tile.png"
```

Файл скачался — тайлы доступны, довод отпадает. Не скачался — довод верен.

**Решение inline-SVG от этого не зависит и остаётся в силе в обоих исходах.**
Оно опирается на два других довода: устав ограничивает фронтенд ванильным JS,
а обе фигуры экрана — контур и маршрут — рисуем мы сами, подложка для их
сравнения не нужна. Доступность тайлов лишь определяет, **сколько стоит
следующий шаг**: при доступных тайлах это Leaflet поверх нашего слоя, при
недоступных — Leaflet плюс локальный кэш тайлов на сервере. SVG-слой не
выбрасывается ни в том, ни в другом случае. Решение о подложке — за
владельцем; работа без неё начинается сегодня.

### Что на экране

Границу поля с именем и площадью; полную траекторию; начало и конец;
классифицированные сегменты; полосу покрытия шириной `spray_width`;
перекрытия; участки вне контура; неопределённые участки пунктиром.

Цвета берутся **из токенов дизайн-системы**, а не назначаются заново:
`--vs-success`, `--vs-warning`, `--vs-danger`, `--vs-info` и серый текста.
Предложенная в ТЗ палитра совпадает с ними по смыслу. Контраст проверяется
`tools/ux/check_a11y_all.mjs` на одноразовом стенде; цвет никогда не остаётся
единственным различителем — у каждого класса свой стиль штриха.

### Что на экране не будет никогда

`signedURL`, cookies, `storage_state`, заголовки DJI, параметры подписи. В
шаблон уходит только геометрия и числа. Отдельный тест проверяет, что ответ
экрана не содержит подстроки `signedURL`.

## 8. API

Два новых приёмника по образцу `/drones/api/flight_sync`. Тот же токен
(`DRONE_API_TOKEN`), та же тройка счётчиков, тот же отказ при незаданном
токене.

### `POST /drones/api/route_sync`

Тело: `{kind, period_from, period_to, fetches: [{response_sha256, endpoint,
dji_status, dji_message, decoder_version, routes: [...]}]}`.

* **Идемпотентность** по `response_sha256` и по `dji_flight_id`.
* **Пакет** — не больше 200 маршрутов за запрос (при 107 точках и 4.3 байта
  на точку это порядка 100 КБ полезной нагрузки; предел тела оставляем тем же,
  что у `flight_sync`).
* **Валидация координат:** широта −90…90, долгота −180…180, не NaN, не ноль-
  ноль. Ломаная короче двух точек принимается, но покрытия не даёт.
* **Частично повреждённый пакет отвергается целиком**, транзакция
  откатывается, `errors = seen`. Так же ведёт себя приём вылетов.
* **Неизвестный `dji_flight_id`** — не ошибка: маршрут кладётся с
  `link_status = UNLINKED` и связывается позже, когда приедет вылет. Молчаливое
  угадывание запрещено.
* **Секреты DJI в теле** — отказ 400 с кодом причины, без эха содержимого в лог.

### `POST /drones/api/field_geometry_sync`

Тело: `{contours: [{external_id, content_md5, sha256, source_format,
geometry_geojson, area_ha_computed}]}`. Ссылка **не передаётся** — collector
скачал по ней и забыл. Приёмник, увидев `signedURL` в теле, отвечает 400.

Идемпотентность по (`external_id`, `content_md5`): та же версия геометрии
второй раз ничего не создаёт.

## 9. Безопасность подписанных ссылок

Порядок, обязательный для collector:

1. браузер получает `signedURL` штатным запросом сайта;
2. collector берёт её **из объекта в памяти**;
3. скачивает, проверяет размер (потолок) и формат;
4. считает свой sha256;
5. отправляет **геометрию и хеши**, но не ссылку;
6. затирает ссылку в рабочем объекте немедленно.

Ссылка не попадает в базу, в лог, в отчёт, в фикстуру, в git, в API и в
интерфейс. Проверяется тестом, который прогоняет полный цикл на подложном
ответе и ищет подстроку ссылки во всём, что цикл записал.

**Подпись DJI не воспроизводится.** Запрос формирует сайт, collector только
слушает — правило, уже действующее для списка вылетов (`browser.py`, шапка
модуля), распространяется на маршруты без изменений.

Массовая закачка: очередь с ограничением скорости, повторы с отступом,
докачка с места обрыва, **кэш по `contentMd5`** (скачивается только то, что
изменилось), журнал полноты по образцу `LandsResult`. При 5 489 контурах
первичный проход разбивается на партии; далее меняются единицы в сутки.

## 11. Отказоустойчивость

| Отказ | Поведение |
|---|---|
| Сессия DJI истекла | код выхода 2, как у существующего сбора; маршруты не теряются |
| Ответ не разобрался | прогон продолжается, ответ кладётся в карантин целиком с хешем; счётчик ошибок растёт |

## 12. Роли и права

Новых ролей не заводится. Существующая модель прав Vehicle Soft:

* **чтение** экрана доказательств и очереди — те же, кто видит модуль дронов;
* **решение** в очереди (принять, отклонить, оставить неподтверждённым,
  назначить поле, исправить связь, зафиксировать ручную площадь) — отдельное
  право модуля, как это сделано для актов запчастей;
* каждое действие пишет строку в `drone_coverage_review_actions`: кто, когда,
  старое значение, новое, причина, комментарий, ссылка на доказательство.
  Удаления нет — только новая строка.

## 13. Финансовый контур

Этап наблюдения и ничего кроме, пока владелец не решит иначе:

* существующие начисления **не меняются**;
* `new_work_area` **не перезаписывается**;
* новая площадь показывается рядом, никогда вместо;
* расхождения копятся, очередь наполняется, статистика набирается;
* `VERIFIED` заблокирован константой.

Переход к применению — отдельное решение владельца, отдельный коммит,
отдельная запись в трековом файле. Никакой автоматики, которая «включится
сама, когда наберётся статистика».
