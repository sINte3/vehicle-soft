## 3. Период и популяция

Дни отчёта (UTC+5) с `2026-09-01` по последний полный день, присутствующий в базе
на момент `plan`. Граничные дни загружаются только ради хронологии борта. Если

## 4. Кандидаты

Все записи периода, у которых существующий `dji_area.structural.screen` (через
сухой прогон `dji_area.pipeline`) дал `structural_candidate = True`. Оцениваемый
набор — кандидаты с `scalar_source_check = True`; кандидаты с несовпавшим скаляром
тоже идут в сбор V4 и показываются отдельно (в августе таких было 0 из 428).

Предсказание по каждому кандидату, фиксируемое до раскрытия: **RETAINED** —
проверенный прирост счётчика не превышает 1 % RAW.

## 5. Контрольная выборка NORMAL

Из записей периода, которые кандидатами **не** являются и имеют RAW > 0. Запись
относится к первой подходящей страте в порядке N3, N2, N1, N4, N5.

| Страта | Определение (только метаданные списка) | Объём |
|---|---|---|
| N3 `SHORT_HIGH_RATE` | длительность ≤ 120 с и RAW / длительность ≥ 49 м²/с (нужно ≥ 7 м/с при захвате 7 м) | все, не более 100 |
| N2 `AUTO_NO_WIDTH` | `mode_name == 4`, ширины нет | все, не более 100 |
| N1 `EQUAL_RECENT` | RAW равен RAW одной из трёх предыдущих записей того же борта | все, не более 150 |
| N4 `CONTIGUOUS_AUTO` | `mode_name == 4`, ширина есть, зазор до предыдущей записи борта 0…120 с | 60 случайных |
| N5 `RANDOM` | всё остальное; слои борт × {AUTO, MANUAL}, пропорционально, не менее 6 на непустой слой | 300 |

N1–N4 — места, где в августе жили пропуски правила (ширина заполнена, зазор 2–110 с,
повтор скаляра). N5 отвечает на другой вопрос: нет ли **неизвестного** класса. Ноль
находок на 300 случайных записях ограничивает его распространённость сверху
примерно 1 % (95 %).

Случайность — `random.Random(20260918)` по записям, отсортированным по
`flight_id`. Повторный `plan` с тем же входом обязан дать тот же план и тот же
SHA-256; второй план в тот же каталог инструмент не пишет.

Предсказание по каждой контрольной записи: **NORMAL** — счётчик подтверждает RAW
в допуске резолвера `max(20 м², 1 % RAW)`.

## 7. Оценка кандидатов и критерий приёмки

Классификация — существующими `structural.py` и `resolver.py` через
`dji_area.pipeline`; параллельного классификатора нет.

- **Оцениваемый** кандидат: резолвер выдал `controller_delta_area_m2` (окно GOOD,
  счётчик закодирован на обеих границах).
- **Попадание**: прирост ≤ 1 % RAW. **Промах**: прирост > 1 % RAW.
- **Опровержение**: статус `RAW_CORROBORATED` или `RAW_CORROBORATED_QUALIFIED`, то
  есть счётчик подтверждает весь RAW.
- **NOT_EVALUABLE**: V4 нет, окно неполное, канал площади отсутствует, baseline
  неизвестен, чужая идентичность, немонотонный счётчик. Не попадание и не промах.

Приёмка, зафиксированная владельцем до прогона:

1. не менее 99 % оцениваемых кандидатов — попадания;
2. ни одного опровержения.

Дополнительное условие состоятельности: оцениваемых не меньше 90 % кандидатов;
иначе итог `INCONCLUSIVE`, а не `PASS`. Вместе с долей печатается точная
95-процентная нижняя граница Клоппера–Пирсона: на 150 кандидатах даже 150 из 150
гарантируют лишь 98 %.

Записи, где счётчик плоский, а применение наблюдалось (`APPLICATION_WITH_FLAT_COUNTER`),
считаются попаданиями по критерию 1 (это утверждение о счётчике), но в учётный
класс `PHANTOM_PROVEN` не входят — резолвер оставляет их нерешёнными.

## 8. Оценка контроля

Пропуск правила — контрольная запись, которой резолвер по проверенному окну дал
`COUNTER_FLAT_RAW_OVERSTATED` или `PARTIAL_RECORDED_OVERSTATEMENT`. Считается
отдельно по стратам и по бортам, без объединения с кандидатами.

Повторяемый пропускаемый класс считается **заподозренным**, если в случайной
страте N5 пропусков два и больше, либо если три и больше пропуска в любых стратах
разделяют одну сигнатуру списка (режим, наличие ширины, корзина зазора, повтор
скаляра). Для N5 печатается верхняя 95-процентная граница распространённости.

Находка в контроле правило не меняет. Она описывается как ограничение, а решение
о новой версии правила принимается отдельно и проверяется на другом периоде.

## 9. Итоговые величины сентября

Считаются по всем записям периода и не сливаются в одно число.

| Величина | Определение |
|---|---|
| DJI RAW | Σ RAW |
| PHANTOM_PROVEN, RAW-экспозиция | Σ RAW по классу |
| проверенный реальный прирост | Σ `controller_delta_area_m2` по классу |
| подтверждённое завышение | экспозиция минус прирост |
| PHANTOM_STRUCTURAL, нерешённая экспозиция | Σ RAW по классу; **не обнуляется** |
| REVIEW, экспозиция | Σ RAW по классу; автоматической коррекции нет |
| проверенный подытог | Σ corrected по `CERTIFIED` (как в существующем отчёте) |
| RAW минус подтверждённое завышение | справочно; нерешённое внутри остаётся по RAW |

Инвариант, проверяемый машиной: RAW = NORMAL + PHANTOM_PROVEN + PHANTOM_STRUCTURAL +
REVIEW по экспозиции, и число записей классов равно числу записей периода.

## 10. Чего этот holdout не устанавливает

Физическую площадь осаждения, соответствие заданного междурядья реальной полосе,
вычитание перекрытий и любую биллинговую семантику. `billable_area_m2` остаётся NULL.

### 11. Калибровка объёма на августе

Август — обучающий месяц, в holdout он не входит. На копии августовской
replay-базы инструмент дал: 428 кандидатов (все со совпавшим скаляром), контроль
N3 = 45, N2 = 5, N1 = 64, N4 = 60 из 402, N5 = 300 из 7093 — всего 902 записи на
8196, то есть 11 % месяца. Для 17 дней сентября ожидается около 650 записей.

На тех же данных приёмка дала бы `PASS`: 425 оцениваемых из 428, 425 попаданий,
нижняя граница 99,30 %, опровержений нет. Контроль нашёл оба известных скрытых
фантома августа (687623234 и 696203208) с одной сигнатурой
`mode=4|width=Y|gap=0-1s|equal=Y`. Двух случаев мало для флага повторяемого
класса (порог — три), но сигнатура названа заранее: если сентябрь даст третий
такой же, это будет ожидаемая находка, а не подгонка.

### 12. Где составляется план

Сентябрьского списка в базе площадки может не быть, а сборщик живёт на рабочей
машине. Поэтому план разрешено составлять на одноразовой списочной базе из дампа
`drone_collector --dry-run` (шаг `list-db`). Экран и конвейер те же; отличие одно:
хронология ведётся по нику, а не по паспортному `hardware_id`, потому что список
DJI борта не несёт.

Эквивалентность проверена на полном августе: план из 33 дневных списков
форензик-архива совпал с планом по replay-базе — те же 428 кандидатов, те же
признаки скаляра, те же страты N1–N4. Случайная страта N5 отличается составом
(другой порядок ключей слоёв), что на её смысл не влияет.

Отчёт исполняется уже на базе площадки с настоящим `hardware_id` и называет
расхождение плана и базы в обе стороны: кандидаты, которых не было в плане, и
кандидаты плана, которых база не отмечает.

### 13. Инструмент заморожен наравне с правилом

Прежняя редакция хешировала `tools/dji_area_holdout.py` отдельно от правила, и
его правка между `plan` и `report` была **предупреждением**. Это неверно: в этом
же файле лежат `candidate_outcome`, `control_outcome` и сам вердикт, поэтому
подмена порога или знака сравнения между двумя шагами прошла бы с пометкой в
углу отчёта.

Теперь файл входит в `FROZEN_FILES` наравне с восемью файлами `dji_area`. Его
правка после фиксации плана — `INVALID`, код возврата 4, отчёт не строится.
Версия протокола поднята до 2, и план версии 1 отвергается (в обороте его не
было: живой holdout не начинался).

Тесты сюда намеренно не входят: они не участвуют ни в отборе, ни в оценке, и,
заморозив их, отпечаток ломался бы от любой новой проверки.

### 14. Контрольные ворота входят в общий вердикт

Прежде `systematic_miss_suspected` был наблюдением и на `PASS` не влиял. Это
делало контроль бессильным: правило могло систематически пропускать целый класс
и всё равно получить `PASS` по своим же кандидатам.

**Приёмка кандидатов остаётся в точности прежней** (раздел 7): ≥ 99 %
оцениваемых с приростом ≤ 1 % RAW, ни одного опровержения, ≥ 90 % оцениваемых.
Она считается и печатается отдельным полем `candidate_verdict`.

Рядом с ней — `control_gate`, отдельное поле, с теми же порогами раздела 8:

| Условие | Ворота |
|---|---|
| ≥ 2 `RULE_MISS` в случайной страте N5 | `FAIL`, причина `SYSTEMATIC_MISS_IN_RANDOM_STRATUM` |
| ≥ 3 `RULE_MISS` одной сигнатуры в любых стратах | `FAIL`, причина `SYSTEMATIC_MISS_BY_SIGNATURE` |
| иначе | `PASS` |

Сигнатура определена кодом до данных: режим, наличие ширины, корзина зазора,
признак повтора скаляра.

Общий вердикт собирается в объявленном порядке:

1. нарушена целостность → `INVALID` (код 4);
2. отказ по кандидатам → `FAIL` (код 3), называется причина о самом правиле;
3. отказ ворот → `FAIL` (код 3);
4. кандидаты `INCONCLUSIVE` → `INCONCLUSIVE` (код 5);
5. иначе → `PASS` (код 0).

Смысл порядка: «мало данных» не смеет прятать доказанную находку, а из двух
отказов называется тот, что о правиле.

**Одиночные несистематические находки holdout не валят.** Они остаются видимыми
в отчёте построчно, с сигнатурой и стратой. Именно так выглядел бы август: два
скрытых фантома на 902 записи — `control_gate = PASS` с двумя видимыми строками.
